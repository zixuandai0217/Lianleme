# Issue: 实时姿态纠错：PoseGraph 的关键点采集、动作周期切分与成本节流

## Problem Statement

用户练深蹲时其实不知道自己的膝盖在往里扣。健身房里最贵的资源不是器械，是一个能站在旁边说"膝盖往外推"的人；没有这个人，用户只能靠镜子、靠手机录完回看、或者靠感觉。镜子看不清侧面，录完回看要等到组间休息，而错误动作在这一组里已经重复了十几次。这个缺口有代价：动作代偿长期积累就是关节疼痛和伤病，而用户拿到伤病的第一反应是"我练错了但没人告诉我"。

系统目前对动作质量完全失明。训练计划只知道"这组做完了没有"，不知道"怎么做完的"；打卡表单里的自学难度是主观的，跟动作是否标准无关；而伤病风险这类判断本可以拿动作质量做证据，现在只能靠完成率猜。用户也无法量化进步——深蹲深度从半蹲到全蹲，系统里看不到任何区别。

这件事的技术约束很具体。摄像头必须在浏览器里、不能依赖 GPU、不能把视频传上云；动作质量的分析又需要理解整段运动，不能只看一帧。同时成本必须可控：如果每一帧都送给视觉模型，费用和延迟都会失控，实时反馈变成"等五秒才出一句话"。用户还很可能没有配置自己的 API Key，那时候姿态纠错不能整个消失。

隐私是这条链路上最硬的一条线。骨架关键点是可以还原人体形态与动作习惯的生物特征数据，用户在自己家里对着摄像头练，默认预期是"没人在看"。因此上传什么、留多久、能不能进模型记忆，必须在设计时就定死，而不是等出事再补。

## Solution

今日训练的入口里多一个「姿态纠错」模式：用户把手机架好，浏览器在本地实时提取 33 个 Keypoint 并画出骨架——这一步完全在设备上完成，断网也照常显示。系统按 Motion Cycle（一次完整动作，通常 2-4 秒）把关键点序列切成一段一段，每个周期结束时把这一小段骨架轨迹交给后端，后端识别动作类型、评估动作质量，然后回一句话：哪里不对、怎么改、该看哪个关节。

反馈在周期结束后一两秒内出现，形式是文字 + 语音播报 + 骨架上的高亮（出问题的关节和连线标红，做对的部位标绿）。同一类问题不会在二十秒内反复念给你听；一次训练会话里对模型的调用有硬上限，超了就自动退回纯几何规则，用户不会因为额度用完而失去功能。

动作评估是规则优先、模型增强：膝内扣、躯干过度前倾、左右不对称、下蹲深度不足这类判断由角度与比例阈值直接算出来，确定、瞬时、离线可用；模型负责识别这是深蹲还是硬拉、把几何问题翻译成一句人话、并补充规则覆盖不到的综合判断。没有 Key 或调用失败时，前一半照常工作，后一半降级成模板文案。

一次训练结束，用户能看到本次每个周期的质量分与曲线；跨次只保留聚合分（例如平均质量分、最常见的问题类型），关键点序列本身在周期处理完成后即被丢弃，不落盘、不进模型长期记忆、不写日志。

## User Stories

1. 作为正在训练的用户，我想要打开摄像头就在画面上看到自己的骨架，以便我边做边确认身体的位置和对称性。
2. 作为做深蹲的用户，我想要每组结束后一两秒听到"膝盖往外推一点"这种具体指令，以便我在下一组立刻改，而不是等回家看录像。
3. 作为必须侧向拍摄硬拉的用户，我想要系统知道我的拍摄角度并按角度选用不同的判断标准，以便它不会因为视角给我一个错误结论。
4. 作为网络不稳定的用户，我想要骨架绘制在断网时仍然流畅，以便我至少能靠实时骨骼看自己的动作。
5. 作为没有配置 API Key 的用户，我想要仍然拿到基于角度的基础纠错，以便姿态功能不是"配了 Key 才能用的空壳"。
6. 作为在自己客厅训练的用户，我想要摄像头画面与关键点都不被保存，以便我不用担心家里被看见。
7. 作为某个动作老是做不标准的用户，我想要出问题的关节被高亮出来，以便我知道该看身体的哪个部位。
8. 作为想知道纠错有没有生效的用户，我想要看到每次训练的动作质量分会话汇总与跨次趋势，以便判断自己的动作是不是真的变好了。
9. 作为被识别错动作的用户，我想要手动指定动作或重新开始这一组，以便系统不会一直按错误的动作类型评分。
10. 作为戴耳机的用户，我想要纠错通过语音播报，以便我不用一直低头看屏幕。
11. 作为在意 Key 额度的用户，我想要系统对同一个问题不反复调用模型，以便我的一次训练不会烧掉一大堆额度。
12. 作为想安静训练的用户，我想要能关掉"深度点评"只留基础提示，以便页面不聒噪、也不产生模型调用。
13. 作为使用老旧手机的用户，我想要设备不支持时能退回"上传视频离线分析"或纯手动记录，以便功能不至于完全不可用。
14. 作为关注伤病风险的用户，我想要动作质量摘要能进入训练计划的伤病风险评估，以便"我最近这个动作一直不稳"这件事被系统记住（聚合层面）。
15. 作为在意数据自主权的用户，我想要清除我的姿态聚合记录，以便我的生物特征数据不会被无限期留存。

## Implementation Decisions

### 1. 部署形态：本地提取 + 会话式上传

- 前端用 MediaPipe Pose 在浏览器内提取 33 个 Keypoint（`x, y, z, visibility`，归一化坐标），前端保留全部 33 点（来自 ADR-0002 的关键点精简策略）。
- 传输采用 **HTTP JSON 短轮询式上行**（每次推送一批帧），每秒 3-5 帧，与 ADR-0002 数据流一节一致；**不引入 WebSocket**。理由是当前工程没有 WS 基础设施（无连接管理、无上行背压、无重连语义、鉴权也要重做），而一个 Motion Cycle 只有 8-20 帧，短轮询的延迟增量远小于模型调用本身；ADR-0002 的优势段提到"后端 WebSocket"，与本 ADR 数据流一节不一致，此处按数据流一节决策（见 Further Notes）。
- 反馈下行同样走 HTTP：周期结果由前端轮询获得（或随下一批帧的响应顺带返回，实现二选一，但对外契约一致：客户端能在周期结束后的下一次请求里拿到结果）。
- **为什么这是必须新造的 seam、以及为什么它仍然在最高层**：姿态是"上行流 + 周期粒度结果"的新交互形态，既有 SSE（单向文本流）与一次性 JSON 接口都表达不了"持续推帧、按周期取结果、会话过期即失效"。但新 seam 仍是 **HTTP 路由层**——新增的是会话资源的四个操作（创建 / 追加帧 / 取结果 / 结束），不是新协议。代价是延迟与流量略高，收益是复用现有的鉴权、错误语义、依赖注入与测试骨架。

### 2. 会话资源契约

```
POST   /api/pose/sessions              创建会话        → { session_id, ttl_seconds, upload_interval_ms, camera_hint }
POST   /api/pose/sessions/{id}/frames  追加一批帧      → { accepted, cycle_state, result? }
GET    /api/pose/sessions/{id}/result  取当前周期结果  → { cycle_id, …, summary? }
POST   /api/pose/sessions/{id}/finish  结束会话        → { cycles_count, avg_quality, issues_histogram }
```

- 会话归属当前登录用户，跨用户访问一律 403；会话空闲超时（量级：分钟）即销毁，过期后访问返回"会话已结束"语义（用 404 + 稳定错误码，前端据此提示重开，不退化成"服务器错误"）。
- 帧批请求体是纯数据，不含图片与视频；服务端不提供任何回放能力（没有"取回这一段的骨架"接口，这是刻意的）。
- 单批帧数上限与单会话总帧数上限都必须在服务端强制，防止客户端无节制上传（也防止一次会话把内存吃满）。
- 会话状态只在服务端内存里持有（这是有意的：它必须能被快速丢弃，且不应该有持久化的诱惑）；进程重启会话即失效，前端提示重开，不视为错误。

### 3. PoseGraph 节点与状态形状

Graph 形状（来自 ADR-0002 的"关键点序列 → 动作识别 + 质量评估 → 纠错反馈"）：

```
ingest_frames → segment_cycle ──未成周期──▶ 等待（不产出结果）
                     │
                     └─成周期─▶ recognize_action → evaluate_quality → feedback
                                      └─识别失败─▶ request_recalibration
```

状态形状（本 spec 定稿；ADR 只给了阶段名）：

```python
PoseState = {
  "session_id": str,
  "user_id": int,
  "camera_view": "front" | "side",
  "exercise_hint": str | None,          # 用户手动指定的动作（可选，优先于模型识别）
  "frames": [Frame],                    # 当前周期内的帧窗口
  "cycle": { "start_ms", "end_ms", "duration_ms" } | None,
  "action": { "name", "confidence", "source": "llm" | "user" } | None,
  "quality": { "score": 0-10, "issues": [Issue], "highlights": [KeypointRef] } | None,
  "feedback": { "text", "tts_text", "tone" } | None,
  "degraded": bool,
  "degrade_reason": str | None,
}

Frame = { "t_ms", "keypoints": [{ "x", "y", "z", "visibility" }] × 33 }
Issue = { "type", "severity": "info" | "warn" | "critical", "joints": [...], "hint" }
```

- `segment_cycle` 是唯一的循环入口：不成周期就直接返回等待态，不产生任何模型调用——这是成本控制的第一道闸。
- 每个周期是独立执行单位：上一周期的失败（模型超时、解析失败）不得影响下一周期。因此 Graph 以"周期"为一次调用，而不是以"会话"为一次长驻任务。
- 全流程只有识别失败这一个非正常分支（转 `request_recalibration`：要求用户回到起始姿态重新开始这一组，而不是给一个错误的评分）。

### 4. Motion Cycle 切分

- 切分信号优先用**主关节角度序列**（膝角 = 髋-膝-踝、肘角 = 肩-肘-腕、髋角 = 肩-髋-膝），按当前候选动作集合选择；没有候选动作时用"手腕高度 + 髋高度"的粗信号（人在做动作时这两条最不容易被遮挡）。
- 周期判定：信号出现一个完整"起点 → 极值 → 回到起点附近"的往返，且满足时长边界（最小 1.5s、最大 6s，对应 CONTEXT 中"2-4 秒"的常态并留出慢速/大重量余量）；回到起点附近允许容差，避免每周期越漂越远。
- 起始姿态要求：稳定 300ms 后才开窗（来自 ADR-0002 缓解方案的"要求用户保持标准起始姿态"），并要求 `visibility` 达标的点数超过阈值，否则不评分，只提示"站进画面 / 让全身入镜"。
- 姿态质量差的周期（大量关键点低置信度、人体出框、多人入镜）标记为"不可评估"，不产生分数，也不消耗模型调用；这类周期数进会话汇总，让用户知道是不是机位问题。
- 关键点缺失用线性插值补齐、低置信度点不参与角度计算；插值策略对"是否构成周期"和"是否可评估"两个判断都生效。

### 5. 动作识别与质量评估

- **规则优先**（ADR-0002 未指定实现方式，此处按 ADR-0003 的混合模式精神决策）：几何规则给出确定性问题项，例如膝内扣（双膝横向距离相对髋宽的比例低于阈值）、躯干前倾角超限、左右不对称（侧向偏移差）、下蹲深度不足（膝角极值未达深度阈值）、手腕/肘部轨迹外翻、节奏异常（向心/离心时间比）。每条规则产出 `Issue`，含问题类型、严重度、涉及关节、以及一句模板提示。
- **模型增强**：每周期最多一次调用，输入是**降采样并摘要后的**关键点序列——每周期 8-12 帧、含关节角度特征、`camera_view`、`exercise_hint`（若有）；输出是动作类型、置信度、综合质量分（0-10）、以及对规则问题的自然语言改写。temperature=0。
- **融合**：最终评分 = 规则问题严重度决定的基础分（有严重问题直接压到低分段），模型分只在规则未发现严重问题时参与微调（取较低者，宁可保守）；模型识别出的异常若规则完全没有覆盖，作为 `info` 级补充进入反馈，但不改名分数段，避免模型随机性把评分抖动。
- **动作识别失败**（置信度低于阈值或模型输出不可解析）：不给评分，转 `request_recalibration`，并允许用户从常见动作里手选（手选后 `action.source=user`，下一周期直接按该动作评分）。
- **质量分语义**：0-10，10 = 该周期无明显问题；严重问题越多、越靠前的关节链问题扣分越重。分数只用于本会话与聚合趋势，不直接进入计划强度计算（那属于计划调整域）。

### 6. 反馈呈现

- 一个周期给一句主提示 +（可选）一句补充：先说最严重的那一个问题，不要罗列全部问题。
- 语音播报（TTS）与文字同一内容，可关闭；语气遵循 West Coast Slang（ADR-0006）：中文为主、每句话最多 1-2 个英文词、带少量 emoji，例："homie 膝盖往外推一点，knees out!"。禁止医疗诊断口吻（不说"你的半月板有问题""你这是髌骨软化"），只说动作层面的事实与改法。
- 视觉：出问题的关节/连线高亮（严重→红、提示→橙），做对的侧面对照用绿；同时高亮"目标姿态参考线"（如膝盖应与脚尖同向）帮助用户理解。
- 提示语生成分三档：有模型 → 模型改写；无模型 → 模板（每个 `Issue.type` 一份模板）；连续同一问题 → 升级为更具体的变体模板，避免用户听腻后忽略。

### 7. 成本节流与降级

节流是四层，缺一不可：

1. **周期粒度**：只在 Motion Cycle 结束时调用一次，帧级永不调用（ADR-0002 明确否决了"每帧调视觉模型"）。
2. **去重窗口**：同一 `Issue.type` + 同一动作在 20 秒内不重复播报；同一周期内同一类型只报一次。
3. **会话硬上限**：单次训练会话的模型调用次数有硬上限（量级：数十次）；用尽后本会话转纯规则并提示一次"这次先给基础提示，深度点评已暂停"。连续失败 3 次同样熔断，本会话不再尝试。
4. **输入最小化**：每周期帧数上限（≤12）+ 关键点摘要，不上传原始帧率数据。

降级路径：

- 无用户 Key 且系统回退被禁用 → 直接进入纯规则模式，`degraded=true`，`degrade_reason=api_key_unavailable`；**不返回凭据错误、不引导去配置 Key**（用户可能就想用基础模式）。
- 模型超时/限流/输出不可解析 → 该周期返回规则结果 + 模板文案，标记降级；下一周期继续尝试（受熔断约束）。
- 规则也不可用（关键点质量太差）→ 返回"不可评估"与机位提示，不给分数，不猜测。
- 前端能力不足（无 WebAssembly、无摄像头权限、非安全上下文）→ 不创建会话，页面提示并给出"上传视频离线分析"或手动记录的入口（ADR-0002 缓解方案）。

### 8. 数据、隐私与保留边界

姿态数据是生物特征，按最严格的一档处理：

- **不落盘**：关键点序列、帧批、周期片段一律不写数据库、不写对象存储、不写临时文件。会话状态只存在于进程内存，会话结束或空闲超时即释放。
- **不进 LLM 长期记忆**：调用为一次性请求，不带会话历史；不使用任何 memory/thread 持久化；不同周期的调用互不携带对方数据。
- **不写日志**：日志只记录会话标识的哈希/短标识、周期序号、耗时、错误分类、规则命中类型与模型是否降级；绝不记录坐标、角度数值序列、或识别出的动作与问题组合到可还原个人的粒度（按会话聚合计数即可）。
- **不上传媒体**：只有关键点坐标上行；摄像头画面、音频、视频帧永不出设备。
- **最小化上传**：只上传当前周期窗口内的降采样帧；周期处理完成后服务端立刻丢弃窗口，不保留"上一周期"数据（除聚合计数）。
- **跨会话只留聚合**：会话结束时由结束操作写入数值摘要（周期数、平均质量分、问题类型直方图、首次/末次时间）——**这是全流程唯一被持久化的姿态数据**，供训练历史与趋势使用；用户可清除这些聚合记录，清除后不可恢复且不能通过其他接口重算。
- **明确告知**：进入模式前用一句话说明"画面不会离开这台设备，只会把骨架坐标用于分析，训练结束即丢"，并给出手动结束入口；用户随时可以停止，停止即停止上传。

### 9. 与计划调整域的唯一接口

- 对外提供一个只读摘要：近期（量级：两周）姿态质量聚合——平均质量分、反复出现的问题类型 top-N、不可评估周期占比、覆盖的训练次数。
- 该摘要可作为伤病风险评估的**可选**输入；字段由本 spec 定义，消费规则（怎么影响评分与是否触发人工确认）属于计划调整域，本 spec 不定义、不越界。
- 摘要里不包含任何关键点级数据，也不包含"哪一天第几组出了什么问题"这类可还原到具体动作实例的细节。

### 10. 前端渲染边界

- 骨架绘制用 Canvas 2D，只用运动相关 12-16 个点连线（ADR-0002 可视化策略）；渲染逻辑与"判断哪些点该高亮"分离——后者是纯函数，见 Testing Decisions。
- 首次加载需要下载 WASM 与模型文件：随前端静态资源自托管（不走公网 CDN，避免隐私与可用性双重风险），并显示加载进度；加载失败时进入"不支持"降级路径，不留白屏。
- 3D 人体模型与肌肉热力图不在此 spec 范围（属独立的 3D 热力图能力）；本 spec 只产出骨架叠加与高亮。

## Testing Decisions

### 好测试的标准

只断言外部可观测行为：会话能否创建、帧批之后 `cycle_state` 如何变化、周期结果里有没有评分与问题项、降级标记与节流是否可观测、过期会话返回什么、以及响应里**不包含**什么（隐私是可断言的）。不断言关节角度的具体计算过程、不断言模型 Prompt 文本、不断言 Canvas 画了什么像素、不断言会话内部用了几个字典。

### 最高 seam：FastAPI 路由层

用 ASGI 测试客户端 + 依赖覆盖 + 隔离数据库（会话本身不落库，但用户与鉴权需要），在这里把 **PoseGraph 执行体**与 **LLM 客户端**替换成可控替身：

- LLM 替身返回固定 JSON（确定性、无网络、不消耗 Key）。规则支路本身不依赖 LLM，所以"无 Key 也能测"不是妥协而是 ADR-0003 混合模式的自然结果。
- 姿态判定替身只在需要精确控制"何时成周期"时使用（喂一段人工构造的关键点序列来触发或不触发周期）；其余场景走真实的周期切分与规则评估，让最有价值的那部分逻辑被覆盖。

为什么不需要更低：本 spec 的风险是"用户能不能听到对的话、没 Key 还能不能用、会不会把额度烧光、会不会留下生物特征数据"——全部可由请求/响应表达。更低（直接调 `segment_cycle`）会锁死切分算法，而切分阈值恰恰是要靠真实拍摄数据迭代的部分。

**为什么这里必须新造 seam，以及它为什么仍在最高层**：姿态是上行流式数据，既有 seam（一次性 JSON、单向 SSE）表达不了"持续推帧、按周期取结果、会话过期"。但新 seam 只是同一层的四个新端点，复用既有 ASGI 测试骨架、鉴权守卫与错误语义，因此它依然是"最高可观测面"，而不是一个需要单独搭基础设施的协议层。

### 前端 seam

把"数据 → 视觉参数"抽成纯 TypeScript 函数直接单测：

1. 关键点 + 角度 → 问题项列表与严重度（何时算膝内扣、对称性、深度不足）；
2. 问题项 + 周期结果 → 高亮集合（哪些关节/连线该标红、标橙、标绿）与要显示的提示文案选择；
3. 上传节流：给定时间戳序列与上一批帧，算出"这批该不该上传、要不要跳过"（节流决策是纯函数，便于断言）。

MediaPipe 初始化、Canvas 绘制、TTS 播放只做冒烟（模块可加载、生命周期不抛错），不作为主 seam——渲染层的正确性靠人工目视，测试无法稳定表达。

### 被测模块

1. 姿态会话 API（创建、追加帧、取结果、结束、越权、过期）
2. 周期切分（成周期/不成周期的外部可观测差异）
3. 几何规则评估（问题类型、严重度、评分区间）
4. 反馈生成（有模型 / 无模型 / 降级文案、去重窗口）
5. 节流与熔断（会话上限、连续失败、关闭深度点评）
6. 隐私边界（响应中无坐标、结束后无残留可查询数据）
7. 前端纯函数（问题项推导、高亮集合、上传节流）

### 必测行为清单

- 创建会话：返回 `session_id` 与 TTL；未登录 401；访问他人会话 403。
- 推送不足一个周期的帧：保持"等待"态，返回体里没有评分，且替身 LLM 的调用计数为 0（成本闸门可断言）。
- 推送一个完整周期：返回动作类型、0-10 质量分、至少一条问题项；`camera_view=side` 的同一段序列与 `front` 得到不同的问题集合（视角影响判断）。
- 明显膝内扣的合成序列：`issues` 包含该类型且 `severity` 至少为 warn，质量分落在低分段。
- 同一问题在 20 秒内重复出现：第二个周期不重复播报（反馈文本为空或仅"保持"），但评分仍在更新。
- 同一周期内模型只被调用一次（替身计数断言）。
- 无 Key + 系统回退关闭：周期结果 200、`degraded=true`、有规则问题项与模板文案，且替身 LLM 调用计数为 0。
- 模型抛超时：周期结果仍返回规则评分，`degraded=true`；下一周期仍会尝试（未熔断）。
- 连续 3 次模型失败：此后每个周期都不再调用模型（计数不再增长），会话摘要标记熔断。
- 会话调用次数达到上限：后续周期转纯规则且只提示一次。
- 关键点质量过差（低置信度占比高）：返回"不可评估"与机位提示，无评分，且不消耗模型调用。
- 动作识别失败：返回重新校准语义 + 可选动作列表；用户手选动作后，下一周期按该动作评分且 `action.source=user`。
- 会话空闲超时后推送帧：404 + 稳定错误码，前端可提示重开。
- 结束会话：返回周期数、平均质量分、问题直方图；**响应体中不出现任何关键点数组**（隐私断言）。
- 结束后再查询会话：拿不到任何坐标级数据（只有聚合）。
- 上行超过单批帧数上限：被拒绝且错误可读，不静默截断。

## Out of Scope

- 多视角融合、3D 重建、深度相机；单视角（正面或侧面）是明确前提。
- 帧级实时反馈（<100ms）与逐帧标注；反馈以 Motion Cycle 为单位。
- WebSocket / WebRTC 推流；本 spec 明确选择 HTTP 短轮询。
- 离线视频批量分析做成正式产品（仅作为能力不足时的降级入口，不定义其交互细节）。
- 动作库扩充与"教练评分体系"的专业化；动作识别只覆盖常见自由重量与自身体重动作。
- 康复、医疗诊断、疼痛部位判断；系统只评动作形态，不评身体状况。
- 姿态数据回填到 3D 肌肉热力图（ADR-0005 列为后续，不在此）。
- 移动端 App、后台常驻采集、多人同框分析。
- 姿态质量分如何影响训练强度/计划量；只在"伤病风险摘要"这一处提供输入。

## Further Notes

- **ADR 未定 / 内部不一致，此处决策**：ADR-0002 的数据流一节写"HTTP 短轮询（每秒 3-5 帧）"，优势一节却写"2-3 天完成前端集成 + 后端 WebSocket"。本 spec 采用短轮询：现有后端没有任何 WS 设施，而上行数据本就是低频批量；WS 的收益（低延迟）在这里被模型调用延迟吞掉。若将来需要亚秒级反馈，替换点被收敛在"帧批上行"这一个契约后面。
- **ADR 未定，此处决策**：姿态分析的实现方式是规则 + 模型混合（规则优先、模型增强），而不是纯模型。ADR-0002 只描述了"LLM 深度分析"，但未考虑 BYOK 下用户可能没有 Key，以及每周期调用的成本；混合模式与 ADR-0003 的既有决策精神一致，并让"无 Key 可用"成为结构性保证而非补丁。
- **ADR 未定，此处决策**：周期切分的信号与阈值（主关节角度、1.5-6 秒、300ms 起始稳定、容差回归）。ADR 只给了"2-4 秒/周期"的常识区间，未给可实现判据。
- **ADR 未定，此处决策**：动作识别失败的处理是"要求重新校准 + 允许手动选动作"，而不是给一个带低置信度的评分。ADR-0002 只说"用户可重新开始"，但没说不给评分——不给分数更安全，也避免低质量数据污染趋势。
- **ADR 未定，此处决策**：会话式 HTTP 资源（而非 WS）与"会话状态只存内存、重启即失效"。持久化会话会与"不落盘生物特征"直接冲突。
- **ADR 未定，此处决策**：模型资源自托管而非公网 CDN。ADR 只说 MediaPipe 可 WASM 运行，未指定分发方式；自托管同时解决离线可用与"不向第三方暴露加载行为"两个问题。
- **ADR 未定，此处决策**：跨会话只保留聚合摘要（周期数、平均分、问题直方图），并给用户清除入口。ADR 完全没有讨论保留策略，但这是生物特征数据必须先定的事。
- **现状缺口**：代码库里没有 PoseGraph、没有 MediaPipe 依赖、没有 WebSocket 路由；前端依赖清单里也没有任何 3D/姿态相关包。因此本 spec 的"新增依赖 + 新增会话路由"都是净新增，不存在与既有实现兼容的包袱；反过来说，也没有既有的流式基础设施可以借用。
- **精度与机位风险**：MediaPipe 的深度（z）精度有限（ADR-0002 已承认）。侧面拍摄的硬拉、以及镜头角度偏离水平的情况会系统性偏移角度阈值。缓解手段是机位引导（全身入镜、镜头与髋同高、正面或正侧）、按 `camera_view` 使用不同阈值，以及在结果里对"机位可能不准"的周期降低置信度而不是直接判错。
- **隐私实现注意**：会话内存里持有的是可还原动作习惯的生物特征，因此不能进应用日志、不能进异常上报的 payload、不能在调试模式下落盘。任何"为了排查把帧序列存一份"的想法都必须被拒绝；排障只能靠规则命中类型与会话级计数。
- **跨 spec 对齐**：姿态质量摘要作为伤病风险分析器的可选输入，消费规则在计划调整 spec；3D 渲染与模型资源不在本 spec。三项能力边界：本 spec 谈"怎么采、怎么切、怎么省、怎么保隐私"。

> **迁移约定**：本 spec 唯一需要落盘的是跨会话聚合摘要（周期数、平均分、问题直方图），属于改表，必须遵守全组统一约定——见 `analysis-task-persistence` spec 的「迁移与数据模型落地约定」一节（ORM 为唯一事实源、迁移与模型手写对齐、按交付追加 revision、可回滚、方言判断只出现在兼容层）。关键点序列与帧批仍一律不落盘，这条迁移只承载数值摘要。

## 落地修订（工单 40）

姿态会话与周期切分的落地取舍：

1. **会话只存进程内存**（ADR-0010）：不落库、不写文件、不写日志；空闲 30 分钟过期
   （每次成功请求续期），进程重启即失效。TTL 用单调时钟，测试可注入；多 worker 部署需要
   粘性路由，这条写进 ADR-0010 与部署注意事项。
2. **端点与形状**：`POST /api/pose/sessions`（会话标识、有效期、建议间隔 200ms、机位提示）、
   `POST /api/pose/sessions/{id}/frames`、`GET .../result`、`POST .../finish`。帧只收
   `{t_ms, keypoints[{x,y,z,visibility}], person_count}`；图片/视频字段一律 422 拒绝，
   响应从不回传关键点坐标。
3. **上限**：单批 60 帧、单会话 3600 帧、`t_ms` 单调不减、每用户最多 3 个进行中会话
   （后者与逐帧顺序校验是落地时补的防护：前者防止单客户端开窗耗尽内存，后者防止客户端
   时间回拨构造伪周期；都属于 §2 未明说但必要的服务端强制项）。超限返回
   `pose_batch_too_large` / `pose_session_frame_limit` / `pose_frames_out_of_order` 等稳定
   错误码，绝不静默截断。
4. **切分算法**：纯函数、无依赖。默认膝角链（髋-膝-踝），按机位选择最可见的一侧，可见度
   低于 0.3 的点不参与、单帧缺失在 700ms 内线性插值。周期定义：起点稳定 300ms（±8°）→
   幅度 ≥25° → 首次回到起点 ±12°；时长必须落在 1.5–6.0 秒，越界不构成周期。返回周期标识
   （`cyc_{起始毫秒}`）、起止与时长，未成周期保持 waiting 且无评分。
5. **质量闸门**：可见度占比 <0.6、出画占比 >0.4 或 `person_count > 1` 的周期标记为不可
   评估，返回机位提示、无评分、零模型调用（`model_calls` 计数可断言）。
6. **错误语义**：未登录 401；他人会话 403；不存在/过期 404 `pose_session_not_found`；
   已结束后再写帧或取结果 409 `pose_session_finished`；非法载荷 422；均与 5xx 可区分。
7. **PoseGraph 最小实现**：只注册 `ingest_frames` 与 `segment_cycle` 两个节点，通过依赖注入
   可替换为替身；工单 41/42 在此之上扩展识别与评估，不改变本票契约。
8. **结束会话**：返回周期数、可评估/不可评估计数与总帧数，重复结束幂等；
   `avg_quality`/`issues_histogram` 在工单 43 之前保持 0/空并带 `quality_available=false`，
   不伪造成真实评分。
9. **范围说明**：MediaPipe 抓取在浏览器侧运行，本票不引入后端模型依赖，也不包含前端采集页；
   采集 UI 与自托管 Wasm 资产不属于本票。


## 落地修订（工单 41）

规则评估与骨架高亮的落地取舍：

1. **纯规则评估器**：`evaluate_cycle(frames, camera_view)` 只依赖关键点与配置，确定性、
   零模型、零网络；每个可评估周期在切分完成后立即评估，等待中/不可评估周期保持
   `score=null`、`issues=[]`、`highlights=[]`。
2. **问题与阈值**：正面视角评估膝内扣（膝相对髋-踝线的内偏移/髋宽）、左右不对称（膝角差）、
   节奏；侧面视角评估躯干前倾（肩-髋线相对竖直）、下蹲深度（最小膝角）、节奏。阈值按合成
   序列标定并做边界测试；真实 MediaPipe 噪声需要后续调参，这是已知风险。
3. **质量分**：从 10 分起扣，严重（critical）每项 −5、提示（warn）每项 −2、info 不扣分，
   钳制 0–10 并保留一位小数；问题越多/越严重分数单调不升。有严重问题时直接落到低分段
   （≤5），与 spec「有严重问题直接压到低分段」一致。
4. **严重度词表对齐 spec**：`info | warn | critical`；高亮沿用同一 severity 由 UI 映射
   颜色（critical 红、warn/info 橙）。问题项与高亮由同一份数据生成，一一对应。
5. **视角影响判断**：同一段序列在 front / side 下命中不同的规则子集，接口按视角选用阈值。
6. **反馈克制**：每个周期最多一句主提示 + 一句补充，按严重度取最严重的问题，不罗列全部。
7. **零模型与零凭据依赖**：规则路径不读 Key、不调用模型；无 Key 时不出现凭据错误。
8. **聚合**：结束会话返回周期数、平均质量分、问题类型直方图与不可评估占比；
   `quality_available` 只在至少一个周期被真实评估时为 true。


## 落地修订（工单 42）

姿态模型增强、节流与降级的落地取舍：

1. **每周期一次调用**：在规则评估之后执行，temperature=0、单次 8 秒超时，使用用户自己的
   BYOK 客户端；输入是降采样后的角度摘要（8–12 帧的膝/躯干角、机位、动作提示与规则问题
   摘要），不含身份、邮箱、照片或完整坐标序列。
2. **动作词表**：`squat | deadlift | other`（不扩动作库）；模型置信度低于 0.4 一律归 `other`，
   用户手选动作走同一归一化。`source` 标明 llm/user。
3. **分数融合**：规则有严重问题时以规则分为准（低分段）；否则取规则分与模型分的较低者，
   模型永远不能把分数抬高；模型分缺失只保留动作与文案。
4. **节流状态机**：闸门顺序 keyless → 熔断 → 预算 → 调用。单会话调用上限 20 次，用尽后
   本会话转纯规则并只提示一次「深度点评已暂停」；连续 3 次失败熔断本会话（成功清零）；
   同一「问题类型 + 动作」20 秒内不重复播报（没有动作标识时按问题类型去重），评分照常更新。
5. **降级可观测**：超时 / 限流 / 鉴权失败 / 输出不可解析分别映射到稳定原因码；无可用 Key
   且系统回退关闭时整会话纯规则、零调用、原因码 `api_key_unavailable`，响应不含「去配置
   Key」的指引文案。凭据/工厂自身异常不再等同于无 Key：本周期按 `provider_error` 降级并
   计入连续失败，下一周期仍会重试，不永久改写会话状态。
6. **模型补充观察**：模型可返回规则未覆盖的观察，作为 `info` 级问题进入反馈（不改分数段、
   不改方向），最多 3 条、每条截断到固定长度。
7. **计数口径**：会话汇总的 `model_calls` 是「实际尝试次数」（闸门通过即计数），
   `PoseGraph.model_calls` 是「成功增强次数」；两者用途不同，不混用。
8. **已知风险**：模型调用在会话锁内执行（单会话串行、最长 8 秒），高并发下会推迟同一会话
   的接帧与结束；后续可把增强移出锁或改异步回填。


## 落地修订（工单 43）

姿态隐私边界与聚合摘要的落地取舍：

1. **唯一持久化的姿态数据**：会话结束时写一行 `pose_quality_aggregates`（迁移 0015）——
   用户、不可猜测的会话标识、开始/结束时间、周期数、可评估/不可评估数、平均质量分、
   问题类型直方图、模型调用次数。只有数值与类型计数，没有关键点、坐标、帧内容或可还原到
   单次动作的明细；同一会话重复结束只命中同一行（`session_id` 唯一），不会二次写入。
2. **聚合读取与删除**：`GET /api/pose/aggregates`（本人最近若干条）、
   `GET /api/pose/aggregates/{id}`（他人 403 且不返回内容、未知 404 稳定码）、
   `DELETE /api/pose/aggregates/{id}`（硬删除，204）。删除后同时丢弃内存里的该会话，
   重复结束返回 404；由于原始帧从不落盘，删除后无法通过任何接口重算。
3. **伤病风险摘要**：`GET /api/pose/injury-summary?days=14` 只返回数值——窗口天数、覆盖
   会话数、训练天数、周期数、可评估/不可评估占比、加权平均质量分、top-5 问题类型计数；
   不含关键点或单次动作明细，供下游只读消费。
4. **隐私断言**：会话创建、帧批、结果、结束四个响应都断言不含关键点字段，也不含
   「≥3 个连续数值的数组」或 `{x,y,z}` 对象；结束后帧与结果接口保持 409，原始坐标不可恢复。
5. **日志边界**：结构化日志只允许会话短哈希（会话 id 的 SHA-256 前 8 位）、周期序号、耗时、
   错误分类与规则命中类型；坐标、角度序列、帧内容一律不写。这条取舍已补进 ADR-0010 §3.1。
6. **范围说明**：`model_calls` 一并持久化用于成本核对（正文列举之外的小幅增量）；
   聚合列表/详情接口是对「供训练历史与趋势使用」的最小落地，前端趋势页不在本票范围。
7. **已知限制**：会话仍是单进程内存（ADR-0010），多 worker 部署需要粘性路由；否则在
   另一个 worker 上重复结束可能重建已删除的聚合行。
