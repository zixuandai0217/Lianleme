# Issue: 首次建档引导：让用户一进首页就知道自己缺哪一步

## Problem Statement

新用户登录后落到首页，首页会给一条"数字教练建议"，但它只认两件事：有没有体型分析、有没有训练计划。真实的首用链路其实有四个前置条件——配置自己的 AI Key、补全身体档案、完成体型分析、生成训练计划——少任何一步，用户点进去都会被拦下或被要求先做别的事，而首页不会提前告诉他这件事。已有什么：首页已经能针对"没分析"和"没计划"给出单条推荐；计划页空态有三步清单；体型分析页有四阶段闭环。缺什么：这三处判定各写一套、互不知情。

更具体的现状问题有三处。其一，首页完全没有"AI Key 未配置"这个状态。体型分析页、计划页、陪练页都在 BYOK 门禁之后，未配 Key 的用户在首页看到"去看体型"，点下去被弹回个人资料页——引导本身制造了一次跳转回环。其二，计划页空态把"生成一周训练"写死成"当前步骤"，无论用户是否已有计划；而计划页在"还没有计划"（后端返回资源不存在）时会把这条正常首用状态当成错误渲染成红色告警条，首用用户第一眼看到的是报错。其三，首页判定"有没有计划"时把所有请求失败都当成"没有计划"：一次网络抖动就会让首页提示去生成计划，而重新生成会把当前 active 计划归档——误判的代价是用户丢掉现有计划。当前 API 封装层只把错误压成一句字符串消息，调用方无法区分"资源不存在"和"网络/服务失败"，这是误判的结构性原因。

还有一处文档与代码已脱节：P1-1 原文要求"没填档案 → 引导去个人资料"，但代码现状是健身档案已经从个人资料页搬到了身体数据页，个人资料页只剩账号信息与 Key 管理。照字面实现会把用户送到一个没有档案表单的页面。另外，后端登录响应里已经有"是否新用户"的标记，前端从未使用；注册后统一落到首页或 Key 配置页，之后不再有任何"首次使用"的差别对待——"首次"目前只存在于文档里。

最后，用户真正需要的不是"看完引导"，而是"知道现在缺哪一步、点哪个按钮能补上"。因此引导必须是可推导、可重放的状态，而不是一次性弹窗；也必须是单一判定来源，否则首页、计划页、分析页会继续各说各话。

## Solution

给用户一条贯穿首用阶段的最小引导：在首页用一块"下一步"区域回答三个问题——现在缺哪一步、为什么缺、点哪里补上；其余页面复用同一套判定，只改呈现形态（首页整块引导、计划页步骤清单、分析页阶段闭环）。引导的每一步只对应一个主行动按钮，已完成步骤以只读进度呈现，用户任何时候都能靠侧栏离开，引导不新增路由守卫、不做强制跳转。

判定顺序按"真实前置依赖"排：先 AI Key（否则后续 AI 页面会被门禁拦回），再身体档案（分析会把档案一起提交，缺档案会降低判断质量），再体型分析，再训练计划，最后第一次打卡。走完这五步后引导自动消失，首页回到"今天怎么练"，不残留"首次使用"痕迹。

对已有数据的老用户，引导只针对还没形成闭环的缺口：已经能训练的用户不会被反复要求补档案，档案缺失最多降级为一条次要提示，不抢主行动。对拿不到数据的情况（网络或服务失败），引导不猜、不下结论，只给中性提示与"看看今日安排"，避免把用户推向"重新生成计划"这种有破坏性的动作。

文案沿用首页现有的产品语气：简短、第二人称、直说下一步，不写催促，也不使用英文俚语梗（ADR-0006 的西海岸俚语只用于 AI 生成的教练对话与姿态纠错，不覆盖产品界面文案）。步骤描述只写事实与动作，保持可核对；引导不承诺效果、不使用打卡施压式话术。

## User Stories

1. 作为刚注册的新用户，我想要一登录就在首页看到"现在只差这一步"，以便我不用自己在四个页面之间摸索。
2. 作为还没配置 AI Key 的新用户，我想要首页就把"先配 Key"当成当前步，以便我点主按钮时不会被弹回配置页。
3. 作为配好 Key 但档案还空着的用户，我想要被引导到真正承载档案表单的页面，以便我不会被送到一个只有账号设置的空页面。
4. 作为已填档案但没做过分析的用户，我想要首页主按钮直达体型分析，以便我先把身体画像建起来。
5. 作为已有分析结果但没有计划的用户，我想要首页直接提示"生成本周计划"，以便我不用先点进计划页才发现空态。
6. 作为已有计划但一次都没打卡的用户，我想要引导停在"完成第一次打卡"，以便我知道闭环还差最后一步。
7. 作为已经能正常训练的老用户，我想要首页回到"今天怎么练"，并且不再被反复要求补档案，以便引导不会变成打扰。
8. 作为中途离开、隔几天再回来的用户，我想要引导按我现在的真实数据重算，以便它不会拿上次的结论误导我。
9. 作为删掉过 Key 或换过 Key 的用户，我想要引导立刻回到"配 Key"这一步，以便我能明白为什么 AI 页面又用不了。
10. 作为网络不稳时打开首页的用户，我想要在拿不到计划数据时看到中性提示而不是"你还没有计划"，以便我不会因为误判去重新生成计划、把现有计划归档掉。
11. 作为第一次用身体数据的用户，我想要引导明确告诉我"档案里的目标与训练经验是必填"，以便我一次填对而不是反复被提示。
12. 作为用屏幕阅读器的用户，我想要当前步骤与主按钮被正确朗读、并说明点下去会去哪，以便我听得出该做什么。
13. 作为在手机上使用的用户，我想要引导在窄屏只保留一个主按钮和一排紧凑步骤，以便我不用横向滚动找下一步。
14. 作为产品与工程协作者，我想要"当前缺哪一步"只有一个判定来源，以便首页、计划页、分析页的引导永远说同一件事。
15. 作为维护者，我想要引导完全由数据快照推导、不写入任何"已忽略"状态，以便我修数据或重置用户后引导自动回到正确位置。

## Implementation Decisions

### 判定来源与模块划分

引导判定收敛为一个无副作用纯函数模块，输入是一份"用户首用状态快照"，输出是引导视图模型。该模块不依赖路由、不发起请求、不读时间、不做文案本地化以外的副作用，因此同一份快照必然得到同一份输出。

三处呈现共享这一次判定，各自只做投影：首页取整块引导（标题 + 步骤 + 单一主行动），计划页取"步骤清单"形态，分析页继续用它自己的四阶段闭环。允许三个页面各自保留自己的视觉表达，但"当前缺哪一步"的值只能由这一个模块产生；页面不允许再内联第二套 if/else 判定。

### 判定规则（设计决策：判定表，非实现代码）

状态快照字段（全部来自现有接口，不新增后端能力）：

```
hasApiKey            // 是否已配置自己的 AI Key
hasProfileBasics     // 档案必填项是否齐全
hasBodyAnalysis      // 是否已有体型分析结果
planLookup           // "exists" | "missing" | "unknown"
hasCheckedIn         // 是否已有至少一次训练打卡
```

档案必填项定义为"健身目标 + 训练经验"两项。身高、年龄、性别为可选加分项：它们影响分析质量与计划细节，但缺失不应把用户挡在引导之外。

判定表（自上而下，命中即返回）：

1. `planLookup === "unknown"` → 未知态：只给中性标题与"查看今日安排"，不显示步骤进度、不显示当前步。
2. `!hasApiKey` → 当前步 = 配置 AI Key。
3. `!hasProfileBasics && !hasBodyAnalysis` → 当前步 = 补全身体档案（先档案、后分析）。
4. `!hasBodyAnalysis` → 当前步 = 完成首次体型分析。
5. `planLookup === "missing"` → 当前步 = 生成首份训练计划。
6. `!hasCheckedIn` → 当前步 = 完成第一次打卡。
7. 其余 → 日常循环态：没有当前步，主行动回到"今天怎么练"。

附则（必须实现，否则会与现状冲突）：

- 当第 7 条生效但 `!hasProfileBasics` 时，追加一条可忽略的次要提示（"档案补全能让下周计划更准"），不改变主行动。
- 当 `planLookup === "exists"` 但 `!hasBodyAnalysis`（历史数据里计划存在而结果被清空）时，不回退到分析步，按第 5 条之后继续判定，避免主行动与用户实际能做的事互相矛盾。
- 未知态只由"无法判别"触发，绝不能把请求失败当成"没有计划"。

### 接口契约：错误语义必须可判别

当前 API 封装把所有失败压成一句字符串消息，调用方无法区分"资源不存在"和"网络/服务失败"，这直接导致判定表第 1 条无法实现。设计决策：封装层保留可判别的失败类别（至少"资源不存在"与其他失败两类），调用点据此产出 `planLookup` 的三个取值。这是本项目内的一次契约扩展，不改变任何现有接口的请求/响应形状。

### 数据结构与字段扩展

不新增后端接口、不新增数据库字段。引导所需信息全部已存在：当前用户响应里已有档案、体型分析、Key 状态；计划存在性走现有查询；打卡存在性走现有统计。为消除三处重复判定，前端新增一处共享的"首用状态快照"类型与投影类型，形状为设计决策：

```
type GapKey = "api-key" | "profile" | "analysis" | "plan" | "first-checkin"
type StepStatus = "pending" | "active" | "completed"
type StepTarget = "profile" | "body-data" | "analysis" | "plan" | "today"
```

`StepTarget` 是页面无关的意图标识，由各页面自行映射成实际跳转目标。这样引导模块保持纯函数、不感知路由；将来档案表单位置再变，只改映射，不改判定。

阶段状态词汇复用分析页已有的三态（pending / active / completed），不另起第二套状态机；动作词汇沿用已有的"标签 + 提示 + 目标"三元结构。这是"同构而非重写"的具体含义：新模块借用既有词汇，既有模块不被改写。

### 空态与降级矩阵

| 情形 | 行为 |
| --- | --- |
| 用户数据加载中 | 不渲染引导骨架，整块延后到数据就绪后一次渲染，避免步骤数跳变 |
| 计划查询失败（非"不存在"） | 未知态，不显示步骤进度 |
| 打卡统计获取失败 | 视为"尚未打卡"但只影响最后一个步骤，不改变已验证的前置步骤 |
| 档案部分字段缺失 | 只按必填两项判定，可选字段缺失不提示 |
| 当前步指向的页面需要 Key 而 Key 已配置 | 正常给主行动（此时门禁不会拦截） |
| 当前步指向的页面需要 Key 但 Key 被删除 | 第 2 条优先命中，主行动永远先回到 Key 配置 |

### 文案策略

- 标题一句话说清缺什么，步骤描述只写事实与动作，不写催促。
- 主行动按钮文案以动词开头，且必须与该步骤真实结果一致（例如"生成本周计划"不能写成"看看计划"）。
- 不使用"坚持""必须""别放弃"等施压措辞；不承诺体重或体型结果。
- 未知态文案不包含"失败""出错"字样，也不暗示用户缺数据。
- 所有引导文案集中在一处供评审，避免散落在三个页面各自修改。

### 旧数据兼容

- 旧用户"有分析、有计划、有打卡"直接落到日常循环态，不出现引导。
- 旧用户"有计划但分析结果为空"按附则处理，不回退也不覆盖现有计划。
- 引导不写入任何"已看过/已忽略"标记，因此不产生需要迁移的本地状态；删除记录或重置数据后引导自然回到正确位置。

## Testing Decisions

### 好测试的标准

只测外部可观察行为：给定一份状态快照，断言"当前步、主行动意图、步骤状态序列、是否进入未知态"；给定一个渲染后的页面，断言"屏幕上只有一个主按钮、它的可读文案与目标页正确、进度状态可被辅助技术读到"。不测私有函数名、不测内部状态变量、不测具体类名或样式类。

### 被测模块

1. 引导判定纯函数模块（最高 seam）：用表驱动方式覆盖判定表 7 行 + 4 条附则 + 未知态的边界组合。
2. 首页渲染接线：jsdom 环境下渲染首页，mock 认证状态与 API 层，断言单一主行动与目标。
3. 计划页步骤清单投影：同一份快照下，计划页显示的当前步必须与首页一致（防止两处再次分叉）。

### 最高 seam 及为何不必更低

最高 seam 是纯函数 + 页面渲染两层。判定规则、文案键、降级行为全部收在纯函数里，用最便宜的单元测试就能锁定；页面层只验证"接线正确"，即快照进、按钮出。不需要更低的 seam：再往下 mock HTTP 客户端只会重复验证网络库行为，而本项目已经用一行拦截器统一处理错误，测它没有新信息；也不需要组件级快照测试，因为引导的可观察价值只有"当前步 + 主按钮"，其余都是装饰。

### 页面测试的落地约定

jsdom 测试按文件声明运行环境（项目默认是 node 环境），用真实路由容器挂载页面、mock 认证与 API 模块，跟现有门禁与教练页行为测试的做法一致。禁止用"读取源码字符串并断言包含某个文案"作为主要验证手段——它只能证明代码里出现过某个字符串，证明不了用户看到什么；如果保留这类断言，只作为防止文案被误删的补充。

### Prior art

- 纯函数 + 逐步断言阶段状态：分析页现有的闭环判定及其单元测试（见相关文件）——本 spec 的判定表测试应写成同样的表驱动风格。
- 页面级 jsdom + mock 认证 + 真实路由容器：BYOK 门禁的行为测试与数字教练行为测试（见相关文件）。
- 不新增后端测试（本 spec 无后端行为变更）。

## Out of Scope

- 提醒与召回（推送、邮件、连续未训练提醒）——依赖通知基础设施，另一条线。
- 引导的"跳过/不再显示"持久化开关（本 spec 明确不做，理由见 Implementation Decisions）。
- 新用户注册后的欢迎页、分步向导、强制流程拦截。
- 个人资料页与身体数据页之间的信息架构调整（本 spec 只承认现状并正确指路）。
- 计划生成算法、分析算法与门禁策略本身。
- 埋点与转化分析。

## Further Notes

- 与 P1-1 字面的差异已记录：档案表单当前在"身体数据"页，个人资料页只剩账号与 Key，因此引导目标是"身体数据"而非"个人资料"。若后续把档案迁回个人资料，只需修改意图到路由的映射，判定规则与测试不动。
- 计划被"重新生成"会归档当前 active 计划，这是误判代价高的根因；因此"区分资源不存在与其他失败"不属于体验优化，而是正确性要求。
- 跨 spec：计划的解释性展示在 `plan-explainability`；体重的统计口径与目标偏离判断在 `weight-trend-insights`。本 spec 只负责"缺哪一步"，不定义计划字段，也不定义体重统计。
- 未决：是否把 HTTP 状态码统一暴露到前端错误对象（本 spec 只要求"可判别失败类别"这一最小契约）。
- 未决：首页引导块在窄屏是否折叠为一行——留待视觉实现决定，不影响判定与测试。

1. **唯一判定来源**：首页、计划页空态、分析页四阶段闭环都从 `web/src/lib/next-step.ts` 的
   共享判定取「当前缺哪一步」；页面只做投影与文案，不再各自维护阶段语言。分析页的
   上传/分析子进度只影响视觉，不构成第二套 gap 判定。
2. **计划页空态**：渲染为中性空态（无红色错误条），阶段列表与当前步骤来自共享指南
   （`stages` 的 pending/active/completed 与 `currentStep`），不再把「生成一周训练」写死为
   当前步；已有计划时展示一行安静的「下一步」提示。计划查询失败（非资源不存在）降级为
   中性的 unknown 指南（不提示去生成计划、不出现错误告警）。
3. **入口指向**：档案类入口走 `NEXT_STEP_ROUTES`（身体数据 → `/weight`，即真正承载档案
   表单的页面）；未配 Key 的用户主行动改为「配置 API Key」；空态只有一个主按钮。
4. **分析页闭环**：四阶段状态由共享指南经 `stageStatusFor` 投影（已满足 completed、当前
   active、其余 pending）；分析完成但无计划时主行动为「生成专属训练计划」，有计划时为
   「查看训练计划」（路由同样来自共享目标）。
5. **一致性测试**：一张六种状态（缺 Key / 缺档案 / 缺分析 / 缺计划 / 缺打卡 / 已完成）的
   用例表同时驱动首页、计划页空态与分析页，断言三处当前步骤一致，任何一页漂移即失败。
6. **已知取舍**：只有主计划请求失败时才额外发一次 lookup 以区分「没有计划」与「查询失败」；
   打卡统计在首帧后返回，已打卡用户可能短暂看到首次打卡提示，不会长期偏离。
