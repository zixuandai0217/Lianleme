# Issue: 体重趋势洞察：把折线图变成能读懂的结论

## Problem Statement

身体数据页已经能做的事不少：录入当日体重（同一天重复提交会覆盖，不会产生重复记录）、选择 30/90/180/365 天窗口、看一张自绘折线图、看四张统计卡（当前体重、总变化、最低、最高）、逐条删除历史记录，并且顺带承载了整块身体档案（身高、年龄、性别、健身目标、训练经验）。已有什么很清楚，缺什么也很清楚：它给的是一张图加四个整段窗口的聚合值，没有一句"最近在往哪走"的结论。

具体缺口有四类。第一，没有分段窗口：所有数字都基于当前选中的整段区间，"最近 7 天"和"最近 30 天"无从区分；用户切换 30 天与 90 天时，"总变化"数字会变，页面上却没有任何地方解释口径变了，用户很容易把它读成"我的体重又变了"。第二，极值没有日期：最低/最高只是两个数字，不知道哪天最低，而这恰是用户最想复盘的信息（"上周五那个数是怎么来的"）。第三，训练与体重完全脱节：页面上没有任何训练数据，用户看不到自己练得多的时候体重怎么走，也无法判断"这周体重涨了是不是因为练得多"。第四，目标只存不用：档案里有健身目标（减脂/增肌/塑形/提升体能），但体重模块完全没有引用它，判断方向时默认"下降就是绿的、上升就是红的"——对增肌用户这是错误的价值判断；同时档案里没有任何数值目标体重字段，所以"是否偏离目标"在数据上根本无法回答。

还有两个由现有实现带来的隐形陷阱，必须在设计里承认。其一，统计窗口以"今天"为终点向后推：用户几天没称重时，最近 7 天窗口里可能一条记录都没有，页面给出的不是"数据不足"而是让人困惑的空结论。其二，保存身体档案是整体替换语义且会丢弃未提交的字段：体重页保存档案时只提交身高/年龄/性别/目标/经验，因此档案里原有的体重值会被清掉。任何新增的档案字段（例如目标体重）都必须与整套档案一起提交，否则会被静默丢弃。

## Solution

在身体数据页的统计卡与趋势图之间加一块"趋势解读"，用短句结论 + 可核对的事实行回答四个问题：最近 7 天和 30 天分别往哪个方向走了多少、这两个窗口内的最低与最高分别出现在哪天、这几周训练频率与体重变化是同向还是反向、当前走势是否偏离我的目标。所有判断由前端纯函数从已有数据派生，不新增统计接口、不改记录语义。

口径先说清楚：窗口以"最新一条记录"为锚点而不是"今天"，这样几天没称重的用户仍能看到自己的最近 7 天；数据明显陈旧时明确提示补记，而不是给出可能误导的结论。任何窗口内记录不足两条时不下结论，只说明"数据不足"。

目标判断分两档：档案里填了数值目标体重，就按"当前体重与目标体重的差距 + 最近 30 天方向"判断是否在朝目标走；没填则退化为方向判断（减脂看是否下降、增肌看是否上升、塑形与提升体能看是否维持），并明确告知这是按目标方向推断的保守判断。为此在身体档案里新增一个可选的"目标体重"输入。颜色语义也随之修正：不再用"降绿升红"，改为"朝目标方向为正色、背离为警示色、无目标时用中性色"。

文案用一句正式短句结论 + 中性事实行（体重趋势属报告类文本，按 ADR-0006 不穿插西海岸俚语）；不做因果声称（只说"同期"），不下健康或医学结论。

## User Stories

1. 作为每天称重的用户，我想要看到最近 7 天的体重变化，以便我知道这周在往哪走。
2. 作为想拉长视角的用户，我想要看到最近 30 天的变化与方向，以便我区分"一周波动"和"一个月的趋势"。
3. 作为好几天没称重的用户，我想要在数据明显陈旧时看到补记提示，以便我不会把旧数据当成今天的结论。
4. 作为刚开始记录的用户，我想要在窗口内记录不足时看到"数据不足，暂不下结论"，以便我不被凭空的判断误导。
5. 作为关心极值的用户，我想要看到最近 30 天最低与最高体重以及各自日期，以便我能复盘那天发生了什么。
6. 作为体重有波动的用户，我想要在极值并列时看到最近那天的日期，以便我理解系统选了哪一个。
7. 作为有训练习惯的用户，我想要看到最近四周的训练天数与该周体重变化并列，以便我自己判断训练节奏和体重的关系。
8. 作为减脂目标的用户，我想要系统用我的目标判断方向，以便它不会默认体重下降就是好事、上升就是坏事。
9. 作为增肌目标的用户，我想要体重上升被判定为朝目标前进，以便我不会看到一条红色的"警告"。
10. 作为设了数值目标体重的用户，我想要看到当前体重与目标的差距以及最近的方向，以便我知道还要走多远。
11. 作为还没想好数值目标的用户，我想要系统先按我的健身目标方向做保守判断，以便我不必被强制填一个数字。
12. 作为在 30/90/180/365 天之间切换的用户，我想要解读区始终标注自己用的口径，以便我明白为什么切换后数字变了。
13. 作为删除过错误记录的用户，我想要删除后解读立即重算，以便结论和我的数据保持一致。
14. 作为用屏幕阅读器的用户，我想要趋势结论与极值日期被完整朗读，以便我不依赖折线图也能理解趋势。
15. 作为想快速看懂的用户，我想要解读以一个短句结论开头、下面跟可核对的事实行，以便我一眼抓住方向又能自己验证。

## Implementation Decisions

### 模块划分

1. **趋势统计与文案（前端纯函数，核心 seam）**：输入是体重记录列表、窗口内打卡日期集合、档案（目标与目标体重）与一个可选的"今天"（用于陈旧度判断，默认由调用方传入，便于测试固定），输出是一份完整的解读视图模型。函数无副作用、不发起请求、不读全局时间。
2. **取数层**：负责把接口数据喂给纯函数。体重记录来自现有趋势接口（请求窗口需覆盖 30 天以上，默认 90 天已足够）；打卡日期来自现有月度打卡日历接口，按窗口覆盖的月份聚合去重。纯函数只接收"打卡日期集合"，不关心来源。
3. **页面渲染**：只渲染视图模型，以及新增的"目标体重"输入与保存接线；不含统计判定。

### 统计口径（设计决策：判定规则）

- **锚点**：窗口锚点 = 记录中最大的 `recorded_date`，不是今天。所有"最近 N 天"均以锚点向前推（含锚点当天）。若锚点距今天超过 7 天，判定为数据陈旧，解读区顶部给出补记提示，但结论照常给出并标注"基于最近一次记录"。
- **窗口内变化**：最近 7 天 = 锚点日与锚点前第 6 日闭区间；最近 30 天 = 锚点日与锚点前第 29 日闭区间。区间内变化 = 区间内最后一条体重 − 区间内第一条体重，保留 1 位小数。区间内记录少于 2 条 → 该窗口返回"数据不足"，不产生数值。
- **阶段性极值**：同一窗口内体重的最小值与最大值，各带其日期；并列时取日期更近的一条。窗口内无记录 → 空。
- **周对照（训练频率关联）**：以锚点所在的 ISO 周为第 0 周，向前取共 4 周。每周的体重变化 = 该周最后一条 − 该周第一条（少于 2 条则该周无变化结论）；训练频率 = 该周内不重复的训练日期数。关联结论只做描述性并列（同向/反向/无明显关系/数据不足），明确不做因果与统计相关性推断，文案里用"同期"而不是"因为"。
- **目标偏离判断**：若档案有数值目标体重 `target_weight`：差距 = 最新体重 − 目标体重；方向 = 目标体重是否低于当前体重。判定为"朝目标前进"当且仅当最近 30 天变化方向与目标方向一致且变化幅度 ≥ 0.1kg；判定为"偏离"当且仅当 30 天变化方向与目标方向相反且幅度 ≥ 0.1kg；其余为"基本持平"。若 30 天窗口记录不足 → "数据不足，暂不判断"。若无数值目标但档案有健身目标：减脂→期望下降，增肌→期望上升，塑形/提升体能→期望维持（30 天变化绝对值 < 体重 0.5% 视为维持），据此给出"按目标方向推断"的结论并显式标注推断来源。两者都缺失 → 中性态，只给 7/30 天变化与极值，不给好坏判断。
- **持平与除零**：窗口内所有体重相同 → "持平"，变化显示 0，不出现百分比抖动或除零；体重为 0 或负数属非法数据，直接过滤（接口已有下限校验，前端仍防御）。

### 数据结构与字段扩展

- 档案新增可选数值字段"目标体重"（单位 kg，1 位小数）。已核实：用户档案列本身是 JSONB 容器，新增一个键不改变表结构，因此**不产生数据库迁移，也不触发全组统一的迁移与数据模型落地约定**（该约定见 `analysis-task-persistence` spec 的同名一节，仅在改表时适用）。真正需要同步的是档案的请求/响应 schema 与前端类型——当前档案模型是严格校验的，未声明的键会被静默丢弃，因此只改前端不会生效。
- 档案保存是"整体替换 + 丢弃空值"语义：页面保存时必须一次性提交全部档案字段（身高、年龄、性别、目标、训练经验、目标体重、以及档案体重），否则未提交的字段会被清空。这是本 spec 必须遵守的既有约束，不属于要修的 bug，但实现时必须按此提交。
- 体重记录模型不加字段：记录仍为"日期 + 体重 + 备注"，同一天重复提交覆盖的语义不变。
- 解读视图模型的形状（设计决策）：

```
{
  anchorDate, isStale,
  windows: { d7: WindowInsight, d30: WindowInsight },   // 变化、方向、极值（值 + 日期）、样本数、是否数据不足
  weekly: WeeklyComparison[],                            // 最近 4 周：周起始、体重变化、训练天数、关系描述
  goal: { mode: "numeric" | "direction" | "none", verdict, gap?, reason }  // 朝目标 / 偏离 / 持平 / 数据不足
}
```

### 空态与降级矩阵

| 情形 | 表现 |
| --- | --- |
| 无任何记录 | 沿用现有空态，不渲染解读区 |
| 仅 1 条记录 | 只显示"已记录 1 次，再记一次就能看出方向"与目标差距（若有数值目标），不出变化数值 |
| 7 天窗口记录不足 2 条、30 天足够 | 7 天块显示"数据不足"，30 天块照常 |
| 两窗口都不足 | 解读区整体转为"数据不足"提示，只保留目标差距 |
| 数据陈旧（锚点早于今天 7 天以上） | 顶部补记提示 + 结论标注"基于最近一次记录" |
| 打卡数据缺失/取数失败 | 周对照整体隐藏，其余解读不受影响（打卡不是解读的前置条件） |
| 档案无目标、无目标体重 | 中性态：只给变化与极值，不给好坏判断，颜色用中性 |
| 记录跨度小于 4 周 | 周对照只渲染已有的周 |

### 文案策略

- 结论一句（正式中文短句，不使用西海岸俚语：体重趋势属报告类文本，ADR-0006），事实行中性且带数值与日期。例如结论"最近一个月呈下降趋势"。事实行"最近 30 天 −1.4 kg（从 72.0 到 70.6），最低 70.6 kg（10 月 28 日）"。
- 方向词固定为"下降/上升/持平/数据不足"，不出现"暴瘦""暴增"等煽动性措辞；不出现医学判断与健康风险结论，涉及变化过快时只说"变化偏快，建议关注恢复与记录频率"。
- 训练与体重的关系只写并列事实（"同期训练 4 天，体重 −0.6 kg"），不写"因为练得多所以"。
- 颜色语义：朝目标方向用正向色，背离用警示色，无目标用中性色；不再以"下降=绿、上升=红"为默认。
- 所有解读文案集中在一处，便于统一评审语气；不得在页面内散写结论句。

### 旧数据兼容

- 旧记录没有备注、没有目标体重、没有打卡关联：全部按缺失降级，不报错、不回填。
- 目标体重字段对旧用户为空 → 走方向判断（若目标存在）或中性态。
- 已存在的同日覆盖与删除语义不变；删除后解读立即重算，不缓存。
- 窗口口径变化不改变趋势图与统计卡的既有行为；解读区是新增块，旧数据下表现为"部分数据不足"，不是错误。

## Testing Decisions

### 好测试的标准

只测外部可观察行为：给定记录序列、打卡日期、档案与固定"今天"，断言解读视图模型中的窗口变化值、极值及其日期、周对照的关系描述、目标判定结论与文案键；给定页面渲染，断言"无记录不渲染解读区""单条记录只出提示""目标体重保存后再读回一致"。不测内部函数拆分、不测排序实现细节、不测 SVG 坐标。

### 被测模块与最高 seam

最高 seam 是**纯函数**这一层，它承载全部统计口径与判定规则。表驱动覆盖这些情形：锚点回退到最新记录而非今天、7 天与 30 天方向冲突、窗口内恰好 1 条、极值并列取最近日期、全部体重相同、数据陈旧、打卡日期为空、四周跨月、数值目标与方向目标两条分支、目标体重等于当前体重、非法数据被过滤。

第二层是**页面渲染接线**（一次）：jsdom 渲染身体数据页，mock API 与认证，断言三种降级形态、解读区在无记录时不出现、以及保存"目标体重"后档案请求体包含完整档案字段（这条必须测，因为档案保存是整体替换语义，漏字段会清空数据）。再配合一次纯函数与页面共用同一视图模型的断言，防止页面自己再算一遍。

### 为什么不需要更低层的 seam

- 不为体重接口写后端测试：本 spec 不改变任何接口行为，只是新增一个档案字段（走既有的档案更新路径），而"保存后能读回"已经由页面层的请求体断言与既有档案接口行为覆盖；再写路由层测试只是重复现有契约。
- 不 mock axios 层做统计断言：统计完全在纯函数里，请求层只负责搬运数据，mock 它得不到新信息。
- 不做像素或图表快照：趋势图是既有能力，本 spec 不改；解读区是可读文本，断言文本即可。

### Prior art

- 纯函数 + 表驱动断言：分析页现有的闭环判定纯函数及其单元测试（见相关文件）。
- jsdom 页面渲染 + mock 认证与 API：BYOK 门禁行为测试、数字教练行为测试（均按文件声明 jsdom 环境，项目默认环境是 node）。
- 不要以"读取源码断言包含某个字符串"作为主要手段；它证明不了渲染结果，最多作为文案防删的补充。

## Out of Scope

- 体重目标达成提醒、连续未记录提醒（属提醒召回体系）。
- 体脂率、围度、BMI 等其他身体指标与多指标趋势。
- 由体重趋势驱动训练计划强度调整（属计划调整算法那份 spec）。
- 在记录体重时自动回填档案体重（会引入隐式写放大，明确不做）。
- 统计图表本身的视觉重做（折线图、坐标轴、交互）。
- 数据导出与医疗/健康风险提示。

## Further Notes

- 本 spec 独占体重统计口径（锚点、窗口、极值、周对照、目标偏离阈值）。`plan-explainability` 只使用档案里的健身目标词汇做计划归因，不定义任何体重口径；`first-run-onboarding` 不涉及体重。
- 目标体重字段是本 spec 唯一的前后端 schema 扩展，且不涉及数据库迁移（仍存在档案 JSON 里）。若评审认为不该新增字段，可退化为纯方向判断（判断逻辑已按两档设计，退回只需去掉数值目标分支）。
- 与打卡闭环 spec 的边界：打卡后反馈报告里的"与上次对比、近 7 天平均完成率"属于打卡域，不在本 spec 重复定义；本 spec 的周对照只使用"某周有几天训练"这一个聚合值，不解读单次训练质量。
- 语言决策记录：体重趋势属报告类文本，按 ADR-0006 使用正式中文，不穿插西海岸俚语（俚语只用于教练对话与姿态纠错）。
- 未决：训练频率的取数方式。当前设计复用月度打卡日历按需聚合；若多次请求成为负担，可新增一次性轻量接口，纯函数契约（接收打卡日期集合）不变，属于取数层替换。
- 未决：颜色语义从"降绿升红"改为"朝目标为正色"会影响现有统计卡与历史列表的配色，需要与视觉规范一起确认后再落地。
- 已知现状风险（供实现者注意）：档案保存是整体替换且丢弃空值，任何只提交部分字段的保存都会清空其余档案数据；新增"目标体重"输入必须与现有档案表单一并提交。

## 实现期修订（2026-11-01）
