# Issue: 管理后台运营化（用户列表搜索筛选 / 用户详情钻取 / 导出 / 行为轨迹）

## Problem Statement

管理后台目前只是一个「展示页」。后端只有两个接口：一个统计概览（总用户数、总计划数、总打卡数、7 日活跃用户）和一个用户分页列表（只有 `page` / `page_size` 两个参数，返回 id、openid、昵称、注册时间、是否已有计划、累计打卡数）。前端只有单页 `/admin`，侧边栏只有「数据概览」一项，路由表里也只注册了 `/admin` 一条管理端路由。

PRD 与路线图对这件事的判断是一致的：后台「只有统计卡片 + 分页列表」，缺搜索筛选、用户详情页、行为钻取、导出报表与异常用户识别；路线图还专门点出过「导航里存在 `/admin/users`，但实际路由只注册了 `/admin`」这种「看起来准备好了、实际没闭环」的半成品状态——而现在更彻底：那条未实现的导航项已经被从侧边栏删掉了，路由依旧只有一条。也就是说，运营今天想找一个反馈问题的用户只能一页页翻（每页 20 条），想找「注册了一周还没生成计划的用户」「有计划但两周没打卡的用户」完全做不到，想把这批人导出来做二次分析也做不到。

现有实现还有两处具体的技术债，直接阻碍运营化：列表接口对每个用户额外发起两次 count 查询（是否有计划、打卡总数），用户量一大就是典型的 N+1；返回体里 openid 是明文原值，前端自己截断展示，接口层没有任何最小化原则。另外前端调用管理接口时还在 URL 上拼了一个 `user_id` 参数——身份其实是 token 决定的，这个参数纯属误导，也容易让人误以为可以「以某个用户身份查询」。

## Solution

把后台从「一个展示页」升级为「一个运营工作台」，包含三个页面：数据概览（保留现有卡片）、用户列表（可搜索、可组合筛选、可排序、分页、一键导出）、用户详情（基础档案 + 体型分析摘要 + 当前计划与最近一次调整 + 打卡时间线与连续性 + 体重趋势 + 关键行为轨迹时间线 + 需关注标记）。侧边栏恢复为用户可识别的两个入口；列表的搜索/筛选/排序/分页状态写进 URL，可分享、可刷新、可后退。导出为同步 CSV，严格遵守当前筛选条件，带行数确认与导出审计。权限方面保持「管理端一律只读」，所有管理接口仅接受管理员 token，敏感字段在接口层就地脱敏。

## User Stories

1. 作为运营，我想要按昵称、邮箱、用户 ID、openid 关键字搜索用户，以便从一条反馈里定位到具体用户。
2. 作为运营，我想要按「是否有训练计划」「注册时间区间」「累计打卡数区间」「最近活跃距今天数」组合筛选，以便把需要干预的人群圈出来。
3. 作为运营，我想要按注册时间或最近活跃时间正/倒序排序，以便分别从「最新注册」和「最久没来」两头看。
4. 作为运营，我想要在列表里直接看到每人最近打卡日期与距今天数，以便一眼判断谁掉队了，不用逐个点开。
5. 作为运营，我想要把当前筛选结果导出为 CSV，以便在表格工具里做二次分析。
6. 作为运营，我想要导出前看到「本次将导出 N 行 + 当前筛选条件摘要」，以便确认导出的不是别的数据集。
7. 作为运营，我想要在筛选结果为空时导出按钮不可用并给出说明，以便不会导出一个空文件还以为成功。
8. 作为运营，我想要点进用户详情看到基础档案（昵称、邮箱掩码、openid 掩码、注册时间、是否管理员、API Key 状态），以便判断账号情况。
9. 作为运营，我想要在详情页看到体型分析摘要与最近一次分析时间，以便确认用户是否已完成初始画像。
10. 作为运营，我想要在详情页看到当前训练计划的周结构、难度系数与最近一次计划调整的类型与理由，以便回答「我的计划为什么被改了」这类投诉。
11. 作为运营，我想要在详情页看到打卡时间线（日期、完成率、时长、难度自评）与当前连续天数，以便判断训练稳定性。
12. 作为运营，我想要在详情页看到体重记录的时间序列与记录频率，以便判断用户是否真的在跟进自己的目标。
13. 作为运营，我想要在详情页看到一条关键行为轨迹（注册 → 首次体型分析 → 首次生成计划 → 首次打卡 → 最近活跃），以便定位用户卡在哪一步。
14. 作为运营，我想要列表能按「需关注」标记筛选（注册 7 天无计划、有计划 7 天无打卡、14 天无活跃、连续天数中断），以便每天有一份明确的待办清单。
15. 作为管理员，我想要非管理员访问任何管理接口都返回 403、未登录返回 401，并且前端也直接跳走，以便后台不泄漏数据。
16. 作为管理员，我想要管理接口的响应里永远不出现密码哈希、加密后的 API Key 或联系方式明文，以便把泄漏面压到最小。
17. 作为管理员，我想要每一次导出都有审计记录（谁、什么筛选条件、多少行、什么时候），以便事后追溯数据流出。
18. 作为运营，我想要详情页各区块能独立加载、单独失败不拖垮整页，以便某个数据源慢的时候还能看别的部分。

## Implementation Decisions

**权限（本 spec 唯一负责，其他特征不重复定义）：** 所有管理端接口只接受管理员身份，身份**只来自 token**，不接受任何 URL/查询参数/请求体形式的「我是谁 / 我在查谁」。当前前端在管理接口上拼 `user_id` 的做法必须去掉。判定规则统一为：未登录或无有效 token → 401；已登录非管理员 → 403；管理员 → 200。前端的管理端路由守卫是体验优化，不是安全边界，后端必须独立校验（现有实现已如此，本次要求扩展到所有新接口，且新增接口必须逐条覆盖测试）。管理端第一版**整体只读**：不提供封禁、改角色、删号、重置密码。

**最小化数据原则：** 列表与详情一律不返回密码哈希、加密 API Key、完整 openid、完整邮箱。openid 一律掩码（前 6 后 4，长度不足则整段打码），邮箱掩码本地部分（保留首字符与域名），API Key 只返回状态（未配置 / 已配置 provider 名称）。没有任何接口提供「原始密钥/原始联系方式」的读取路径，需要联系用户的场景走外部流程。

**列表接口契约：** 分页参数 `page`（≥1）、`page_size`（默认 20，上限 100）；`q` 对昵称、邮箱、openid、数字型用户 ID 做模糊匹配（数字精确匹配优先）；筛选参数：`has_plan`、`registered_from`/`registered_to`、`checkins_min`/`checkins_max`、`active_within_days`、`is_admin`、`has_api_key`、`flag`（需关注标记，可多选）；排序 `sort` 取值固定枚举（注册时间升/降、最近活跃升/降）；返回体包含 `items`、`total`、`page`、`page_size`，每项带派生字段：`has_plan`、`plan_difficulty_factor`、`total_checkins`、`checkins_30d`、`last_checkin_date`、`last_active_at`、`days_since_last_checkin`、`flags`。派生字段必须由一次聚合查询算出，禁止对每个用户再发查询（现状的 N+1 必须消除）。`page` 超出范围时返回空 `items` 与正确的 `total`，不报错。

**详情接口契约：** 单个聚合响应，按 `sections` 参数可选返回（默认全部），分区为：`profile`（基础档案与账号状态）、`body_analysis`（最近一次分析摘要：体型、体脂区间、弱势肌群、时间）、`plan`（当前计划周结构摘要、难度系数、周起始日、最近一次调整的类型/理由/时间，若无调整历史则为空）、`checkins`（近 90 天序列 + 连续天数 + 完成率分布）、`weights`（近 90 天序列 + 记录频率）、`timeline`（行为轨迹，见下）、`usage`（AI Key 状态与对话条数等可聚合用量）。某个分区数据源缺失时返回空值而不是报错，保证单区块失败不拖垮整页。

**行为轨迹由既有数据派生，不引入埋点。** 事件类型固定枚举：注册、首次体型分析、最近一次体型分析、首次生成计划、最近一次计划调整、首次打卡、最近一次打卡、首次体重记录、最近一次体重记录、最近一次对话。每条事件含类型、发生时间、简短摘要与可读文案，按时间倒序返回并分页。**注意**：当前数据模型没有登录会话表，也没有 `last_active_at` 字段，因此「最近登录」无法精确得到；第一版把「最近活跃」定义为上述业务事件时间的最大值，并明确在接口文档里说明它不是登录时间（若后续愿意加一个 `last_active_at` 字段在登录时更新，是最小成本的改进，但不在本 spec 范围）。

**异常/需关注标记（服务端计算，非机器学习）：** `new_no_plan`（注册 ≥7 天且无计划）、`planned_no_checkin`（有计划但 ≥7 天无打卡）、`inactive_14d`（≥14 天无任何活跃）、`never_analyzed`（注册 ≥3 天且无体型分析）、`api_key_missing`（未配置 Key，AI 功能不可用）。标记可同时存在，可被列表筛选。

**URL 状态约定：** 搜索词、全部筛选、排序、页码都进查询串；键名与接口参数一一对应（前端不做方言映射）；空值不写进 URL；页码为 1 时省略。前端用一个纯函数在「查询串」与「请求对象」之间双向转换，页面刷新与浏览器前进后退必须还原同样的结果。

**导出格式（本 spec 唯一负责，其他特征不重复定义）：** 同步导出 CSV 文件。编码为 **UTF-8 with BOM**（保证 Excel 打开中文不乱码）；首行是中文表头；列顺序固定并写入文档：用户 ID、昵称、邮箱（掩码）、openid（掩码）、注册时间、是否管理员、是否有训练计划、计划难度系数、累计打卡数、近 30 天打卡数、最近打卡日期、最近活跃时间、是否已做体型分析、API Key 状态、需关注标记（分号分隔）。日期与时间统一 ISO 8601（带时区偏移），布尔值输出「是/否」，空值留空字符串，数值不带千分位。导出必须应用与列表**完全相同**的筛选与排序，不带分页限制但有行数上限（建议 5000 行）：超限时拒绝并明确提示「请收窄筛选条件」，不得静默截断。文件名包含导出日期与筛选摘要的短哈希，响应头带 `Content-Disposition: attachment`。每次导出写一条审计记录（操作者 ID、筛选条件摘要、行数、时间、是否被拒绝），审计记录本身可在管理端以只读方式查询（可选，建议做，成本很低）。

**前后端结构约定：** 管理端路由从一条扩展为三条（概览、用户列表 `/admin/users`、用户详情 `/admin/users/:id`）；侧边栏恢复「数据概览」「用户」两个入口，当前高亮按路径前缀判定；管理端布局已具备的「非管理员跳走」行为保留。列表页工具栏包含搜索框（输入防抖 300ms 后才发请求）、筛选面板（可一键清空）、导出按钮（0 行时禁用并说明原因），表格列可横向滚动；详情页以分区卡片组织，每张卡片独立 loading / 空态 / 错误态。分页、筛选、排序全部服务端完成，前端不做本地过滤。

**时间与边界：** 接口返回的时间统一带时区（UTC 偏移），前端按浏览器本地时间格式化展示；但**筛选的日期区间**按运营本地日界解释后转换为 UTC 区间再查库，并在接口文档里写明，避免「筛 6 月 1 日却少了 8 小时数据」。搜索第一版用模糊匹配 + 既有索引，不做全文索引；性能备注写进代码注释即可。

## Testing Decisions

好测试只断言**外部契约**：请求 → 响应的字段与数值、CSV 文件的字节内容、页面渲染出的可见文本与可交互状态。不断言 SQL 具体写法、不测 ORM 关系、不写整页快照。

**后端最高 seam：FastAPI 路由层**，httpx ASGITransport + `dependency_overrides` 覆盖数据库会话，用 JWT 构造管理员 / 普通用户两种身份。prior art：鉴权守卫路由测试——它已经有「非管理员访问统计接口 403」「管理员 200」的现成用例形态，以及隔离 SQLite + 从用户 ID 构造 JWT 的 fixture 写法（位置见「相关文件」），本次直接扩展。

为什么这是最高且够用的 seam：本特征的全部产品价值是「管理员发出查询 → 拿到正确的列表/详情/文件」，搜索、筛选、排序、聚合、脱敏、导出、权限都是这个契约的一部分；再往下测查询构造会把测试绑死在实现上（而这些查询正是本次要重写的），再往上就只有人工点页面。因此不需要更低层的 seam。

必须在路由层覆盖的外部行为：未登录 401 / 普通用户 403 / 管理员 200，逐一覆盖**每一个**新管理接口（含导出）；按昵称、邮箱、ID 搜索命中与不命中；多条件组合筛选的交集正确；排序两种方向；分页边界（首页、末页、页码越界返回空 items + 正确 total）；`page_size` 超上限被拒或裁剪（按实现约定择一，测试锁定行为）；列表里 openid/邮箱是掩码形态、响应文本中不出现密码哈希或加密 Key 字段；导出 CSV 的表头文本与列顺序、行数与同一筛选下的 `total` 一致、含 BOM、日期格式符合约定；导出超上限被拒绝且响应可读；导出后审计记录存在且记录了行数；`q` 里的特殊字符（`%`、`_`、引号）不会造成通配符泄漏或 500；详情接口在缺计划/缺分析/缺体重的用户上返回空分区块而不是报错。

**前端最高 seam：纯 TS 辅助函数**——查询串 ↔ 请求对象的双向映射、掩码与日期格式化、需关注标记的文案映射、导出按钮可用性判定。prior art：体型分析旅程的纯函数与其单测（把页面判断抽成纯函数，只喂输入看输出，位置见「相关文件」）。这些是产品的全部判定逻辑，组件只负责展示，所以不需要更低层的 hook 测试。

**页面级测试用 vitest + jsdom**：MemoryRouter 挂载管理端路由 + mocked `useAuth`（管理员/非管理员）+ mocked API 模块，断言：输入搜索词后防抖结束发出一次带该词的请求；改动筛选后 URL 查询串更新且表格内容随之变化；导出按钮在 0 行时禁用并展示提示文案；详情页各分区渲染对应数据与空态；非管理员挂载管理端路由时被重定向。prior art：API Key 网关的 jsdom 页面测试（MemoryRouter + mocked auth，断言路由与查询串，位置见「相关文件」）。不断言 className，不对整页做快照，不测第三方表格组件内部实现。

## Out of Scope

- 任何写操作：封禁/解封、改角色、删号、重置密码、代用户改计划。只读后台之外的写能力需要单独设计二次确认与审计。
- 异步导出、定时报表、报表订阅、数据仓库同步。
- 留存/漏斗分析平台、埋点 SDK、A/B 实验。
- 实时在线状态、实时日志流、告警系统。
- 用户画像标签体系与推荐运营策略。
- 邮件/短信触达用户（属于提醒通道，只在 reminder-recall 里定义）。
- 多租户/多组织隔离与细粒度角色（第一版只有「管理员 / 非管理员」两档）。
- 登录会话表与「精确最近登录时间」（见 Implementation Decisions 的说明）。

## Further Notes

**读代码时确认的现状问题：**

1. 列表接口对每个用户再各发两次 count 查询（是否有计划、打卡总数），是明确的 N+1；再加上详情接口要聚合四五个数据源，如果沿用逐用户查询的写法，用户量上千后后台会明显变慢。本次要求在服务端用聚合查询一次算齐派生字段。
2. openid 在接口层是明文下发、由前端负责截断展示；接口层没有任何脱敏。这个模式在新增详情页、导出功能时会直接扩大泄漏面（导出文件尤其危险），所以脱敏必须在接口层做，而不是依赖前端。
3. 「最近活跃/最近登录」在当前模型里**没有数据支撑**：用户表只有创建与更新时间，没有登录会话表也没有 `last_active_at` 字段。本次用业务事件时间派生；如果运营真的需要精确登录时间，最小改动是在登录成功时更新一个字段，这属于后续优化，不该在本特征里悄悄加一张会话表。
4. 前端在管理接口 URL 上拼了 `user_id` 参数，后端接口签名里并没有这个参数（FastAPI 会静默忽略），属于「看起来在控制身份、其实没有」的误导性代码，容易让后来者以为可以越权查询。本次一并清理，并让管理端身份只由 token 决定。
5. 路线图里记录的「导航有 `/admin/users` 但只注册了 `/admin`」已经演化为「导航项被删掉了，路由仍然只有一条」——说明这块的收口一直没做；本次要把路由、导航、页面三者一次对齐，并补一条回归测试防回退。

**方向性决策记录：**

- 后台第一版只读：写操作涉及责任边界与审计成本，先把「看得见、查得到、导得出」做扎实。
- 导出同步 + 上限 5000 行：单次导出足以覆盖一次运营动作，超限要求收窄筛选比排队等异步任务体验更好；行数上限同时保护数据库与浏览器。
- CSV 带 BOM 而不是提供 xlsx：不引入服务端表格库依赖，Excel 兼容性足够，解析成本最低。
- 用服务端派生 flags 代替「异常用户识别模型」：规则透明、可解释、可测，运营能理解为什么某人被标出来。
- 筛选/排序/分页全部服务端完成：前端本地过滤在分页数据上必然算错总数，这是后台类产品的经典坑。

## Implementation Decisions（工单 36 落地修订）

工单 36（后端用户列表）实现期对上述契约的落地取舍，覆盖正文中与之冲突或含糊的表述：

1. **`page_size` 超上限选择「拒绝」而非裁剪**：`page_size > 100` 直接返回 422（沿用查询参数
   校验），与「`page` 越界返回空 `items` + 正确 `total`」刻意区分——参数越界属于调用方错误，
   页码越界属于正常浏览行为。测试锁定 422，前端应据此禁用/收窄每页条数。
2. **「一次聚合查询集」的落地形状**：一次列表请求固定发两条业务 SQL——一条 `COUNT(*)`、
   一条当页行；计划 / 打卡 / 体型分析 / 体重 / 对话各自一个按 `user_id` 分组的聚合子查询，
   以 LEFT JOIN 挂到用户表上。「最近活跃」用嵌套 CASE 求六路时间戳（注册、计划、打卡、
   分析、体重、对话）的最大值，避开 `greatest` / 多参 `max` 的方言差异；最近一份计划的
   难度系数用窗口函数 `row_number() over (partition by user_id order by created_at desc,
   id desc)` 取排名第一行。计数查询只投影用户 id、不读 JSON 列。实测当页 1 人与 20 人的
   语句数相同（2 条业务语句，另有 1 条鉴权查询），AC4 用查询计数断言锁死。
3. **注册时间区间边界语义**：`registered_from` 含下界、`registered_to` 不含上界；不带时区的
   入参按 UTC 解释（只给日期即当天 00:00 UTC）。正文要求的「运营本地日界」由前端换算成
   UTC 区间后传入，接口不猜调用方时区，接口文档写明该语义。
4. **掩码在 API 层落地**：openid 前 6 + 后 4，长度 ≤10 时整段打码（保留长度）；邮箱保留本地
   部分首字符 + `***` + 完整域名；`llm_provider` 只在确实配置了 Key 时返回，`has_api_key`
   只暴露布尔状态；密码哈希与加密 Key 的列既不 select 也不进入响应模型（无对应字段名）。
5. **需关注标记口径**：阈值常量（7 / 7 / 14 / 3 / 30 天）集中在服务层，SQL 过滤与响应里的
   标记使用同一组常量计算，避免两处漂移。`planned_no_checkin` 把「有计划但从未打卡」视作
   无限久未打卡并计入；`never_analyzed` 认可用户表体型分析快照与体型分析历史任一存在；
   `inactive_14d` 以六路事件时间最大值判定。多选 `flag` 取**并集**（任一命中即返回），单选
   即精确筛选。
6. **数字关键字只改变排序优先级**：`q` 为纯数字时，用户 ID 精确命中的行排在所选 `sort`
   结果之前，其余模糊命中仍按所选排序；`sort` 的固定枚举语义不被搜索改变。
7. **兼容旧前端字段**：保留 `id`、`nickname`、`openid`、`created_at`、`has_plan`、
   `total_checkins`（`openid` 由明文改为掩码，仍是字符串）；新增 `email_masked`、`is_admin`、
   `has_api_key`、`llm_provider` 与全部派生字段；旧前端在 URL 上拼的 `user_id` 查询参数被
   忽略（身份只来自 token），并有回归测试保证它不改变结果集。
8. **`has_plan` / `plan_difficulty_factor` 口径**：任意计划记录（含 archived）存在即
   `has_plan=true`；难度系数取最近一份计划的 `difficulty_factor`，无计划时为 `null`。
9. **时间字段格式**：响应里的时间统一是带时区的 UTC（序列化为 `Z` 后缀，等价 `+00:00`），
   `last_checkin_date` 为 `YYYY-MM-DD` 日期；筛选入参按 UTC 瞬时值比较，避免「筛 6 月 1 日
   却少 8 小时数据」的错位由后端隐式猜测造成。

## 落地修订（工单 38）

工单 38（CSV 导出 + 导出审计）实现期对正文「导出格式」一节的落地取舍，覆盖与之冲突或含糊的表述：

1. **两个端点与权限**：导出为 `GET /api/admin/users/export`，只读审计为
   `GET /api/admin/export-audits`；两者都只接受管理员 token（未登录 401、非管理员 403、
   管理员 200，逐端点覆盖测试），身份只来自 token，不接受任何「我是谁 / 我在查谁」的参数。
   导出路由必须声明在带路径参数的详情路由之前，否则 `export` 会被当成用户 ID 解析。
2. **CSV 形状**：UTF-8 with BOM 开头、`\r\n` 行尾；首行固定 15 列中文表头——用户 ID、昵称、
   邮箱、openid、注册时间、是否管理员、是否有训练计划、计划难度系数、累计打卡数、近 30 天打卡数、
   最近打卡日期、最近活跃时间、是否已做体型分析、Key 状态、需关注标记。时间列是 ISO 8601 带
   `+00:00` 偏移（与列表的 `Z` 等价），日期列 `YYYY-MM-DD`，布尔输出「是 / 否」，空值留空串，
   难度系数不带千分位且整数值写作 `1`（而非 `1.0`），Key 状态只写「未配置」或已配置的 provider
   名称，需关注标记按固定枚举顺序以 `;` 分隔。邮箱与 openid 复用列表的同一套掩码函数；文件里没有
   密码哈希、加密 Key 或原始联系方式（测试直接断言文件字节中不出现这些串）。
3. **行数上限的落地**：配置项 `ADMIN_EXPORT_ROW_LIMIT`（默认 5000 行）。导出先发与列表同语义的
   计数查询、再取行；总数超过上限时返回 400，detail 为
   `{"code": "export_row_limit_exceeded", "message": "…请收窄筛选条件后重试…"}`，不产出任何文件，
   绝不静默截断。总数在取行之前已知，因此审计里的 `row_count` 对成功与被拒都是真实行数。
4. **0 行与不分页**：筛选结果为 0 行时返回 200 的「仅表头文件」（BOM + 表头 + 行尾），与「超限」
   严格区分；导出不带分页，行数恒等于同条件下列表的 `total`（测试用两次不同筛选各导一次，
   与列表的 id 顺序逐一比对）。
5. **筛选条件只有一份**：列表与导出共用同一个筛选条件对象与同一套条件 / 排序 / 序列化逻辑，
   导出只是在其上换掉分页、加上行数上限；新增筛选只改一处，两边同时生效，不存在两套查询漂移。
   导出额外取一个「是否已做体型分析」布尔（列表不需要该列），该字段不进入列表响应模型。
6. **审计表**：新增 `admin_export_audits`（`operator_id` 外键 users、`filter_summary`、
   `filter_hash`、`row_count`、`outcome` = `success` / `rejected`、`rejection_reason`（成功为
   NULL）、`created_at`），迁移 0007 与 ORM 逐列对齐。每一次**通过鉴权**的导出尝试写一条：成功
   写 success，被拒写 rejected 并带可读原因；写入后显式提交，保证随后抛 4xx 时请求级回滚不会
   吞掉这条被拒记录。401 / 403 的尝试进不到处理器、也无法归因到操作者，因此不写审计（测试锁定
   该边界）。审计接口只读、按时间倒序、分页，不提供任何修改入口。
7. **文件名与筛选摘要**：`user-export-YYYYMMDD-<hash8>.csv`，日期取导出当时的 UTC 日期；`hash8`
   是「只含显式传入条件 + 排序」的规范化摘要（`key=value`、固定顺序）的 SHA-256 前 8 位，
   同一筛选必得同一文件名、不同筛选必得不同文件名，审计记录存同一哈希，可把文件对回记录。
8. **响应头**：`Content-Disposition: attachment; filename="…"`（纯 ASCII，不用 `filename*`）、
   `Content-Type: text/csv; charset=utf-8`、`X-Content-Type-Options: nosniff`。
9. **未做与已知边界**：不做 CSV 公式注入（`=` / `+` / `-` / `@` 开头的单元格）转义——导出只对
   管理员开放，后续若把导出扩到非管理员再补；不做异步导出、定时报表与 xlsx。新增配置项有默认值，
   无需改环境变量即可运行。

## 落地修订（工单 37）

工单 37（用户详情聚合 + 脱敏）实现期对正文「详情接口契约」「行为轨迹由既有数据派生」「最小化数据原则」的落地取舍，覆盖与之冲突或含糊的表述：

1. **端点与分区参数**：详情为 `GET /api/admin/users/{user_id}`，只接受管理员 token（未登录 401、
   非管理员 403、未知用户 404，逐条覆盖测试；非管理员读自己的详情同样是 403——不存在「以某个
   用户身份查询」的旁路）。`sections` 同时接受 `?sections=profile,usage` 与
   `?sections=profile&sections=usage` 两种写法，省略或留空返回全部分区；响应里的 `sections` 按
   固定枚举顺序回显本次实际返回的分区。未知分区名返回 422 而不是静默忽略——否则一个拼写错误
   会让运营页看起来「这个用户什么都没有」。该路由声明在 `/users/export` 之后，避免 `export`
   被当成用户 ID 解析。
2. **响应形状与空态语义**：「没请求」与「没有数据」必须可区分：未请求的分区整个键不出现，
   请求了但数据源为空的分区是显式 `null`。具体地：`profile` 只要有用户就有；`body_analysis` /
   `plan` 无数据时为 `null`；`checkins` / `weights` / `timeline` / `usage` 恒为对象，内容为空
   （空序列、计数 0、轨迹里至少一条「注册」）。缺计划、缺分析、缺体重的用户照常 200，只有未知
   用户 ID 是 404。分区按需查询：未请求的分区不发查询（只请求 `profile` 不付轨迹的代价），
   单个数据源为空不影响其他分区。这是单用户请求，不套用列表「一次聚合查询集」的批量约束。
3. **档案复用列表的同一份聚合**：新增 `user_directory.load_user_row()`，与列表共用聚合子查询、
   标记阈值与掩码函数，`profile` 分区的字段形状与列表项一致。这样「需关注标记」「最近活跃」
   在两个页面永不分叉，也避免为详情再写一套阈值。
4. **计划分区复用计划解释投影**：`plan` 直接调用 `PlanService.get_current_plan_with_explanation()`，
   取当前 active 计划的 `week_start` / `difficulty_factor` / `status`，把七天结构压成「周几、
   训练重点、是否休息日、动作数、总组数、预计时长」的摘要，并原样带上 `generation`（生成依据）
   与 `latest_adjustment`（方向 / 触发指标 / 完成率 / 时间 / 理由）。从未被调整过的计划是
   `latest_adjustment: null`，与「方向 keep」的真实调整可区分，也不伪造一条调整。
5. **打卡分区与用户自己的统计接口同源**：`streak_days` / `total_checkins` 直接取
   `WorkoutService.get_stats()`，序列只查窗口内的记录，因此详情页的连续天数与
   `GET /api/workout/{user_id}/stats` 恒等（测试对两个端点逐字段比对）。窗口定义为**含今天在内的
   90 个自然日**（`[today-89, today]`），窗口外的记录既不进序列也不进完成率分布；「今天」取与
   服务端统计接口同一个 `date.today()`，不用 UTC 瞬时日期，避免运营凌晨查看时窗口边界与用户看到
   的连续天数差一天。完成率分布固定三档：0-49 / 50-79 / 80-100。轨迹与其余时间字段仍是带时区的
   UTC 瞬时值。
6. **体重分区**：同一 90 天窗口内的序列（日期 + kg）；`record_count`、`latest_weight`、
   `last_recorded_date` 都只算窗口内；`records_per_week = 窗口内条数 / (90/7)`，保留两位小数。
   窗口外的记录不参与任何体重指标，对久未记录的用户该分区如实为空（而不是拿一条几个月前的
   记录冒充「最近体重」）。
7. **行为轨迹的派生规则**：事件类型固定十种（注册、首次 / 最近体型分析、首次生成计划、最近一次
   计划调整、首次 / 最近打卡、首次 / 最近体重记录、最近一次对话），全部由既有记录的 `created_at`
   派生，不引入埋点、不伪造阶段：某个数据源从未发生就不产生事件；只有一个记录时只产出「首次…」
   一条（同一条记录不可能同时是首次与最近），因此「首次 / 最近」不会变成两条重复事件。打卡事件
   的时间用记录写入时间，「训练日期」写在摘要/文案里。排序按时间倒序，同一时刻按固定枚举顺序
   兜底，保证翻页结果稳定。
8. **分页只作用于轨迹**：`page`（≥1）/ `page_size`（默认 20、上限 100，越界 422，与列表一致）
   只影响 `timeline`，其余分区一次返回。轨迹 `total` 是固定事件集合的条数（最多 10 条），
   页码越界返回空 `items` 与正确的 `total`；轨迹自身的 `page` / `page_size` 与请求一致。
9. **脱敏与用量口径**：`profile` 复用列表的掩码（openid 前 6 后 4、长度 ≤10 整段打码；邮箱保留
   首字符 + 完整域名），API Key 只给 `has_api_key` 与 `llm_provider`；`usage` 给对话消息计数
   （按 role 分组）、最近消息时间与 Key 状态，不含任何消息内容；响应里不出现密码哈希、加密 Key、
   原始 openid 或原始邮箱（测试对响应全文断言）。当前模型没有「会话」表，所以对话量按消息条数
   统计，不凭空造 conversation 维度。
10. **没有迁移**：轨迹与各分区全部由既有表派生，本工单不新增表、不改表结构；确实需要 schema
    变更时再排 0009（排在 0008 之后）。
11. **AC5 的「与统计接口一致」落在可比字段上**：用户自己的 `/stats` 只暴露「连续天数、累计
    打卡、最近 5 条」，没有 90 天序列，因此详情与本接口对齐的是 `streak_days` / `total_checkins`；
    近 90 天序列本身按窗口自证（条数 = 窗口内记录数，窗口外记录不进序列、不进完成率分布），
    不为对齐而给 `/stats` 新增窗口参数（那属于统计口径变更，另排）。「今天」同样走共享本地日期
    工具，避免凌晨时详情与用户统计的窗口边界差一天。
