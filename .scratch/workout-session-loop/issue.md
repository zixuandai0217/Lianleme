# Issue: 今日训练过程页与会话闭环，以及打卡后的反馈闭环

## Problem Statement

今天用户在「练了么」里能做的训练动作只有一个：**打卡**。首页会展示今天的动作清单（动作名、组数、次数、建议重量、组间休息），用户练完在弹窗里填「完成组数 / 时长 / 难度自评」提交，系统记一条打卡记录并让 AdjustGraph 异步调一次计划。除此之外没有别的。

这就意味着训练过程本身完全没有被承载：没有「开始训练」这个动作，没有当前动作、当前组数、已完成组数、整体进度，也没有「下一个该练什么」。用户在健身房里的真实流程是「做一个动作 → 做几组 → 看下一步」，而现在他必须反复回到静态清单页自己数；中途切走页面、杀进程、换设备，进度无从恢复，只能凭记忆填一个大概的完成组数。首页的「AI 陪练」按钮也只是跳到对话页，训练上下文（当前动作、已完成组数）并不会自动带过去。

打卡之后同样没有闭环。提交成功后弹窗里只有一句 LLM 生成的鼓励语（而且这句反馈只存在于当次响应里，刷新即消失，虽然存进了记录但前端再没展示过）。用户看不到本次完成率和上一次相比是进步还是掉队，看不到针对今天这份强度的恢复建议，更看不到「这次打卡到底有没有改变我下周的计划、往哪个方向改、为什么」。实际上计划往往确实被改了：打卡后会触发 AdjustGraph，按完成率走「加量 / 减量 / 保持」分支并改写当前周计划——但调整类型和理由在 Graph 出口就被丢弃了，只有被改写后的计划 JSON 被写回，用户和运营都无法追溯「我的计划为什么变了」。CONTEXT.md 里 WorkoutGraph（训练全流程编排）仍然是「待实现」，本次不做 Graph 化改造，但用户侧的价值缺口必须补上。

权限与统计侧已经有基础：打卡与统计接口都做了「登录用户 == 目标用户」的越权校验，统计已能给出连续打卡天数、总次数、本月次数与月均完成率、最近 5 条记录，月历数据接口也已存在（但前端尚未使用）。这些是本次可以直接复用的地基，不需要重做。

## Solution

把「今日训练」从一个静态清单升级为一个可以推进、可以中断恢复的**训练会话**，并把打卡变成会话的收尾动作，同时把打卡结果做成一份**可读、可对比、可追溯**的反馈报告。

用户侧体验是：从首页或训练计划页点「开始训练」进入今日训练过程页；页面顶部是整体进度（已练组数 / 计划总组数、已练动作 / 总动作、已用时长），中间高亮**当前动作**（组数、次数、建议重量、要领）并给出「第 2/4 组」这样的组内进度和「下一组 / 下一个动作」的提示，底部是一个大的「完成一组」按钮和「跳过这个动作」入口；每完成一组自动进入休息倒计时（用该动作自己的组间休息秒数），倒计时结束提示回到训练。中途退出再进来会接着上次的进度继续，不会丢。动作不熟可以一键把当前上下文带去问 AI 陪练。

练完点「结束并打卡」，系统基于会话真实明细计算完成率（而不是让用户自己填数字），弹出**训练反馈报告**：本次完成率与完成组数/时长摘要、与上一次的对比（差值、方向、连续打卡天数、近 7 天平均）、结构化的恢复建议（下次训练强度建议 + 补水/睡眠/拉伸等要点，风格遵循 West Coast Slang 但以中文短句为主），以及最关键的一块——**计划影响说明**：这次打卡有没有影响下周计划，是加量、减量还是保持不变，理由是什么，下周该注意什么；如果 AdjustGraph 因为命中人工确认条件（如伤病风险高）而暂停，就明确告诉用户「计划调整在等你确认风险处理方式之后才会生效」。

## User Stories

1. 作为正在训练的普通用户，我想要从今日清单直接点「开始训练」进入一个专门的过程页，以便不用在计划页里来回滚动找下一个动作。
2. 作为正在训练的用户，我想要在过程页看到当前动作的组数、次数、建议重量与要领，以便不用回翻计划就能执行。
3. 作为正在训练的用户，我想要看到「第 2/4 组」这样的组内进度，以便清楚还剩几组。
4. 作为正在训练的用户，我想要点一次「完成一组」就记录该组并自动进入组间休息倒计时，以便不用自己数秒。
5. 作为正在训练的用户，我想要在整体进度条上看到已练组数 / 计划总组数与已练动作 / 总动作，以便判断这次还要多久。
6. 作为正在训练的用户，我想要在一个动作做完后立刻看到「下一个动作」和它的要领，以便训练不中断。
7. 作为正在训练的用户，我想要跳过某个动作（器械被占、太累、不会做）并选择一个原因，以便打卡完成率仍然反映真实情况。
8. 作为正在训练的用户，我想要中途退出后再次进入时接着上次的进度继续，以便被打断也不用重来。
9. 作为在健身房单手操作手机的用户，我想要过程页的主要操作都是大按钮并固定在底部，以便单手握持时也能点准。
10. 作为不确定动作要领的用户，我想要在过程页一键把「当前动作 + 已完成组数」带进 AI 陪练对话，以便立刻得到指导。
11. 作为刚完成训练的用户，我想要在打卡后看到本次完成率、完成组数、时长与难度自评的摘要，以便确认这次训练被正确记录。
12. 作为刚完成训练的用户，我想要看到本次完成率与上一次的对比（含差值与方向），以便知道自己在进步还是掉队。
13. 作为刚完成训练的用户，我想要看到结构化的恢复建议（下次训练强度 + 恢复要点），以便安排接下来的休息和饮食。
14. 作为刚完成训练的用户，我想要明确知道这次打卡是否影响下周计划、影响方向和理由，以便不再把计划变化当成黑箱。
15. 作为计划被临时挂起的用户，我想要看到「调整在等你确认风险处理方式之后才会生效」的说明，以便理解为什么计划暂时没变。
16. 作为连续训练的用户，我想要同一天重复进入会话或重复打卡时不会产生第二条打卡记录，以便统计数据不被污染。
17. 作为每周有固定休息日的用户，我想要在休息日进入时看到「今天是恢复日」的轻量活动建议而不是空白训练页，以便不会以为功能坏了。
18. 作为还没有训练计划的新用户，我想要被引导先去完成体型分析并生成计划，以便不会卡在一个没有内容的训练页。

## Implementation Decisions

**会话是独立实体，不复用打卡记录。** 新增「训练会话」聚合：归属用户与当周计划、会话日期（按用户本地日界，默认 Asia/Shanghai）、状态、开始与结束时间、最后活动时间、当前动作指针与当前组指针、每个动作的完成明细（动作名、计划组数/次数、已完成组数、是否跳过、跳过原因）、累计时长。选择独立实体而不是给打卡记录加状态字段，是因为会话需要「进行中」这个可恢复的中间态，而打卡记录在语义上代表「已完成的训练事实」，混在一起会让统计口径变复杂。会话与当天的打卡记录一对一（同一用户同一本地日期只有一条会话）。

**会话状态机**（以下为设计决策，非代码片段）：

```
not_started --开始训练--> in_progress
in_progress --结束并打卡--> completed
in_progress --超过 12 小时无活动/用户主动放弃--> abandoned
in_progress --再次进入--> in_progress（恢复，不新建会话）
completed / abandoned --同一天再次进入--> 只读回看，不再产生新的打卡
```

会话日期以开始当天的本地日界为准，跨零点继续训练仍然归属开始日；第二天进入会开新会话。

**组级推进必须幂等。** 完成一组是「(会话, 动作序号, 组序号)」的集合式操作：重复提交同一组只记一次，且不接受倒退（已完成组数不回退）。跳过动作把该动作标记为 skipped，保留在明细里但不计入完成组数。指针推进规则由服务端计算后返回，前端不自行推算进度，避免两端漂移。

**打卡契约升级为「以会话为准」。** 打卡请求从「客户端自报 total_sets / completed_sets」升级为「会话标识 + 可选覆盖项（时长、难度自评）」，完成率与各动作完成情况由服务端根据会话明细计算；无会话的旧提交路径保留但必须显式标记为手工填报（source=manual），便于以后区分数据质量。打卡响应不再是「记录 + 一句文本」，而是结构化的反馈报告。

**反馈报告的形状**（设计决策，字段语义固定，实现可增字段）：

```
completion:  { rate, completed_sets, total_sets, duration_minutes, difficulty_rating }
comparison:  { previous_rate | null, delta_points | null, direction: up|down|flat|first_time,
               streak_days, avg_rate_7d | null }
recovery:    { next_intensity: reduce|hold|increase, tips: [string], generated_by: llm|fallback }
plan_impact: { job_id: string | null,
               status: not_created | evaluating | pending_choice | applied | expired_no_choice | failed,
               applied: bool, direction: increase|decrease|keep|null,
               reason: string, next_week_suggestion: string }
```

`comparison.previous_rate` 取同一用户上一条打卡记录的完成率（不是上一条会话），不存在时整段退化为首次训练形态，不允许出现「比上次提升 100%」这类无意义文案。

**`plan_impact` 是「调整作业」状态的投影，本特征不重写 AdjustGraph，也不拥有评估过程。** 打卡后的计划调整是一次**持久作业**：执行、租约与失败重试由任务持久化 spec 定义的 DB 驱动执行器统一负责，作业的状态与结果语义（`evaluating | pending_choice | applied | expired_no_choice | failed`、五维小结、合并分、决策方向、前后差异）由计划自适应 spec 定义。会话服务在这里**只做两件事**：打卡时投递一条调整作业（或在节流窗口内复用同一条），以及读取该作业的当前对外结果并投影成 `plan_impact`——`direction` 来自作业的决策方向，`reason` 来自作业的对外说明，`applied` 由作业是否已落地决定，`next_week_suggestion` 是给用户看的一句话。若作业停在 `pending_choice`（命中 ADR-0004 的人工确认条件：伤病风险高、连续大幅调整、目标冲突），则 `applied=false`、`status=pending_choice`，文案为「在等你确认风险处理方式」。**5 路并行分析器、HITL 流程、Graph 内部节点与作业执行器都不在本 spec 范围内**，这里只消费它们的可查询语义；本 spec 不新增第二个调整入口，也不自己起协程跑评估。

**调整结论必须落地可查。** 打卡记录保存本次的完成率、对比快照，以及调整作业的标识与**提交时的状态快照**；最终结论以作业详情为准，不复制一份会过期的结论副本。这样反馈报告在刷新后仍可复原，也满足运营侧「解释计划为什么变了」的追溯需求；反馈不得只活在一次 HTTP 响应里。

**投递即返回，绝不等待评估。** 打卡请求只做两件事：写打卡记录、投递（或复用节流窗口内的）一条调整作业，然后**立即**返回；响应里带作业标识与该时刻的状态，不等待评估完成，也不因评估失败而回滚打卡（打卡的成功与调整的成败是两件独立的事实）。作业投递本身失败时打卡仍然成功，`plan_impact.status=not_created` 并记录原因供排障。反馈卡片的语义按状态分档：`evaluating` → 「本次评估还在进行，稍后可在计划页看到结论」；`pending_choice` → 「在等你确认风险处理方式」；`applied` → 展示方向、理由与下周建议；`expired_no_choice` / `failed` → 明确说明本次未调整计划及原因。**前端不为等这个结论建立轮询循环**：只在用户重新进入反馈详情或计划页时读取一次最新状态，避免为了一个可能分钟级完成的评估把页面绑在轮询上。

**权限。** 所有会话与反馈接口只允许本人访问：会话归属用户必须等于登录用户，越权一律 403；管理员不能代用户跑会话或代打卡。训练会话只暴露给本人，不在管理端开放写入。

**前端视图判定放在纯函数里。** 过程页需要的派生信息全部由一个纯函数从「会话快照 + 今日动作清单」算出：当前动作、当前组、已练组数、总组数、进度百分比、下一个未完成动作（跳过与已完成的都要排除）、是否可打卡、休息剩余秒数、结束提示（全部动作完成时为「收尾拉伸并打卡」）。「下一次该练什么」的判定逻辑必须可单独单测，不藏在组件里。休息倒计时由前端计时并在每次 tick 用剩余秒数派生，服务端不记录计时器状态。

**与 AI 陪练的联动只传上下文。** 过程页把「当前动作、已完成组数 / 计划组数、今日重点」作为对话上下文传给 CoachGraph，不改变 CoachGraph 的持久化与流式行为，也不新增教练状态机。

**文案风格。** 反馈报告与过程页提示遵循 West Coast Slang 的教练口吻（ADR-0006），但必须中文可读、短句、每条建议可执行；不得使用攻击性措辞。LLM 不可用时用规则兜底文案（按完成率与难度自评分档），并在 `generated_by` 标注 `fallback`，保证没有 API Key 的用户也能看到完整反馈。

### 落地修订（工单 07：今日三态）

- **`status` 是今日接口的唯一判定入口**，取值 `training_day` / `rest_day` / `no_plan`（稳定枚举，前端仅凭它分叉）。旧字段（`is_rest_day`、`day`、`focus`、`exercises`、`estimated_duration`）全部保留；训练日额外返回 `exercise_count` / `total_sets` / `plan_id`，动作数量与总组数由服务端一次算好，前端不再自己累加（AC1）。
- **`is_rest_day` 语义收紧**：只有「有计划且当天是休息日」才为真，无计划一律为假。旧实现把「无计划」也返回成休息日形态，正是首页把首用用户显示成「今天留给恢复」的根因（AC4 的「语义不再混淆」）。
- **休息日文案沿用既有 `今日休息，好好恢复`**：前端空态与历史文案都依赖该句，改文案属于产品决策而非本次契约变更；无计划态**不返回 `message`**，避免任何调用方把无计划误读成休息日。
- **有计划但当周缺今天条目按休息日降级**：这类退化数据既不能渲染成空训练日（会话页无从开始），也不能算「无计划」（会诱导用户重建并归档现有计划），因此归休息日并保留 `plan_id`。
- **前端判定抽成纯函数** `resolveTodayState`（`status` 优先，缺 `status` 的旧响应按旧字段推断）；「拿不到响应」与「无计划」是两种态——网络失败不能渲染成「去生成计划」，否则会诱导用户归档现有计划。
- **三态各有独立、用户可见的文案**：训练日动作清单 + 打卡入口、休息日恢复建议、无计划「去生成本周计划」，由路由层与 jsdom 页面测试共同锁定差异（AC5）。


### 落地修订（工单 22 / 23：训练会话与过程页）

- **会话是独立聚合，动作明细存 JSONB**：`workout_sessions` 一用户一本地日期一条（唯一键），明细按「动作序号 + 组序号」定位并随会话整体读写，不做行级更新；**当前动作 / 当前组不落库**，由明细派生，避免指针与明细两套真相漂移。
- **对外视图全部由服务端算好**：`current_exercise`、`next_exercise`、`target_set_number`（「第 2/4 组」的 N）、`progress`、`finished`、`can_checkin` 都在响应里；前端只渲染，不做本地推算，因此刷新/换设备看到的是同一份状态。
- **完成一组是集合式幂等操作**：`set_index < completed_sets` 直接返回成功且不改变任何状态；`set_index > completed_sets` 视为乱序提交返回 422，杜绝静默跳过中间组。JSONB 是可变对象，更新前深拷贝再整体赋回，否则 SQLAlchemy 不认为列变更、明细不会落库（实现坑，已写进注释）。
- **跳过必须带原因且不污染完成率**：`SkipExerciseRequest.reason` 必填、且**去空白后不能为空**（缺失或纯空白都 422），已完成的动作拒绝跳过；跳过动作保留在明细里，`skipped=true` + `skip_reason`，完成组数不变，完成率仍是「已完成组数 / 计划总组数」。
- **开始训练的空态用稳定错误码**：无计划 → 409 `no_plan`、休息日 → 409 `rest_day`，且**不创建空会话**；同日重复「开始训练」返回同一个会话（唯一键 + 并发冲突回退读取）。`GET /sessions/current` 没有会话时返回 404 `no_session`。
- **12 小时无活动在读取时收敛为 abandoned**：状态机里的超时分支不需要后台定时器，`GET current` 会按 `last_activity_at` 惰性收敛；abandoned 会话是只读回看（`can_checkin=false`），不会产生新会话或新打卡。
- **跨零点归属开始日，且恢复入口能找到它**：`session_date` 在开始时固定；`GET /sessions/current` 先找**最近一条进行中的会话（不限当天）**，因此 23:10 开始、00:20 继续的训练仍返回原会话与原日期，再次「开始训练」也恢复同一条；只有超过 12 小时无活动才收敛为 abandoned、由当天新会话接替。
- **前端页面与入口**：新增 `/session` 页（当前动作、组内进度、整体进度、按动作 `rest_seconds` 的休息倒计时、跳过原因弹窗、收尾打卡入口；会话非进行中时只读展示、不再显示推进按钮）；展示判定与倒计时格式化抽成纯函数模块（见「相关文件」），`today` 空态复用 07 的三态判定，因此休息日与无计划文案不同且都不显示「开始训练」。首页今日卡片新增「开始训练」入口；会话页的「收尾并打卡」跳回首页并带 `?checkin=1`，首页由 URL 初始化打卡弹窗（打开后清掉参数），该链路有 jsdom 用例锁定。
- **迁移**：新增 `workout_sessions`（revision 0008），ORM 为唯一事实源、迁移逐列手写对齐、downgrade 可回滚。

## Testing Decisions

好测试只断言**外部可见行为**：HTTP 请求序列得到的响应形状与数值、页面渲染出的可见文本与可交互状态。不断言内部状态、不 mock 到函数调用层面、不对整页做快照。

**后端最高 seam：FastAPI 路由层**，用 httpx ASGITransport + `dependency_overrides` 覆盖数据库会话，用 JWT 构造不同身份的 token。选它作为最高 seam 的理由：会话推进的本质就是「一串 HTTP 请求 → 可观察的响应」，状态机、幂等性、完成率计算、权限与反馈形状全部能从响应验证；再往下测 service 或 ORM 只会把测试绑死在当前的表结构与指针实现上，而这些恰恰是本次要自由设计的部分。模型层不提供比路由层更高的价值，因此不需要更低的 seam。prior art：鉴权守卫路由测试（隔离 SQLite fixture、从用户 ID 构造 JWT 的 helper、含越权与管理员用例，位置见「相关文件」）。

需要在路由层覆盖的外部行为至少包括：开始会话返回 `in_progress` 与第一个动作；连续完成两组后进度为 2、重复提交同一组进度不变；跳过动作后完成率不被污染且明细里有跳过原因；同一天重复「开始训练」不新建会话；打卡后反馈报告包含 completion/comparison/recovery/plan_impact 四段且 `plan_impact.status` 与 `direction` 落在枚举内；上一次记录不存在时 comparison 为首次训练形态；完成率为 0（全部跳过）与 100% 两种极端；休息日与无计划两种空态；跨用户访问返回 403，未登录 401。

打卡与调整作业的分工必须由外部行为锁定：评估作业尚未完成时打卡**仍然返回成功**，且响应里带作业标识与 `status=evaluating`（断言「不等待」这条契约，而不是断言耗时）；作业随后失败时打卡记录与反馈仍完好、`status=failed` 可读；作业停在 `pending_choice` 时反馈文案指向「等你确认」而不是「已调整」；投递失败时打卡成功且 `status=not_created`。测试里用可控的作业替身推进状态（手动把作业置为 applied / failed / pending_choice），不测执行器的认领、租约与重试——那属于任务持久化 spec 的 seam。

**LLM seam 用假客户端。** 在依赖覆盖层把 LLM 工厂替换为固定返回的假实现，分别验证「有 LLM 时结构正确（含 West Coast Slang 文案）」与「LLM 抛错时走 `generated_by=fallback` 兜底」两条路径。不测 Prompt 文本，不测 Graph 内部节点。

**前端最高 seam：纯 TS 判定函数**（会话视图派生 + 下一次动作选择 + 对比文案分档），prior art：体型分析旅程的纯函数与其单测（把「旅程阶段 / 主次动作」抽成纯函数，测试只喂输入看输出，位置见「相关文件」）。它高于组件、低于页面，足以覆盖全部「下一步是什么」的产品判断，因此不需要为这些判断写更低层的 hook 测试。

**页面级测试用 vitest + jsdom**，MemoryRouter + mocked `useAuth` + mocked API 模块挂载渲染，断言用户能看见的东西：进度文本、当前动作名、「完成一组」按钮可见、点击后进度变化与倒计时出现、打卡后反馈卡片四个区块出现、休息日与无计划空态的文案。prior art：API Key 网关的 jsdom 页面测试（MemoryRouter + mocked auth，断言路由与查询串）与陪练页的页面级集成测试（位置见「相关文件」）。不断言 className、不测第三方 UI 组件内部实现。

## Further Notes

**读代码时确认的现状问题（供实现者避坑）：**

1. 打卡后触发计划调整的异步调用是「响应返回后再无回音」的形态：没有保存任务引用、异常被完全吞掉、且它在数据库事务提交之前就发起了另一个独立会话。结果是调整可能失败而用户毫无感知，也无法回答「这次打卡到底改了没改计划」——这正是本特征要求「打卡只投递持久作业、结论必须可查」的原因，而作业本身的执行与重试交给任务持久化 spec 的执行器。
2. AdjustGraph 的 `run()` 只返回改写后的计划 JSON，`adjustment_type` 与 `reason` 在出口被丢弃，且计划写回时没有记录任何变更历史。因此「是否影响下周计划」当前**无法从数据回答**：本特征需要的是作业级可查询结果（状态 + 决策方向 + 理由 + 前后差异），这部分由计划自适应 spec 定义、由执行器落地；本 spec 只读取它并投影成 `plan_impact`，不自行新增评估契约。
3. 今日训练接口把「用户还没有计划」和「今天是休息日」混成同一个响应（都返回休息日形态），首页只能显示「今天留给恢复」。过程页若要区分「休息日轻量活动」与「去生成计划」两种空态，需要先让接口能区分这两个语义。
4. 月历统计接口已经存在但前端从未调用，统计卡片只用了连续天数/总数/本月数/月均完成率；本次的对比与恢复建议可以复用这些既有统计口径，不另建一套。

**方向性决策记录：**

- 会话明细以「动作序号 + 组序号」定位而不是动作名，同名动作重复出现时不会串组。
- 反馈报告不做成「AI 长文」，而是固定四段结构 + 短文案；LLM 只负责 recovery 与鼓励措辞，数值必须由服务端计算，保证可测与可复现。
- 时区问题当前没有用户时区字段，第一版统一按 Asia/Shanghai 计算本地日界，并把该假设写进接口文档；后续加时区字段时只需替换日界计算函数。
- 本次不引入新的调度/队列依赖，也不在本特征内引入任何定时器或轮询等待：「打卡后调整」改为投递一条持久作业，由任务持久化 spec 定义的 DB 驱动执行器消费；本特征对评估只做「投递」与「读取作业当前状态」两件事，作业的执行、租约、重试与超时收敛都在执行器与计划自适应 spec 的边界内。
- 上述分工要求打卡响应的语义显式包含「评估尚未完成」这一合法状态：`status=evaluating` 不是错误也不是中间态待重试，而是一个稳定可见的事实，前端据此展示「稍后可见」而不是转圈等待。

> **迁移约定**：本 spec 引入了新的持久实体（训练会话聚合与动作级完成明细），属于改表，必须遵守全组统一约定——见 `analysis-task-persistence` spec 的「迁移与数据模型落地约定」一节（ORM 为唯一事实源、迁移与模型手写对齐、按交付追加 revision、可回滚、方言判断只出现在兼容层）。本 spec 不另立迁移约定。

## 落地修订（工单 28）

打卡四段式反馈与作业投递的落地取舍：

1. **完成率以会话为准**：当天存在 `WorkoutSession` 时，完成组数/总组数从会话明细派生，
   客户端自报的 `completed_sets` 不改变结果；没有会话的历史客户端请求回落到请求值以保持
   兼容（这是显式的兼容分支，不是默认路径）。
2. **四段式契约**：`feedback = {completion, comparison, recovery, plan_impact}`，扁平旧字段
   （id / workout_date / completion_rate / duration_minutes / ai_feedback）保留。恢复建议
   永不为空：模型文案可用时 `source=model`，否则确定性兜底列表 `source=fallback`。
3. **对比段**：有上一条打卡时给出完成率差值（百分点，字段 `delta_percent`，并保留规格命名
   `delta_points` 同义字段）与方向；首次训练 `has_previous=false`、差值为空，绝不伪造
   「提升 100%」。
4. **计划影响是投影**：按打卡记录上的 `adjustment_job_id` 读作业当前状态，再按
   `job.adjustment_id` 读同一份调整结论；方向/理由/前后摘要与计划页解释卡同源（计划解释
   的 `latest_adjustment` 也补上同一作业快照里的 before/after 摘要）。打卡记录只保存作业
   标识与提交时刻状态快照，不复制理由文本。
5. **状态词表**：`not_dispatched / evaluating / pending_choice / expired_no_choice / applied /
   failed`。超时兜底（工单 27）确实落地了计划，但与用户选择区分：报 `expired_no_choice` 并
   说明「5 分钟未确认，已按推荐方案自动应用」。`pending_choice` 明确指向「等你确认风险处理
   方式后才会生效」。
6. **不阻塞、不反噬**：作业投递或评估失败仍返回 200，只是计划影响状态不同；HTTP 不等待评估，
   前端不为等结论轮询。
7. **同日幂等**：同一天重复打卡返回已有记录与同一作业，不新建记录、不重复投递；迁移 0013
   追加记录侧引用列，并建立 `(user_id, workout_date)` 唯一索引兜底并发（迁移前先清理历史
   重复，保留最新一条）。
8. **作业与打卡原子化**：作业创建放在 savepoint 里，成功则与打卡记录同一次提交，失败只回滚
   作业；不会出现「作业已提交但打卡记录没有指向它」的半截事实。
