# 28 — 打卡投递作业 + 四段式反馈

**What to build:** 用户结束会话后打卡，拿到的不再是一句鼓励语，而是一份四段式反馈：本次完成情况、与上一次的对比、恢复建议、以及这次打卡对下周计划的影响。完成率由服务端按会话明细计算，客户端自报数字不再生效。打卡只负责投递一条调整作业并立即返回，评估慢或失败都不影响打卡成功；未完成时明确告诉用户「稍后可见」，前端不为等结论而轮询。

**计划影响这一段是「投影」，不是新存储。** 它由两样既有事实拼成：调整作业的当前状态与标识（来自 26 的可查询调整作业），以及调整结论本身（加量 / 减量 / 保持、理由、前后摘要——这些已经由 20 落盘为计划解释字段）。打卡这一步只在打卡记录上保存作业标识与提交时刻的状态快照作为引用，**不新建第二份调整说明存储**，因此计划页解释卡与打卡反馈永远显示同一份结论：改一处，两处同时变。

**Blocked by:** 11 DB 驱动执行器；20 计划解释字段落库与读取；22 训练会话实体 + 推进 / 恢复接口；26 可查询调整作业 + pending / detail

**Status:** ready-for-agent

- [ ] AC1 打卡返回 200，响应含四段字段（本次完成情况、对比、恢复建议、计划影响）；其中完成率由服务端按会话明细计算（客户端请求里自报的完成组数不改变结果），恢复建议的要点列表非空且标注来源为模型生成或兜底文案（模型不可用时不得为空、不得 500）。
- [ ] AC2 打卡响应不等待评估，且失败不反噬打卡：评估作业尚未完成时仍返回 200，响应带作业标识、计划影响状态为「评估中」，且评估未被同步调用（用可控作业替身断言）；作业评估失败、或作业投递本身失败时同样返回 200 且打卡记录存在，计划影响状态分别为「失败」与「未投递」，其余三段完整可读。
- [ ] AC3 单一来源边界锁死：同一调整在计划页解释卡与打卡反馈里显示的方向、理由、前后摘要逐字相同；直接改动该调整结论的唯一存储后，两处响应同时变化（不需要第二次写入）；打卡记录侧只存在作业标识与状态快照，不存在独立的调整理由字段被写入。
- [ ] AC4 作业已落地时计划影响为「已应用」，含调整方向（加量 / 减量 / 保持）与可读理由；作业停在 Human-in-the-loop 待确认时标记为未应用，文案指向「等你确认风险处理方式后才会生效」。
- [ ] AC5 对比段：存在上一条打卡时给出完成率差值与方向；不存在时退化为首次训练形态（对比值为空，不出现「比上次提升 100%」之类伪对比）。
- [ ] AC6 同一天重复打卡返回明确结果（同一结果或稳定冲突语义），数据库里当天只有一条打卡记录，且不会重复投递第二条调整作业。
