# Issue: 运行与观测基线（请求关联、结构化日志、依赖健康检查）

## Problem Statement

系统出问题时，唯一的信号是用户说「坏了」。用户能在界面上看到一句「服务器内部错误，请稍后重试」，但那句话背后什么都没留下：全局兜底异常处理器把异常转成友好文案后就结束了，既不记录堆栈，也不记录是哪次请求、哪个用户、哪个接口。等到有人去翻日志，能翻到的只有零散的几行异常日志，彼此之间没有共同标识，无法拼出一条请求的完整轨迹。

更麻烦的是「串不起来」。同一时刻可能有多个用户在跑体型分析、等多个流式回复，日志里出现一条失败，没人能说出它属于哪次前端操作。后台任务的问题同样：任务日志里只有一个任务号，没有触发它的请求、没有用户、没有耗时、没有重试次数，于是「用户说分析一直转圈」这种反馈根本无法被证实或推翻。

LLM 调用是这条链路里最需要被看见的一段，却几乎不可观测。供应商鉴权失败、限流、超时、返回内容无法解析，对外都收敛成同一句「AI 服务暂时不可用」；对内没有区分错误类别，于是无法判断是全供应商故障、某个用户 Key 配错，还是一个模型偶发输出格式异常。同时又必须小心：日志里绝不能出现用户的 API Key、图片内容或对话原文。

健康检查也只是形式主义。它永远返回「ok」，即使数据库连不上、对象存储挂掉；编排系统据此认为实例健康，流量继续打进来，负载均衡也不会摘除。值班的人想知道「现在到底是哪个依赖坏了」，只能靠猜。

## Solution

先建立一条「请求可以被打断、日志能与请求对上」的最小观测基线，而不是一次上齐指标与追踪。

请求进来时生成或继承一个请求标识，写进上下文并一路带到响应头、日志、后台任务；用户报错时只要报出这个编号，就能把该请求相关的全部日志取出来。日志统一成单行结构化格式（机器可索引），字段名固定且文档化：谁、哪个接口、什么结果、耗时多少、错误码是什么。

错误分成两层记录：可预期的业务错误记一条简短警告（不堆栈、不刷屏）；未知异常记错误并带完整堆栈；对外仍只返回稳定错误码加安全文案，内部信息不越过边界。LLM 与对象存储这类外部依赖的失败有专属事件与错误类别，且强制脱敏——绝不记录密钥、图片内容与对话原文。

健康检查拆成两级：存活检查只回答「进程还在吗」，永远快速返回、不查外部依赖；就绪检查逐项报告数据库、对象存储（以及可选的 Redis）是否可用，任何必需依赖不可用时返回 503，让编排系统把流量摘走而不是继续打。

## User Stories

1. 作为值班开发者，我想要每次前端报错都能凭响应头里的请求编号找到该请求的全部后端日志，以便不用靠时间戳猜。
2. 作为值班开发者，我想要未预期的异常一定留下堆栈与请求上下文，以便不用复现就能定位。
3. 作为值班开发者，我想要日志是单行结构化格式，以便日志系统能按字段索引与聚合。
4. 作为值班开发者，我想要每条请求日志带接口、方法、状态码与耗时，以便找出慢接口与异常比例。
5. 作为值班开发者，我想要后台任务日志带任务标识与用户，并继承触发它的请求编号，以便把「请求 → 任务 → 结果」串成一条线。
6. 作为值班开发者，我想要 LLM 调用失败按错误类别记日志（鉴权、限流、超时、输出不可解析、内部错误），以便判断是系统性故障还是个别用户配置问题。
7. 作为值班开发者，我想要对象存储操作失败有专属事件与错误类别，以便区分「图片不合法」和「存储不可用」。
8. 作为安全负责人，我想要日志里绝不出现 API Key、密码、令牌、图片内容与对话原文，以便排查能力不以泄漏用户数据为代价。
9. 作为运维，我想要存活检查只在进程真的不健康时失败，以便依赖抖动不会导致实例被误重启。
10. 作为运维，我想要就绪检查逐项报告依赖状态，以便负载均衡能把流量摘到健康实例。
11. 作为运维，我想要健康检查返回版本与启动时间，以便确认滚动发布真的生效、实例确实是新版本。
12. 作为开发者，我想要错误的对外文案与内部错误码彻底分离，以便既不泄漏实现细节又能被前端精确处理。
13. 作为开发者，我想要日志字段命名稳定且有明确约定，以便新增日志不会破坏既有查询与告警。
14. 作为开发者，我想要流式与长连接请求在结束或中断时也有结束日志，以便流式中途断开的故障不被吞掉。
15. 作为开发者，我想要观测能力本身有回归测试（断言响应头、状态码与字段存在性），以便重构不会悄悄丢掉可观测性。

## Implementation Decisions

### 1. 日志格式与字段约定（本组 spec 中日志字段只在此处定义，其他 spec 引用本节）

单行结构化日志，一行一条事件，不带换行与多行堆栈拼接（堆栈作为字段值转义存放）。固定字段：

| 字段 | 说明 |
| --- | --- |
| timestamp | ISO 8601，UTC，带毫秒 |
| level | debug / info / warning / error |
| event | 稳定事件名，三段式点分：领域.动作.结果 |
| message | 人类可读短句，不参与检索 |
| request_id | 请求标识；后台任务继承触发请求的同值 |
| user_id | 已认证用户；未认证时为空，绝不写令牌 |
| route | 路由模板（不含路径参数真实值，避免把用户标识写进指标维度） |
| method | HTTP 方法 |
| status_code | 响应状态 |
| duration_ms | 请求或任务耗时 |
| error_code | 稳定错误枚举（复用分析任务 spec 定义的错误码，不在此重新定义） |
| error_class | 异常类型名（内部信息，只出现在服务端日志） |
| task_id | 后台任务标识 |
| dependency | 外部依赖名：数据库 / 对象存储 / LLM 供应商 |
| attempt | 任务尝试次数 |
| version | 应用版本 |
| stack | 仅错误级，完整堆栈文本 |
| model_purpose | LLM 模型用途：`chat` / `vision` / `voice`（工单 05 追加） |
| llm_mode | 本次调用凭据来源：`byok`（用户自带 Key）/ `system`（系统回退或内部任务）（工单 05 追加） |
| error_category | LLM 错误分类：`auth` / `rate_limit` / `timeout` / `network` / `output_parse` / `unknown`（工单 05 追加） |
| prompt_chars | 提示词字符数（非内容型元数据）（工单 05 追加） |
| image_size_bytes | 图片字节数（非内容型元数据；命名避开脱敏黑名单里的 `image_bytes` 内容字段）（工单 05 追加） |

禁止字段（任何级别都不得出现）：API Key 与其掩码、Authorization 头、密码与令牌、图片 base64 或图片字节、对话原文与提示词全文。允许记录图片字节数与内容类型这类非内容型元数据。实现一个统一脱敏环节，而不是靠每个调用点自觉。

日志级别语义：业务可预期失败（4xx）为 warning；未知异常（5xx）为 error 且必须带 stack；依赖失败为 warning 或 error（按是否影响用户请求判定）；正常状态流转为 info。

### 2. 请求标识与上下文传播

- 入口中间件读取请求头中的请求标识：格式合法则沿用，非法或缺失则生成新的不可猜测标识。
- 标识写入请求作用域的上下文，供本次请求内所有日志自动携带；无需逐处传参。
- 响应头回显该标识（含错误响应），并加入跨域允许暴露的响应头列表——否则浏览器端拿不到，前端无法在报错提示里带上它。
- 后台任务创建时把当前请求标识与用户写入任务记录，执行时重新注入上下文；任务重试时携带同一 request_id，但 attempt 递增。
- 明确边界：不做跨进程传播（不引入分布式追踪的 trace 语义），一个请求一个标识，任务侧通过任务标识关联。

### 3. 错误契约

- 对外统一错误形状：`detail` 内含稳定错误码与安全文案（沿用现有的「API Key 前置校验」那种形状，不新造第二套）。
- 未知异常对外固定为一条通用内部错误语义（现有文案可保留），内部必须落 error 日志带堆栈；绝不在响应体里返回异常类型、堆栈、SQL、供应商原文。
- 已知业务错误的错误码在路由处明确产生，不靠异常继承链推断。
- 全局异常处理器的职责从「只翻译」变成「翻译 + 记录」，且必须能在测试里被断言为「记录了一次 error」。

### 4. 请求日志

- 每个请求在完成时产生一条事件，包含方法、路由模板、状态码、耗时、请求标识、用户、错误码。
- 流式与长连接请求（SSE）：在流开始、正常结束、客户端中断、上游失败四种情况都有结束事件，其中中断与失败为 warning，且记录已发送字节数或块数以便判断是否已产生用户可见输出。
- 慢请求（超过阈值，量级：数秒）单独标记为慢事件，便于不依赖外部监控也能发现。

### 5. 后台任务观测

任务的生命周期节点各产生一条事件：创建、认领、成功、失败、回收、过期、清理。字段含任务标识、用户、尝试次数、耗时、错误码。失败必须带 error 级日志与堆栈（除可预期的业务失败外）。任务日志必须沿用第 1 节的字段名，不得自创同义字段（例如不要出现 `req_id` / `uid` 之类的别名）。

### 6. LLM 调用观测

- 每次调用失败产生一条 `llm` 领域事件，字段含供应商、模型用途（对话 / 多模态 / 语音）、错误类别（鉴权失败、限流、超时、网络、输出解析失败、未知）、耗时。
- 成功调用记录耗时与是否走了系统回退（BYOK 与系统回退要能在日志上区分开，否则无法评估回退成本）。
- 提示词全文、图片内容、用户对话原文一律不记录；可记录字符数与图片字节数。
- 输出解析失败（结构不合法、markdown 包裹、降级到兜底）单独成事件，因为它是「看起来成功但质量下降」的隐性故障。

### 7. 对象存储观测

写、读、签名、删除四个操作在失败时产生事件，字段含操作类型、依赖名、错误类别、字节数（若有）、内容类型（若有）。key 记录时可保留用户前缀但不得记录文件名原文。

### 8. 健康检查

- 存活检查：保持现有路径与语义，永远快速返回，不查任何外部依赖；返回应用版本与启动时间。
- 就绪检查：新增独立路径，逐项探测必需依赖（数据库执行最小查询、对象存储检查 bucket 存在、可选 Redis ping），每项给出可用性与耗时，聚合状态分为 正常 / 降级 / 不可用；必需依赖不可用时整体返回 503。
- 每个探测有独立的短超时（量级：一秒），任一探测超时不得拖慢整体响应；探测失败也要产生日志事件，但要限流，避免探针高频刷屏。
- 就绪检查响应形状（设计决策）：

```json
{
  "status": "ok | degraded | unavailable",
  "version": "0.1.0",
  "started_at": "2026-05-01T09:00:00Z",
  "uptime_seconds": 3600,
  "dependencies": [
    { "name": "database", "required": true, "status": "ok", "latency_ms": 3 },
    { "name": "object_storage", "required": true, "status": "fail", "latency_ms": 1002, "error_code": "timeout" },
    { "name": "redis", "required": false, "status": "ok", "latency_ms": 1 }
  ]
}
```

- 存活路径不得复用就绪探测；两者混用会让编排系统在依赖抖动时重启健康的进程。

### 9. 配置与运行形态

- 日志级别可配置，默认信息级。
- 日志输出格式：开发环境允许人类可读的文本格式便于本地阅读，非开发环境强制结构化单行格式；两者字段集合必须一致（文本格式只是同一字段的另一种渲染），避免本地与生产观测能力不一致。
- 不做日志采样（本期量级不需要），只对探测类重复失败做限流。
- 不新增第三方观测依赖：使用标准日志库 + 自定义格式化器即可满足单行结构化输出；引入重型框架会提高部署与测试成本。

### 10. 前端契约

- 前端在请求失败时从响应头读取请求标识，并在错误提示或错误上报里带上它（用户可见文案保持简短）。
- 错误文案继续从既有的「detail 里的 message」取，不因契约收紧而改变前端解析方式。

### 11. 落地修订（工单 04：就绪/存活探针）

- **探测实现**：数据库执行 `SELECT 1`；对象存储检查 bucket 是否存在，并按探测超时新建独立 `PoolManager`（禁用重试）——`asyncio` 的超时只能取消等待，取消不了阻塞 I/O，若复用默认连接池，反复探测会在依赖挂掉时堆积线程；Redis 为可选探测，未配置 URL 直接视为通过。
- **聚合口径**：必需依赖失败 → `unavailable` + 503；只有可选依赖失败 → `degraded` + 200（第 118 行「正常 / 降级 / 不可用」三态的具体落地）。
- **配置项**：`HEALTH_PROBE_TIMEOUT_SECONDS`（默认 1s，逐项独立）与 `HEALTH_PROBE_LOG_THROTTLE_SECONDS`（默认 30s，按依赖限流）。
- **事件**：`dependency.probe.failed`（warning，带 `dependency` / `error_code` / `duration_ms`）与 `dependency.probe.recovered`（info，一次失败窗口只报一条，让故障有可见终点）；两者都走统一结构化日志，自动带 `request_id`。
- **单一来源**：应用版本与启动时间在健康检查模块内各定义一次，存活与就绪共用；`/health` 不引用任何探测函数，依赖全挂时仍 200。
- **预期内 5xx 不按异常刷日志**：就绪检查在依赖不可用时返回 503 是探针的正常结论，该请求的完成事件降为 warning（与第 1 节「依赖失败按是否影响用户请求判定级别」一致），避免探针高频刷 error。
- **Redis 默认不探测**：`REDIS_URL` 有本地默认值，「有 URL」不等于「本部署用了 Redis」。只有显式 `REDIS_PROBE_ENABLED=true` 时才把它作为可选依赖参与聚合，否则无 Redis 的部署会永久 degraded 并按窗口刷失败日志。

### 12. 落地修订（工单 05：LLM 调用观测与脱敏）

- **字段追加**：`model_purpose` / `llm_mode` / `error_category` / `prompt_chars` / `image_size_bytes`（已并入第 1 节表格）。供应商沿用第 1 节既有的 `dependency` 字段（表里本就写明「LLM 供应商」），不新造 `provider` 别名。
- **事件**：`llm.call.completed` / `llm.call.failed` / `llm.output.degraded`；成功与失败事件都**不带 stack、不带 exc_info**——SDK 异常文本可能内嵌密钥、提示词或供应商回包。跨出 provider 边界时改抛 `LLMCallError`（只含分类标签），阻断上游 catch-all 把原文写进堆栈。
- **降级与成功分开**：JSON 外壳、代码围栏、解析失败、兜底文案各记一条 `llm.output.degraded`，`error_code` 用 `output_parse` / `markdown_wrapped` 区分，绝不混进成功调用的结果标记。这两个值**是输出质量分类，不复用任务错误码**（第 67 行的 `error_code` 约定针对请求级失败；调用失败事件本身不再写 `error_code`，分类只在 `error_category` 上）。
- **降级判定按消费者契约区分**：对话场景只要清洗后仍有可读正文就不算降级（外壳/围栏里取到正文属正常输出），只有结构被丢弃且没取到正文、或最终落到兜底文案时才记；结构化输出场景（体型分析、计划生成、计划调整）只要模型没按约定直出 JSON（被 markdown 包裹也算）就记 `markdown_wrapped`，解析失败记 `output_parse`。流式对话的判定发生在 Graph 侧（路由拿到的是清洗后文本，看不到结构），非流式对话复用同一判定，两条路径口径一致。
- **覆盖范围**：所有 LLM 调用点（coach 同步/流式、vision、计划生成、计划调整、打卡反馈、Qwen TTS）共用 `invoke` / `stream` / `voice_call` 一套包装；语音的 BYOK 与系统回退由路由解析凭据时一并确定后传入（运行时不猜来源），无凭据来源时如实记 `unknown`。

## Testing Decisions

### 好测试的标准

只断言对外可观测面：响应头是否带请求标识、标识是否被沿用/重新生成、状态码与响应体错误码、健康检查的聚合状态与逐项字段存在性、日志事件是否存在且含必需字段。不断言日志整段文本、不断言格式化器的内部结构、不断言日志行数（除「某事件必须出现」这类存在性断言）。测试应能在换成其他日志后端时不改断言。

### 最高 seam：FastAPI 路由层

用测试内应用客户端（ASGI 传输）发真实请求，断言：

- 响应头里有请求标识；传入合法标识时被沿用；传入非法标识时被替换。
- 未预期异常下响应体是统一错误形状且不含堆栈/异常类名，同时捕获到一条 error 级日志事件。
- 就绪检查在依赖被替换为失败时返回 503，且对应依赖项标记失败；全部健康时返回 200。
- 存活检查在依赖全部不可用时仍然返回成功（证明它不依赖外部）。
- SSE 路由在正常结束与上游失败时都产生结束事件。

日志断言通过测试捕获器（标准日志库的捕获机制或临时 handler）读取结构化字段，不解析终端输出。

为什么不需要更低层的 seam：观测是横切能力，唯一有意义的事实都出现在「请求-响应」与「日志事件」这两个边界上。中间件、格式化器、异常处理器这些都是可替换实现，为它们写单元测试会把实现钉死，而它们恰恰是最容易在后续重构中换掉的部分。健康检查的探测函数同理：断言路由输出即可，不必断言每个探测的内部调用。

前端 seam：纯 TypeScript 函数覆盖「从响应/错误对象里取请求标识并拼进提示」的映射，vitest 单测，不渲染页面。

### 被测模块

1. 请求上下文中间件（生成、沿用、回显、跨域暴露）
2. 全局异常处理器（统一形状 + 记录 error 事件）
3. 请求完成日志与慢请求标记
4. 后台任务生命周期事件
5. LLM 失败事件与脱敏（含系统回退标记）
6. 存活检查与就绪检查
7. 日志格式化器（一条：验证输出是一行且字段齐全，允许直接单测这一处，因为「单行」是外部契约）

### 必测行为清单

- 普通请求：响应头带请求标识；日志里有对应事件的 request_id、route、status_code、duration_ms。
- 客户端传入合法标识：沿用到响应头与日志。
- 客户端传入非法标识：被替换为合法新标识（不得原样回显）。
- 未预期异常：响应 500 + 统一错误形状 + 无堆栈泄漏；同时存在一条带 stack 的 error 事件。
- 4xx 业务错误：不产生堆栈型 error 事件（避免刷屏），但仍记录 warning 与错误码。
- 日志脱敏：构造一个含密钥与图片字串的调用路径，断言输出里不出现这些值。
- SSE 正常结束与上游失败：都有结束事件，失败事件为 warning 且带错误类别。
- 后台任务失败：事件带 task_id、user_id、attempt、error_code，且继承触发请求的 request_id。
- LLM 失败：事件带供应商、模型用途、错误类别；走系统回退的成功调用带明确的回退标记。
- 就绪检查：数据库正常 + 对象存储失败 → 503，逐项状态正确；全部正常 → 200。
- 存活检查：所有依赖被替换为失败仍返回成功且快速。
- 格式化器：一条事件序列化为单行，必需字段齐全，无换行。

### 显式不做

不写连接真实数据库/对象存储的健康检查测试（用替身）；不断言日志的具体措辞；不写采集后端（Loki/ELK）的集成测试。

## Out of Scope

- 分布式追踪（OpenTelemetry / trace-id 传播 / span）。
- 指标系统与导出（Prometheus 计数器、直方图）、仪表盘、告警规则与通知。
- 日志采集与存储后端的选择与部署（只保证输出形态可被采集）。
- APM、性能剖析、错误聚合平台（Sentry 等）接入。
- 前端错误上报 SDK 与埋点体系。
- 审计日志的合规要求（谁在何时做了什么的可追溯留存策略）。
- CI 与质量门（属于工程基线任务）；本 spec 只保证观测能力可被 pytest 断言。
- 任务状态机本身与错误码枚举的定义（见 `analysis-task-persistence`）。

## Further Notes

- 现状里最要紧的三处：全局异常处理器只翻译、不记录；应用从未配置日志输出格式，因此所有 logger 输出都是未格式化的默认文本；存活检查路径写死返回 ok，不查任何依赖。这三点决定了本 spec 的第一步是把「已存在的日志调用」纳入统一格式，而不是新增大量日志调用点。
- 日志里已经出现了一些非结构化写法（把任务号、用户号拼进消息文本）。改造时应把这些值提为字段，而不是继续拼字符串；否则字段化日志只覆盖新代码，检索仍然要正则。
- 请求标识的跨域暴露容易被忽略：不把该头加入允许暴露列表，浏览器端就读不到，前端的「请提供编号」就永远拿不到值。
- 就绪检查会引入周期性探测流量，务必加短超时与失败限流，否则一个挂掉的依赖会让日志被探针刷满。
- 版本与启动时间应来自单一来源（应用版本常量 + 启动时刻），不要在两处各写一份。
- 跨 spec 依赖：错误码枚举与任务事件语义见 `analysis-task-persistence`；对象存储操作的依赖名与失败类别见 `media-asset-storage` 的存储端口；本 spec 只负责字段与输出形态，不重新定义业务错误码。
