# 05 — LLM 调用日志与脱敏

**What to build:** 让「AI 不好用」这件事在日志里能被区分出原因。每次 LLM 调用失败都记一条事件，带供应商、模型用途（对话 / 多模态 / 语音）、错误类别（鉴权失败、限流、超时、网络、输出解析失败、未知）与耗时；成功的调用也记耗时，并标明这次走的是用户自带 Key（BYOK）还是系统回退——否则无法评估回退被用掉多少、成本落在谁身上。

「看起来成功但质量下降」的隐性故障单独成事件：输出无法解析、被 markdown 包裹后降级到兜底，这类情况现在和成功混在一起，是最难被发现的一类。同时这条链路是脱敏压力最大的地方：日志里绝不出现用户的 API Key（含掩码形式）、提示词全文、对话原文与图片内容，只保留字符数、图片字节数这类非内容型元数据。

**Blocked by:** 03 结构化日志与请求关联 ID

**Status:** ready-for-agent

- [ ] AC1：LLM 调用失败时产生一条事件，含供应商、模型用途、错误类别、耗时与请求标识；鉴权失败、限流、超时、网络失败、输出解析失败在事件里可区分。
- [ ] AC2：成功的 LLM 调用产生一条事件，含耗时与模式标记，使 BYOK 与系统回退可在日志上被区分开。
- [ ] AC3：输出无法解析或降级到兜底时单独产生一条事件，不与成功调用共用同一结果标记。
- [ ] AC4：构造一次携带 API Key、提示词全文、对话原文与图片内容的调用路径后，日志输出里不出现这些值（包括掩码形式），只出现字符数/字节数这类元数据。
- [ ] AC5：事件字段名沿用结构化日志约定，不出现同义别名（例如同一含义既叫 request_id 又叫 req_id、既叫 user_id 又叫 uid 的情况）。
