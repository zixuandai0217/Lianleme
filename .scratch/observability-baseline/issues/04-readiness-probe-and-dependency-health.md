# 04 — 就绪探针与依赖健康检查

**What to build:** 让编排系统知道「这个实例现在能不能接流量」。存活检查只回答进程还在不在，永远快速返回、不查任何外部依赖；就绪检查逐项探测必需依赖（数据库、对象存储，可选的 Redis），每项给出可用性与耗时，聚合状态分为正常、降级、不可用——必需依赖不可用时整体返回 503，让流量被摘走而不是继续打进一个坏实例。

探测要有限度：每项有独立的短超时（量级一秒），一个挂掉的依赖不能拖慢整个响应；探测失败会持续产生日志，因此必须限流，避免一个坏依赖把日志刷满。所有探测事件都带请求标识，值班的人能把它和同一时刻的用户请求对上。

**Blocked by:** 03 结构化日志与请求关联 ID

**Status:** ready-for-agent

- [ ] AC1：就绪检查路径在全部依赖可用时返回 200，响应逐项给出依赖名、是否必需、状态与耗时，并含聚合状态。
- [ ] AC2：数据库不可用时就绪检查返回 503 且数据库项标记失败；对象存储不可用而数据库正常时同样返回 503，且数据库项仍显示正常——两项互不掩盖。
- [ ] AC3：单个依赖探测挂起时整体响应仍在数秒内返回（每项独立短超时），不会因为一个依赖卡住而超时或崩溃。
- [ ] AC4：存活检查在数据库与对象存储都被替换为失败时仍返回 200 且不触发任何外部探测；其响应含应用版本与启动时间。
- [ ] AC5：探测失败产生带请求标识与依赖名的日志事件，并对同一依赖的重复失败做限流——短时间内的高频探测不产生等量日志。
