# Issue: 训练计划解释性：让用户看懂"为什么这周这样练"

## Problem Statement

训练计划页目前只回答"练什么"：一周七天用日签切换，每天列动作名、组数、次数、重量建议、组间休息和一句动作要领。顶部副标题只有三件事——本周起始日、难度系数、几天。难度系数是给调整算法看的技术值，对用户没有任何含义，而且生成后永远是初始值。

"为什么这样练"完全没有。用户看不到本周目标是什么，看不到重点肌群是从哪次体型分析得出的，看不到本周总训练量是多少，也无从知道计划是不是被自动调整过、凭什么调整。已有什么：生成计划时后端确实把当次的体型分析快照随计划一起存了下来——但这份快照从未出现在接口响应里，前端类型里也没有这个字段，等于存了没用；打卡后会异步触发 AdjustGraph，它确实算出了调整方向与一句人话理由（例如"完成率 92%，表现优秀，适当加量"），但调用链只把改完的动作列表写回计划，理由和调整方向被丢弃，难度系数也不更新，且没有任何调整历史。缺什么：一条从"生成依据"和"调整依据"到用户眼前文案的完整通路。

这带来三种具体的用户困惑。第一，用户对 AI 计划天然存疑，却看不到可核对的事实，只能用"练着看看"来验证，中途放弃的概率高。第二，计划被自动加量或减量后，页面只剩动作变了：加量被当成正常波动，减量被当成功能丢数据，两种情况都会有人去点"重新生成"——而重新生成会归档当前计划，等于把系统刚为他做的调整抹掉。第三，重点肌群这个最有说服力的信息是半成品：计划的重点字段由 AI 生成，可能返回英文分类（推/拉/腿）、中文部位（胸背、全身）或空值，前端只认其中一小部分，剩下的原样透出，用户看到的是 push、upper 这种黑话，或者整块信息空白。

另外，"本周目标"这个说法本身有个数据缺口：计划只存了体型分析快照，没有存生成那一刻的档案快照。用户中途从增肌改成减脂后，计划还是按旧目标生成的，但页面若直接读当前档案，就会得出错误归因。这个缺口必须在设计里承认，不能靠猜。

## Solution

在计划页给用户一块"本周为什么这样练"的解释区，默认收起，展开后回答四件事：本周目标、重点肌群的来源、本周总训练量、本周是否被调整过及调整依据。解释区只陈述可核对的事实（来自哪次分析、什么时间生成、完成率多少触发了加量或减量），不编造因果。文案遵循语言分区：训练计划与报告属正式语言区（ADR-0006），因此解释区全程使用正式中文，不穿插西海岸俚语——那是教练对话与姿态纠错的语气。

数据来源分两类。可派生的一类在前端算：训练量摘要（训练日与休息日数量、动作总数、总组数、预计总时长、重点肌群出现次数分布）完全由已有的周计划数据推导，不新增接口、不改算法。需要落盘的一类由后端只读暴露：生成依据（体型分类、体脂区间、弱势肌群、优势部位、分析结论摘要、分析时间）与最近一次调整说明（方向、触发指标、完成率、时间）。调整判定规则与加减量幅度本 spec 不改，只要求把调整链路里已经算出来的理由与方向持久化下来，让用户看得见。

对没有解释数据的旧计划，解释区降级为可读的说明（"这份计划生成于解释字段上线之前""本周还没有调整记录"），绝不渲染空白或占位符。对重点字段的任何非预期取值，一律归一到人话标签并保留原文兜底，绝不因为一个字段不认识就让整块解释消失。

## User Stories

1. 作为刚拿到新计划的用户，我想要在计划页顶部看到"本周目标是什么"，以便我知道这周在为什么而练。
2. 作为刚做完体型分析的用户，我想要看到重点肌群来自哪次分析，以便我把计划和刚看到的分析结论对上号。
3. 作为对 AI 计划半信半疑的用户，我想要看到解释区列出的可核对事实（体型分类、弱势肌群、分析时间），以便我判断这份计划是不是真的按我的情况来的。
4. 作为中途改过健身目标的用户，我想要知道这份计划是按生成时的目标还是按我现在的目标排的，以便我决定要不要重新生成。
5. 作为想确认训练量是否合理的用户，我想要看到本周训练日与休息日数量、动作总数、总组数、预计总时长，以便我评估这周能不能扛住。
6. 作为关心弱项的用户，我想要看到弱势肌群在本周被安排了几次，以便我确认它们真的被照顾到而不是写在纸上。
7. 作为完成率不错、计划被自动加量的用户，我想要看到"本周被加量了"以及加量的依据（上周完成率百分比），以便我理解计划为什么变难。
8. 作为完成率偏低、计划被自动减量的用户，我想要看到减量说明，以便我不会以为动作变少是功能出问题。
9. 作为本周没被调整过的用户，我想要看到"本周还没有调整记录"，以便我不会把空白当成加载失败。
10. 作为在解释字段上线前就已有计划的用户，我想要看到一句明确的降级说明，以便我不会对着空白区猜。
11. 作为拿到中英混杂重点标签的用户，我想要重点肌群统一显示成人话，以便我不用猜 push、upper、full_body 各是什么意思。
12. 作为遇到恢复周或全体息计划的用户，我想要解释区说明这是恢复安排而不是数据缺失，以便我不去乱点重新生成。
13. 作为在手机上翻计划的用户，我想要解释区默认收起且不挡住今天的动作清单，以便我随时展开又随时收起。
14. 作为要把计划讲给别人听（或自己想核对）的用户，我想要解释区使用正式、可核对的语言而不是口语梗，以便它能被原样复述而不显得像广告词。
15. 作为维护者，我想要解释字段全部可选、旧计划缺字段时接口不报错，以便这次变更不需要回填历史数据。

## Implementation Decisions

### 模块划分

三块，边界清楚：

1. **解释数据契约（后端只读暴露）**：计划响应中新增一个可选解释对象，承载生成依据与最近一次调整说明。后端不新增计算逻辑，只把已经存在或将要落盘的字段读出来。
2. **解释视图归一化（前端纯函数）**：把接口可能给出的任意重点字段取值、缺失依据、缺失调整归结为一份稳定的、可渲染的视图模型；同时从周计划派生训练量摘要与重心分布。这是本 spec 的核心 seam，无副作用。
3. **计划页渲染**：只负责把视图模型画出来，不含任何判定分支（所有"缺什么就显示什么"的判断都在第 2 层）。

### 接口契约（设计决策：类型形状）

计划响应在同一层级新增可选字段 `explanation`，缺省为 null，全部子字段可选：

```
explanation: {
  basis?: {                       // 生成依据
    body_type?: string            // 体型分类（ectomorph/mesomorph/endomorph 或后端原值）
    body_fat_range?: string
    weak_muscles?: string[]
    strengths?: string[]
    analysis_summary?: string
    captured_at?: string          // 该分析的时间；缺失表示无法定位
    profile_goal?: string         // 生成时的档案目标；缺失表示无法定位
  }
  adjustment?: {                  // 最近一次自动调整；null 表示尚未调整
    direction: "increase" | "decrease" | "keep"
    trigger: "completion_rate"
    completion_rate?: number      // 0-1
    occurred_at?: string
    note?: string                 // 调整链路已产出的一句人话理由
  }
}
```

`difficulty_factor` 保留在响应里以兼容既有调用方，但从用户可见的页头文案中移除——它是技术值，用户无法据此行动。

### 数据结构与字段扩展

- 计划记录新增一个可空的解释存储位，用于保存"最近一次调整说明"（方向、触发指标、完成率、时间、理由）。选择写在计划行上而不是新建调整历史表：本 spec 只需要"本周最近一次"，历史表属于计划演化分析，另议。这是改表，因此**遵守全组统一的迁移与数据模型落地约定**（见 `analysis-task-persistence` spec 的「迁移与数据模型落地约定」一节：ORM 为唯一事实源、迁移文件与模型手写对齐、按交付追加 revision、迁移必须可回滚），本 spec 不另立一套约定；本次迁移内容仅为本表新增可空列，不含数据回填。
- 计划记录新增一个可空的"生成时档案快照"，与已有的体型分析快照同级。理由：只有存了生成时的目标，才能诚实地回答"这份计划是按哪个目标排的"。旧计划该字段为空，走降级文案；该列与上一条同一次迁移交付。
- 体型分析快照需要能定位到具体某次分析（时间或记录标识）。当前快照里没有任何时间信息，因此要么在快照里补上生成时间，要么另存引用；二者都是可选字段，旧快照缺失时解释区只显示"分析时间未知"，不报错。
- 所有新增字段均可空，读取路径必须先判空再渲染。

### 归一化规则（设计决策：判定规则）

重点字段（focus）的取值可能来自三种来源：英文分类键（上肢推/拉、腿、核心、全身、上肢、下肢、有氧、恢复等）、AI 自由输出的中文（例如"胸背""背+二头"）、以及空值或休息日标记。规则：

1. 命中已知英文分类 → 映射为中文标签并归入稳定分类。
2. 命中已知中文标签 → 直接使用，并尽量归入同一分类。
3. 其余情况 → 原样作为标签显示，分类记为"其他"，绝不丢弃、绝不显示空白。
4. 空值或休息日 → 视为恢复日语义，不进入重点肌群计数。
5. 训练量摘要遇到空动作列表或全体息 → 输出明确的 0 值形态（"本周为恢复周"），不做除零计算。

训练量摘要的最小定义（设计决策）：训练日数、休息日数、动作总数、总组数、预计总时长合计、重点肌群出现次数（按分类聚合，同一天同一分类只计一次），以及"最重的一天"。全部由周计划派生，不依赖接口新字段。

本周目标的推导顺序（设计决策）：生成时档案目标优先 → 缺失则当前档案目标（并注明是按当前档案推断）→ 再缺失则用弱势肌群概括（"优先补齐上肢拉力"）→ 全缺失则中性文案"本周以均衡发展为主"。

### 空态与降级矩阵

| 情形 | 解释区表现 |
| --- | --- |
| 还没有计划 | 不渲染解释区，沿用现有空态 |
| 有计划、无解释数据（旧计划） | 依据区显示"这份计划生成于解释字段上线之前"，调整区显示"本周还没有调整记录" |
| 有解释数据、快照字段缺失 | 只显示已有字段，缺失字段整行不出现，不显示"—"或"undefined" |
| 有解释数据、adjustment 为 null | 显示"本周还没有调整记录"（明确是"没有"，不是"加载中"） |
| 调整方向为 keep | 显示"本周保持原强度"，与"没有调整"区分开 |
| weekly_plan 为空或解析失败 | 解释区整体隐藏，计划区走现有错误/空态，不在解释区报错 |
| 计划为全体息日 | 显示"本周为恢复周"及安排原因（若快照里有），训练量摘要显示 0 与休息日天数 |

### 文案策略

- 解释区标题中性（"本周为什么这样练"），四块小标题固定为：本周目标、重点来源、训练量、调整说明。
- 事实性字段用中性陈述句 + 具体数值（"上周完成率 92%，超过加量线，本周组数上调"），不写"AI 认为"。
- 全篇正式中文（ADR-0006：训练计划与报告类不穿插西海岸俚语，与教练对话、姿态纠错的语气明确区分），不堆感叹号、不玩梗、不用"yo/bro"。
- 解释区结尾可以有一句"本周意图"的总结，但用正式短句（例如"本周以补齐上肢拉力为主，训练量比上周上调一档"）。
- 禁止在无数据时下结论；禁止承诺结果；调整说明必须给出触发数值，不能只写"系统已优化"。
- 恢复周、数据不足、旧计划三种降级文案固定，不允许各页面自造。

### 旧数据兼容

- 旧计划没有解释存储位与档案快照：接口返回 null，页面走降级文案，不回填、不追溯。
- 旧计划没有分析时间：显示"分析时间未知"，其余依据字段照常展示。
- 旧的调整已经发生但未记录：明确显示"本周还没有调整记录"，不猜测历史。
- `difficulty_factor` 字段保留但不再展示，避免旧前端类型报错。
- 重新生成计划会归档旧计划——本 spec 不改变该行为，但解释区必须让"重新生成"的后果可预期（调整说明存在时，解释区明确写出"重新生成会归档本周已调整的计划"这类提示属于可选增强，若实现需在文案集中评审）。

## Testing Decisions

### 好测试的标准

只测外部可观察行为：给定一份计划响应（含/不含解释字段、字段残缺、focus 混杂）断言视图模型的目标文案、训练量数字、重点分类计数、调整说明文案；给定计划页渲染结果，断言解释区在三种降级形态下的可见文案与"默认收起"。不测内部实现细节、不测具体样式、不测函数拆分方式。

### 被测模块与最高 seam

最高 seam 有两层，各自锁定不同风险：

1. **前端纯函数（主 seam）**：归一化 + 训练量摘要 + 目标推导。表驱动覆盖：混合 focus 取值（英文键、中文、自由文本、空、休息日）、全空计划、缺 explanation、缺快照字段、adjustment 三种方向、并列分类去重、除零边界。
2. **后端路由层（读取契约）**：用 ASGI 传输层直接打计划读取路由，数据库用进程内隔离库，直接插入两类计划记录——一类的解释字段齐全，一类为旧数据（解释为空）——断言响应包含解释对象、旧数据返回 null 且仍为成功响应（状态码非错误、不抛出）。只读路径不触发 LLM，因此不需要模型桩。
3. **页面渲染（一次）**：jsdom 渲染计划页，mock API 与认证，断言三种降级形态与"解释区默认收起、可展开"。

### 为什么不需要更低层的 seam

- 不为 AdjustGraph 的 LLM 节点写单测：调整算法本身（5 路并行分析器）是另一份 spec 的范围，这里只需要"理由被持久化并被读出来"，用路由层响应验证即可。
- 不为 ORM 列写迁移测试：字段可空 + 路由层读旧数据不报错，已经覆盖了兼容性风险；再测 schema 本身只是重复。
- 不在页面层重复断言归一化规则：页面只验证接线，规则细节由纯函数层负责，避免同一规则两处维护。

### Prior art

- 后端路由层 + ASGI 传输 + 进程内隔离库 + 覆盖数据库依赖：仓库现有的鉴权守卫测试（见相关文件）的 fixture 写法可直接沿用。
- 纯函数 + 表驱动断言阶段状态：分析页现有的闭环判定纯函数及其单元测试（见相关文件）。
- jsdom 页面渲染 + mock API/认证：BYOK 门禁行为测试与数字教练行为测试（见相关文件）。
- 不要以"读取源码断言包含某字符串"作为主要手段：它证明不了渲染结果，最多作为防止文案被误删的补充。

## Out of Scope

- 重设计计划调整算法（5 路并行分析器、疲劳度/伤病风险/睡眠/体重趋势参与决策）——属另一份 spec；本 spec 只消费调整链路目前已产出的方向与理由。
- 计划历史与周与周之间的对比视图（需要完整的调整历史表，另议）。
- 训练过程页（当前动作、组数推进、完成进度）与打卡后反馈闭环。
- 计划生成提示词与体型分析提示词的改写。
- 计划分享、导出、打印。
- 个性化解释风格的 A/B 或用户可选语气。

## Further Notes

- 本 spec 与 `first-run-onboarding` 的分工：引导只判断"有没有计划"，不定义计划字段；计划页解释区不参与引导判定。
- 与 `weight-trend-insights` 的交叉点只有一个：档案里的健身目标词汇（减脂/增肌/塑形/提升体能）被两处使用，但目标偏离判断的阈值与口径只在体重那份 spec 定义。
- 与打卡闭环 spec 的边界：让调整图输出"方向 + 理由"属于打卡反馈那条线的最小契约；本 spec 不重复定义 Graph 的输出形状，只要求"该结论必须被持久化，并在计划读取时可见"。两份若同时实施，以"Graph 输出结论"为共同前置，落盘与展示在本 spec。
- 语言决策记录：术语表把"计划调整理由"列为西海岸俚语适用范围，但 ADR-0006 明确规定训练计划与报告类保持正式语言。本 spec 以 ADR 为准（正式中文），并把这条差异记在这里，避免实现者按术语表写成口语梗。
- 未决：解释数据采用"计划行上的可空 JSON 位"还是"独立调整历史表"。本 spec 按前者设计（最小改动、只保留最近一次）；若后续要做历史对比，需要把存储升级为表，视图模型与页面不变。
- 未决：分析快照定位方式是"快照内补时间"还是"存分析记录标识"。前者改动小，后者能直接回链到分析历史页；两者都兼容缺省。
- 已知现状风险（供实现者注意）：重新生成会归档当前 active 计划，因此解释区里任何指向"重新生成"的入口都必须写清后果，避免用户把系统刚做的调整抹掉。

## 落地修订（工单 20）

以下修订由工单 20 的实现回写，覆盖正文（尤其「接口契约」与「数据结构与字段扩展」）中
与之冲突的旧表述。只记录与 spec 有差异或把 spec 写得更具体的地方。

### 工单 20（计划解释字段落库与读取）

1. **接口命名以工单为准**：正文的 `explanation.basis` / `explanation.adjustment` 落成
   `explanation.generation` / `explanation.latest_adjustment`。理由：验收条款（AC1/AC2/
   AC3/AC5）逐条点名这两个名字，前端视图模型按验收写；正文里的旧名字作废。正文中
   `adjustment.note` 一并改名为 `reason`，`trigger` 保留且恒为 `completion_rate`
   （当前调整链路只有完成率一个触发指标，由投影层写死，不落库）。
2. **`explanation` 恒为对象，两个子对象可空**：正文写「新增可选字段 `explanation`，缺省
   为 null」，实现取更严的形态——读当前计划时 `explanation` 永远存在，旧计划读到的是
   `{"generation": null, "latest_adjustment": null}`。理由是键集合稳定后，前端只在子对象
   上做降级判断，不必再区分「字段缺失」与「整块缺失」两种情况；AC3 要求的「解释字段为
   null」正是这两个子对象。生成接口（`POST /plan/generate`）不回填该字段（读路径才投影）。
3. **存储只加两列，且都是可空列**（同一次迁移交付，不回填历史）：
   - `profile_snapshot`（JSONB，可空）：生成时的档案快照。存整份档案而不是只存 `goal`
     一个字符串——正文要求「生成时档案快照」，且下一个要用档案字段（身高/体重/经验）
     做解释的工单不必再改一次表；读取时只投影 `goal`，缺失即为 null。
   - `analysis_captured_at`（带时区 DateTime，可空）：该次体型分析快照被本计划捕获的
     时刻。分析结果本身不带时间戳，生成接口也不持有分析记录标识，因此按正文允许的
     「在快照里补上生成时间」落地；语义**刻意**限定为「该分析被这份计划捕获的时间」，
     不冒充 LLM 分析完成时间。旧计划为空 → 「分析时间未知」；生成时没有拿到分析则
     不写，绝不伪造一个时间。
4. **调整说明不新增自己的存储位**：正文「数据结构与字段扩展」里「计划记录新增一个可空
   的解释存储位（方向、触发指标、完成率、时间、理由）」与本条冲突，作废。方向、完成率、
   时间、理由全部按 `training_plans.latest_adjustment_id` 读回工单 08 的结论记录再投影，
   计划行只存引用、不复制文本（这是 Lead 在工单里点明的裁决，也是结论唯一事实源的物理
   保证）。`occurred_at` 取结论记录的 `created_at`。
5. **投影层做类型容错，读路径不因残缺数据失败**：快照里的自由值收敛成文本或字符串列表；
   `weak_muscles` / `strengths` 被模型写成字符串时按单元素列表兜底，整型/空串/None 降级为
   null；调整引用指向不存在的记录（该列无外键，记录可能被清理），或方向的取值越出
   `increase` / `decrease` / `keep` 时，`latest_adjustment` 降级为 null——宁可不解释，也
   不谎报方向。这三种情形在路由层用例里各有断言。
6. **解释对象挂在 `PlanResponse` 顶层而不是塞进 `plan` 里**：`TrainingPlanSchema` 同时是
   生成链路的 LLM 输出解析目标，往它里面加字段会被写进提示词的格式指令，改变生成行为；
   顶层新增字段对既有调用方是纯增量，`difficulty_factor` / `weekly_plan` 等字段的类型与
   含意不变（AC5 用例守住）。
7. **迁移落地**：`backend/alembic/versions/0006_plan_explanation.py`，revision `0006`、
   down_revision `0005`，upgrade 只做两条 `op.add_column`（可空），downgrade 精确删除这两
   列，可回滚到 0005；ORM 是唯一事实源，列集合与类型逐列对齐（SQLite 上即 TEXT 与
   DATETIME），不含数据回填。
8. **刻意不做**：`explanation.latest_adjustment` 不返回 `adjustment_id`（AC 未要求；前端
   若要回链 `/adjustments/{id}`，下一张工单再加，属纯增量）；「重新生成会归档本周已调整
   的计划」的提示文案与解释区渲染在工单 21。

## 落地修订（工单 21）

计划页解释卡与训练量摘要的落地取舍，覆盖正文中与之冲突或含糊的表述：

1. **卡片默认收起，四块固定标题**：「本周为什么这样练」默认收起，展开后依次是 本周目标 /
   重点来源 / 训练量 / 调整说明；四块在任何输入下都有非空文案（缺数据走降级句，不出现占位符
   或空白块）。展开状态不写进 URL——它只是查看偏好，不是可分享的查询状态。
2. **训练量全部由周计划派生**：训练日/休息日数、动作总数、总组数、预计总时长合计、按分类
   聚合的重点出现次数、最重的一天（组数最多，组数相同比时长）。**同一天同一分类只计一次**
   （重点是「这周练到了哪些部位」，不是动作条目数）；休息日不进入分类计数；空计划与全体息
   计划输出「本周为恢复周」与 0 值，不做除法，因此不会出现除零或 NaN。
3. **重点字段先归一再展示**：英文分类键（push / pull / legs / lower / upper / core / cardio /
   full_body / recovery 等）映射为中文标签并归入稳定分类；已知中文按关键词归入同一套分类；
   未知值**原样保留**且分类记为「其他」；空值显示「未标注重点」——不丢弃、不伪造、不出现空白标签。
   分类聚合后的展示标签用**稳定分类名**（同一周里「胸」与「push」归入同一类时只显示「上肢推」，
   不会出现两个标签指向同一类）。
4. **本周目标按优先级推导**：生成时档案目标 > 当前档案目标（文案标注「按当前档案推断」）>
   弱势肌群概括（「本周重点补强：…」）>「本周以均衡发展为主」。四条路径各有单测，页面只渲染
   推导结果。
5. **三档降级互不混淆**：没有任何解释数据 → 「生成于解释字段上线之前」；有解释但本周没有
   调整 → 「本周还没有调整记录」；方向为 keep → 「本周保持原强度：…」。三种情形都不出现空缺
   块、未填充占位符或错误提示。调整说明**直接引用后端理由**，不再重复拼接完成率——理由文本
   本身已含触发数值，重复拼接会让同一句话出现两次。
6. **页头移除难度系数**：`difficulty_factor` 是不可行动的技术值，用户看到只会困惑；页头只
   保留周起始日与天数。数据本身仍在 API 与计划对象里，不删字段、不改算法。
7. **生成后补读一次解释**：生成接口只返回计划本身，解释字段随读取接口回来；页面在生成成功
   后重新读一次当前计划以填充卡片，避免刚生成的计划被误显示成「生成于解释字段上线之前」。
8. **不新增接口、不改算法**：本票只用工单 20 已暴露的 `explanation` 与周计划本身；训练量
   聚合、重点归一与目标推导都是纯函数（见「相关文件」），页面只做展开/收起与渲染。
