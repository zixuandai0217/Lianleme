# Issue: AI 陪练输出协议收口（结构化 SSE 事件、服务端快捷动作、异常兜底）

## Problem Statement

陪练页的对话现在是一条「裸管道」：CoachGraph 逐 token 吐出模型原文，服务端把每一段原文塞进一行 `data:`，前端把收到的字符串直接累加进气泡。于是用户看到的到底是不是教练该说的话，取决于模型这一轮心情好不好。模型偶尔按上下文沿用 JSON 形状回答时，用户就在气泡里读到 `{"reply": "...", "suggested_actions": [...]}` 这种字样，而前端没有任何一层能识别它不是要给用户看的内容。

更糟的是错误也被伪装成了正常输出。供应商鉴权失败、限流、超时的时候，服务端会把一句中文提示当成普通 token 发进流里，前端照单拼接进气泡。用户与旁观的评审者都分不清这句话是教练在说、还是系统在报错——状态灯不亮，重试按钮不出现，语音朗读还会把这句话念出来。这条路径上的「失败」没有形状。

快捷动作是另一个断层。气泡下方的按钮是写死在前端页面里的四条固定文案，与用户此刻在练什么动作、做到第几组、今天是不是恢复日毫无关系。非流式对话接口其实已经要求模型返回 `suggested_actions`，但没有任何界面消费它——服务端算出过建议，用户却永远看不到。

协议本身的健壮性也不足。帧是把原始文本直接拼进单行 `data:` 的，一旦模型输出里出现换行（代码块、结构化内容几乎必然出现），前端按行切分就会把一帧切成两半，表现为文字断裂、丢字或者整轮停在一个空气泡上。而持久化保存的正是这段未经清洗的原始流，所以即使这一轮侥幸没崩，下次进页面回放历史时，泄漏过的内容会原样再出现一遍。

## Solution

把陪练输出从「谁的文本都能过」改成一条有类型的事件流：服务端只发几类结构明确的事件——开场元信息、正文增量、教练状态、快捷动作、错误、收尾，每帧是一条合法的 JSON、一行一个事件，前端只认这几种类型。用户看到的正文只来自「正文增量」这一类事件，错误永远走错误事件，绝不会混进气泡。

正文在离开服务端之前统一过一遍清洗：模型返回的代码围栏、JSON 外壳、结构化残留一律不出现在用户可见文本里；如果模型这一轮整段都不可读，服务端给一句符合 West Coast Slang 人设的兜底文案，而不是把原始结构当作回答。清洗后的文本才是入库的内容，所以历史回放与实时看到的是同一份东西。

快捷动作改由服务端按当前训练上下文生成，随事件流下发；点击一个动作就是把它的回填文案发成下一条用户消息。取不到动作（上下文缺失、模型不可用）时退回一组与训练无关的通用动作，按钮不会消失、也不会点出无意义的空消息。

失败被分成两层说清楚：流还没开始就失败（未登录、身份与请求不匹配、没有可用的 BYOK Key）仍然走普通 HTTP 错误，不进流式状态；流开始之后失败则先发一条错误事件（带稳定错误码和一句可读文案），再以收尾事件结束这一轮。前端据此显示一条独立的、不属于教练正文的提示，并停止朗读。用户主动中断不算错误：不弹提示、不播报、不落库半截回复。

## User Stories

1. 作为正在跟练的用户，我想要气泡里只出现教练该说的话，以便不用费力分辨哪些字是机器残留。
2. 作为正在跟练的用户，我想要快捷动作跟着我当前的动作和进度变化，以便点一下就是我想问的那句话。
3. 作为正在跟练的用户，我想要教练回复读起来仍然是西海岸健身房搭子的口气，以便结构化改造没有让陪练变成客服机器人。
4. 作为正在跟练的用户，我想要服务出问题时看到一句明确的「暂时用不了」，而不是把它当成教练在敷衍我，以便我知道该重试还是该去配 Key。
5. 作为正在跟练的用户，我想要流到最后话题卡住时至少收到一句完整的话，以便界面不会永远停在「正在思考」。
6. 作为正在跟练的用户，我想要自己按停止后不会被弹一条错误，以便中断是可控的而不是像故障。
7. 作为重新进入页面的用户，我想要历史记录里的每条回复和我当初看到的一样干净，以便旧数据不会把泄漏再演一遍。
8. 作为重新进入页面的用户，我想要历史里的回复也能带出当时的快捷动作，以便我可以接着上次的节奏继续问。
9. 作为用语音听教练的用户，我想要错误提示不会被朗读成教练台词，以便耳朵里不会出现两套声音。
10. 作为配置自带 Key（BYOK）的用户，我想要 Key 不可用时立刻收到明确的配置提示，以便不必等一轮流走完才发现没配好。
11. 作为弱网用户，我想要流在传输中途断开时界面能收敛到一个确定的终态，以便不会留下半句话和一个不动的光标。
12. 作为前端开发者，我想要服务端只发我认识的几种事件类型，以便新增事件不会让旧解析逻辑崩掉。
13. 作为前端开发者，我想要协议版本在开场事件里给出，以便线上出问题时能从日志判断是哪一版客户端。
14. 作为前端开发者，我想要解析与归约逻辑是独立于页面的纯函数，以便不渲染界面也能测清分帧、乱序帧与未知事件。
15. 作为后端开发者，我想要「清洗」「动作规划」「状态推导」各自是独立可替换的环节，以便调整人设或换模型时不动协议。
16. 作为后端开发者，我想要一轮对话有且只有一条收尾事件，以便服务端不必假设客户端如何判断流结束。
17. 作为评审者，我想要协议形状被一条路由层契约测试钉住，以便后续重构不会悄悄退回裸文本。

## Implementation Decisions

### 1. 事件流契约（设计决策：事件形状在此定义，本组其余 spec 引用本节）

传输仍是 SSE：每帧一行 `data: <一个 JSON 对象>`，帧之间空行分隔；不使用命名事件（`event:`）字段，类型判别放在 JSON 里的 `type` 上，这样客户端只有一条解析路径，也不会因两种判别方式并存而分叉。JSON 序列化保证单行，正文中的换行以转义形式存在，因此「一帧一行」永不破裂。

事件集（v1，`protocol: 1`）：

```jsonc
{ "type": "turn_started", "protocol": 1, "turn_id": "<opaque>", "message_id": "<opaque>" }
{ "type": "message_chunk", "text": "<增量文本>" }
{ "type": "state", "coach_state": "guide" | "count" | "rest" | "complete" }
{ "type": "actions", "actions": [ { "label": "<按钮文案>", "prompt": "<点击后发送的文本>" } ] }
{ "type": "error", "code": "provider_unavailable" | "rate_limited" | "upstream_timeout" | "internal", "message": "<用户可读中文>" }
{ "type": "done", "finish_reason": "complete" | "error" | "truncated" }
```

约束：

- 每轮恰好一条 `turn_started` 且为首帧；每轮恰好一条 `done` 且为末帧，`done` 之后服务端不再发任何帧。
- `message_chunk` 是增量（delta），客户端累加；不得发空文本；不得在 `error` 之后继续发。
- `state` 可出现多次，最后一次生效；缺省为 `guide`。
- `actions` 一轮最多一次，且必须早于 `done`；列表长度 0–4，0 表示本轮不给动作（前端保留默认动作集）。
- `error` 不是终结帧；它必须被 `done(finish_reason: "error")` 收尾，这样客户端只需要认一个终态。`finish_reason: "truncated"` 用于服务端主动提前收尾（例如超出时长预算）且已产生可见正文的情况。
- 未知 `type` 与未知字段必须被客户端忽略（前向兼容），字段缺失必须降级而不是抛错。

### 2. 正文清洗（协议边界上的一个环节）

清洗发生在「模型增量文本 → 可展示文本」这一层，位于事件发送之前，且是纯函数式、可单独替换的环节：

- 开头缓冲判定：先缓存开头少量字符（量级：数十字符），若判定为 JSON 对象/数组起始（`{` 或 `[` 后接引号键），则暂停放行，直到能解析出完整对象；解析成功则取其中的 `reply`（其次 `message`、`content`）作为正文，解析失败则丢弃该段并继续放行后续自然语言部分。若不是 JSON，则立即放行并停止缓冲，避免给首字增加延迟。
- 代码围栏与代码块：三反引号围栏（含 `json` 标注）整体不进入正文；围栏内若是可解析的 JSON 且含回复字段，则取该字段文本替代。
- 行内结构残留：单行疑似键值 JSON 片段、裸露的 `{"` / `"}` 边界剥离；连续反引号替换为空。
- 空正文兜底：清洗后整轮无有效文本时，发送一句固定兜底文案（短句、西海岸口气、不含脏话），`finish_reason` 仍为 `complete`，因为用户视角这是可用的回答。
- 幂等与顺序：清洗是流式的，输出顺序与模型顺序一致；不允许把已放行的文本再回收（不产生「撤回」体验）。
- 入库内容是清洗后的正文，不是模型原文。

### 3. 快捷动作规划

- 服务端新增一个动作规划环节，输入是当前训练上下文（今日是否恢复日、当前动作、已完成/总组数、计划是否存在）、最近一条用户消息、当轮教练状态；输出 0–4 条 `{label, prompt}`。
- `label` 是按钮文案（短、可点击），`prompt` 是点击后作为用户消息发送的文本；缺省时 `prompt` 等于 `label`。这个分离使「按钮短」与「消息完整」不再互相牵制。
- v1 采用确定性规则（关键词与上下文优先，覆盖热身建议、完成一组、换动作、动作要领、状态不佳时的降级建议等），不额外调用 LLM：一次额外模型调用会拖慢首字并引入新的失败面，而动作的价值来自「和当前上下文对得上」，规则已经能做到；模型侧的 `suggested_actions` 在 v1 不作为动作来源。
- 规则全部未命中时返回通用动作集（与今天写死在页面里的那几条等价），这是降级路径，保证按钮区永远有内容。
- 非流式对话接口复用同一个规划环节与同一套清洗/状态枚举，返回形状保持不变（避免破坏既有前端类型），因此两条接口不会出现两套契约。

### 4. 教练状态推导

- `coach_state` 由服务端根据上下文与当轮进展确定性推导（例如是否在计组、是否建议休息、是否完成、是否在讲解），不依赖模型自述；模型自述的状态只在非流式接口里作为可选修正输入。
- 状态只影响数字教练的呈现，不影响正文内容；状态推导失败时回落 `guide`，不允许因为状态推导异常中断整轮。

### 5. 轮次状态机与客户端归约

- 一轮的生命周期：`idle → thinking → streaming → (idle | error | aborted)`。`turn_started` 把 `thinking` 推进到 `streaming`，`done` 收敛：`complete` 与 `truncated` 回 `idle`，`error` 进 `error`；本地中断进 `aborted`。
- 客户端只接受当前 `turn_id` 的帧；旧轮次的迟到帧丢弃（避免中断后重发时的串台）。
- `error` 帧产生的提示是独立于气泡正文的展示单元（提示条/系统消息样式），不与教练正文混排，且不进入朗读队列。
- 传输层在 `done` 之前就结束（连接断开、无收尾帧）视为 `truncated`：保留已收到的正文、标注「连接中断」、不保留空气泡；若已收到 `error` 则按 `error` 处理。
- 用户中断：不产生错误提示、不播报、不落库助手消息；服务端记一条告警级日志（字段约定由运行与观测 spec 定义，本节不重复）。

### 6. 前后端模块边界

- 服务端：路由层只负责「鉴权前置校验 → 调用 Graph → 把增量与副产物转成事件帧」；清洗、动作规划、状态推导是三个独立的可替换环节，路由不内联它们的逻辑。
- 前端：拆出一个与 React 无关的协议层，含两个纯函数/纯对象——帧解码器（字节流 → 事件序列，负责 UTF-8 增量解码、跨块拼帧、忽略注释行与心跳、容忍多帧同块与帧被切断）与轮次归约器（事件序列 → 气泡文本、教练状态、快捷动作、终结原因）。页面只订阅归约结果，不再自己切字符串拼 `data:`。
- 向后兼容：前端与后端同仓同部署，v1 不承诺跨版本兼容；`protocol` 字段保留用于日志定位与将来灰度。
- 现有非流式对话入口在前端没有任何调用方（历史遗留方法）；本期保留方法但不在页面上使用，避免顺手扩大改动面。

### 7. 错误与降级策略汇总

| 场景 | 识别时机 | 对外表现 |
| --- | --- | --- |
| 未登录 / 身份不匹配 | 流开始前 | 普通 HTTP 4xx，不进流式状态 |
| 无可用 BYOK Key（含系统回退关闭） | 流开始前 | 普通 HTTP 409 语义，提示去配 Key |
| 供应商鉴权失败 | 流中 | `error(provider_unavailable)` + `done(error)`，提示检查 Key |
| 限流 | 流中 | `error(rate_limited)` + `done(error)`，提示稍后重试 |
| 供应商超时 | 流中 | `error(upstream_timeout)` + `done(error)` |
| 输出不可读（整段结构残留） | 清洗阶段 | 兜底文案，`done(complete)` |
| 服务端内部异常 | 任意 | `error(internal)` + `done(error)`，绝不泄漏异常原文 |
| 用户中断 | 客户端 | 无事件保证；前端 `aborted`，不落库、不提示 |
| 超出时长预算 | 服务端 | `done(truncated)`，保留已发正文 |

- 任何错误路径都不得把错误文案伪装成 `message_chunk`；这是本 spec 要修掉的核心缺陷。
- 已产生可见正文后失败时，正文保留、错误提示追加在其下，不覆盖、不清空。

## Testing Decisions

### 好测试的标准

只断言用户可观测面：帧类型及顺序、正文增量拼起来的值、快捷动作条目、教练状态、终结原因、历史回放内容，以及前端归约后的展示状态。不断言提示词字符串、不断言内部函数调用次数、不用整段字符串相等去钉帧分隔符的字节细节（用测试侧一个最小解码器把响应体读成事件列表，再断言事件列表）。测试应当允许实现替换清洗策略、动作规则、状态推导，只要外部契约不变。

### 最高 seam：后端 FastAPI 路由层

用测试内应用客户端直接请求陪练流式路由，依赖替换注入隔离数据库，并用假 Graph 替身（或替换 LLM 工厂）控制模型输出。断言：

- 正常一轮：首帧 `turn_started`、末帧 `done`、正文增量累加等于预期正文、`state` 至少一次、`actions` 早于 `done`。
- 模型输出 JSON 外壳：正文不含 `{"reply"`、不含围栏标记，且正文等于其中的回复字段。
- 模型输出含换行/代码块：正文中不出现围栏，且帧仍是「一帧一行」的合法 JSON（由测试侧解码器断言解析成功）。
- 上游失败：出现 `error` 事件（带错误码与可读文案）且随后 `done(error)`，且**不存在**把错误文案当正文的 `message_chunk`。
- 整轮不可读：只有兜底文案，`done(complete)`。
- 上下文为空（无今日计划、无当前动作）：仍返回通用动作集，且 `prompt` 字段非空。
- 鉴权/Key 前置失败：不进入流式响应，返回 4xx 且不产生任何事件帧。
- 历史回放：写入带结构残留的助手记录时，回放接口返回的是清洗后文本（或明确不返回泄漏内容）。

为什么不需要更低层的 seam：客户端唯一依赖的是事件形状与顺序，Graph 内部实现、提示词文案、清洗规则的具体正则表达式都是可替换实现；对它们写单测会把最容易变的策略钉死。人设类断言已由既有回归覆盖，本 spec 不重复。

### 最高 seam：前端纯 TypeScript 协议层

用 vitest 直接驱动「帧解码器 + 轮次归约器」这对组合，输入是真实帧序列的字符串，按不同分块方式喂入，断言归约后的展示模型（正文、状态、动作列表、终结原因）。覆盖：帧被任意位置切断、多帧同一块、注释行/心跳、未知 `type`、字段缺失、迟到旧 `turn_id` 帧、`error` 后仍有帧、`done` 前连接结束、空正文兜底。页面级 jsdom 测试只覆盖接线：快捷动作来自服务端并在点击后作为用户消息发送、错误提示与正文分离渲染、中断不出现错误提示、历史回放内容直接展示不二次解析。

为什么不需要更低层的 seam：把解码器与归约器拆成两层分别测，会漏掉「分帧」这一最关键的真实故障模式——现在的缺陷正是分帧与拼接之间的缝隙。合成一个纯函数组合恰好是页面唯一依赖的边界，且不渲染界面就能覆盖全部分支。

### 必测行为清单（进入质量门）

1. 正常轮次的帧序列符合契约（首帧、末帧、类型集合）。
2. JSON 外壳与代码围栏不出现在正文里。
3. 错误在流中发生时不伪装成正文，且以 `done(error)` 收尾。
4. 整轮不可读时给出兜底文案。
5. 快捷动作由服务端下发，字段齐全，点击后文本等于 `prompt`。
6. 上下文缺失时动作降级为通用集。
7. 历史回放内容与实时清洗结果一致。
8. 前端解码器在任意分帧下产生同一事件序列。
9. 前端归约器对未知事件/缺失字段/旧轮次帧保持不崩且状态正确。
10. 中断与传输中断分别收敛到 `aborted` / `truncated`。

### 仓库内 prior art

- 陪练流式失败的既有回归测试：假 Graph 替身 + 异步测试，是「路由层 + 事件序列断言」的直接模板（其断言里的错误文案需要用新契约重写）。
- TTS 与用户 Key 的路由层测试：进度替换依赖、隔离数据库、前置校验 4xx 的断言方式。
- 前端纯函数测试与页面级 jsdom 测试：纯函数单测、`@vitest-environment jsdom` 声明、路由与鉴权 mock 的既有写法；分析页的旅程推导纯函数是「把页面状态收敛成纯对象」的既有范式。

## Out of Scope

- TTS 与唇形同步协议（口型时间轴、音频分片）——本次只保证错误提示不被朗读。
- 语音输入与浏览器语音识别。
- 教练人设与内容质量的调优（西海岸口气的取舍、脏话尺度）。
- 多轮记忆摘要、历史分页与检索。
- VisionGraph、计划生成、打卡等其他链路的输出契约。
- 模型选择、成本控制与多供应商路由。
- 协议跨版本兼容承诺与灰度能力。

## Further Notes

读代码后确认的现状（本 spec 要修的事实）：

1. 流式输出是裸文本协议，且失败路径把一句中文提示直接当正文 token 发出去；现有回归测试把这个字符串写死为断言目标，所以它是本次契约变更的锚点，需要随契约一起改成「错误事件存在、正文不含错误文案」。
2. 两条对话入口契约互相矛盾：非流式接口的系统提示要求模型返回 JSON 并带快捷动作，解析失败时却把模型原文当作正文返回（这是 JSON 泄漏最直接的根因）；流式接口的系统提示又明令「不要用 JSON」。同一份人设出现两套输出要求，是必须收口的地方。
3. 持久化保存的是未经清洗的原始流，所以历史回放会把泄漏再演一次；清洗必须发生在入库之前，否则只修实时路径等于没修。
4. 前端快捷动作是页面内硬编码常量；非流式接口返回的快捷动作在全部页面里没有任何调用方，属于已实现但未接线的能力。
5. 帧编码本身不安全：原始 token 被直接拼进单行 `data:`，而结构化输出几乎必然带换行；前端按行切分时会静默截断。这是「换行一出现就丢字」的机制性原因，也是本次坚持「JSON 单行帧」的理由。

未向 Lead 确认、按代码现状做出的决策（记录于此）：

- 选择「data 里放 JSON 对象、用 `type` 判别」而不是命名 SSE 事件：客户端只有一条解析路径，且与现有逐行读取的客户端结构兼容度最高。
- `error` 不作为终结帧，`done` 是唯一终态：把「流何时结束」收敛为单点，前端不必维护两套终止条件。
- v1 的服务端快捷动作用确定性规则而非额外 LLM 调用：优先首字延迟与可测性。
- 用户中断不落库助手消息（与现状一致），只留告警日志。
- 不为协议保留跨版本兼容：前后端同仓部署，多一层兼容会显著放大清洗与归约的复杂度。
- 非流式入口保留但不接页面，避免在本期顺手扩大改动面。

## 落地修订（工单 19）

错误 / 中断 / 回放清洗的落地取舍：

1. **流开始前的失败不产生任何事件帧**：未认证 401、身份不匹配 403、无可用 Key 仍是仓库
   统一的 HTTP 428 `api_key_required`（由工单 09 与 BYOK 设计文档确立），响应体是普通
   JSON。AC5 的「409 语义」按「前置 4xx、普通 JSON、零帧」理解；不为这张票单点改成 409，
   以免同一个前置条件在分析、陪练、计划三条链路上出现两种状态码。
2. **流中失败**：先发 `error(code, message)` 再发 `done(error)`；错误文案绝不以
   `message_chunk` 发出，已显示的部分正文保留。
3. **主动中断不算失败**：SSE 生成器在增量之间与收尾之前检查 `request.is_disconnected()`，
   中断时不发 error/done、不落库该轮助手消息、不降级为错误提示；服务端只记一条告警事件。
   事件复用观测中间件已有的 `stream.sse.interrupted` 契约（ADR-0008 §2 禁止同义别名），
   字段为 route / method / chunks_sent / error_code=client_disconnect，不含任何正文。
   被 Starlette 取消（`CancelledError`）的那条路径由中间件记录同一事件，路由不重复记。
4. **传输截断**：收尾帧之前连接结束时，前端把该轮收敛为 truncated，保留已收到的正文，
   显示独立的「连接中断」提示（`role=status`），不留下永远「正在思考」的空气泡；
   正文为空时不留空气泡，只显示提示。
5. **提示单元与朗读隔离**：错误提示是转写区之外的独立单元（`role=alert`），绝不混进教练
   气泡；语音只朗读 `presentation.speakable`，错误与中断提示都不进入朗读队列。
6. **回放清洗**：历史接口在读取时对 assistant 文本再次应用 `CoachTextCleaner`（幂等），
   旧数据里的 JSON 外壳与代码围栏不会再被演一遍；清洗后为空的行回落标准兜底句。
7. **测试 seam**：httpx 的 ASGITransport 不会在应用产出响应期间投递 `http.disconnect`，
   因此中断用例在路由 seam 用 monkeypatch `Request.is_disconnected` 驱动，断言零
   error/done 帧、`save_turn` 未被调用、恰好一条无正文的告警事件。


## 落地修订（工单 18）

服务端快捷动作与教练状态的落地取舍：

1. **确定性规划器**：`plan_quick_actions` 与 `derive_coach_state` 只读服务端上下文
   （今日计划三态、当前动作、已完成/总组数、最近一条用户消息），不调用模型、不含随机；
   同一上下文 + 同一消息的重复请求得到相同动作与状态。
2. **动作**：0–4 条，每条 `{label, prompt}`（短按钮文案 + 完整发送文本）；有当前动作与
   组数进度、恢复日、无计划三种上下文各有不同动作集，均非空；上下文取不到时回落到通用
   四条。点击按钮发送 `prompt`，绝不发送空文本。
3. **教练状态**：`guide | count | rest | complete` 四态，缺省 `guide`；按「会话完成 / 最后
   一组 / 组间休息 / 进行中」确定性推导，模型自述不参与。每轮在收尾帧之前恰好下发一次
   `state` 与一次 `actions`（错误路径同样保证），中断路径仍不发终态帧。
4. **持久化与回放**：助手消息保存当时的动作快照与教练状态（迁移 0014，两列可空），历史
   接口原样返回；旧消息没有快照时返回空列表/null，前端不显示动作且不报错。
5. **非流式一致**：非流式 `/chat` 复用同一规划器，返回相同的动作列表（`quick_actions`，
   旧 `suggested_actions` 与之保持一致）与同一教练状态。
6. **前端**：每个助手消息下方渲染该轮服务端动作快照；没有快照的消息不显示按钮。四种状态
   映射到数字教练的可见文案（计组/休息/完成/引导）；工单 19 的错误提示与中断行为不变。
