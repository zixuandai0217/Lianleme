# 18 — 服务端快捷动作与教练状态

**What to build:** 快捷动作不再写死在前端页面里，而是由服务端按当前训练上下文生成随事件流下发：用户在练什么动作、做到第几组、今天是不是恢复日，决定他看到的四个按钮是什么。按钮文案短、点击后发送的文本完整，两者分开；取不到上下文时退回一组通用动作，按钮区永远不空，也不会点出无意义的空消息。

教练状态（引导 / 计组 / 休息 / 完成）同样由服务端按上下文确定性推导后随流下发，数字教练的呈现跟着变，不依赖模型自述——模型偶尔漏说状态不会让角色卡在错误表情上。动作与状态都进入持久化，重新进入页面时历史消息能带回当时的动作快照。

**Blocked by:** 17 陪练协议帧 + 服务端清洗 + 前端协议层

**Status:** ready-for-agent

- [ ] AC1：每轮对话在收尾帧之前下发一次快捷动作事件，含 0–4 条动作、每条带按钮文案与发送文本；点击按钮后作为用户消息发出的内容等于该动作的发送文本（缺省时等于按钮文案）。
- [ ] AC2：动作随上下文变化——有当前动作与组数进度时下发的动作集，与无今日训练上下文时下发的通用动作集不同；两种情况动作集均非空。
- [ ] AC3：相同训练上下文与相同用户消息重复请求，得到相同的动作列表与相同的教练状态（动作规划是确定性的，不随模型输出漂移）。
- [ ] AC4：教练状态事件取值限定在引导 / 计组 / 休息 / 完成四种之内，缺省为引导；状态变化在数字教练的呈现上可见（例如计组与休息的状态文案不同）。
- [ ] AC5：重新进入陪练页后，历史助手消息能带回当时的动作快照并可直接点击；快照缺失时该消息不显示动作且不报错。
- [ ] AC6：非流式对话接口返回的快捷动作与流式接口来自同一规划环节：同一上下文与消息下两处动作列表一致。
