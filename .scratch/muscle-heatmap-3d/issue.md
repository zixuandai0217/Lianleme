# Issue: 3D 肌肉热力图：从肌肉评分到可旋转人体的视觉映射

## Problem Statement

体型分析其实已经算出用户各部位的肌肉评分——0 到 10 分，胸部 7、核心 4、腿部 5 这样。但这些分数在页面上是一列进度条加"7/10"的文字，藏在"部位评分详情"这个可折叠面板里。用户要理解"我整体弱在哪"，得把十几行数字读完、在脑子里拼一遍；多数人扫两眼就滑走了。评分被算出来，又被藏在文字里，等于白算。

历史记录同样吃亏。用户隔两个月再做一次分析，前后两条记录只能对比数字：胸部 5 → 7、核心 4 → 4。数字差异是抽象的，"我这两个月到底变成了什么样"这个问题得不到回答。而这对健身用户恰恰是最重要的动机来源——进步要看得见，才有下一次。

视觉上也没有任何记忆点。一个健身应用把最关键的身体影像数据做成了一串进度条，用户没法把它讲给别人听、没法截图发出去、也没法在打开应用的第三秒被震住。对简历项目而言，这一块的缺失尤其明显：能力都在后端，前端没有把能力兑现成体验。

需要的是：把评分变成一具能转的人体——弱的部位暗淡、强的部位发光，用户一眼看到重点；把两次分析并排放在一起，让变化自己说话；并且在设备不行、模型加载失败、评分不全的时候，仍然退回今天这份"能读"的列表，而不是白屏。

## Solution

分析结果页加入 3D 肌肉热力图，历史记录区加一个对比视图：一具通用人体模型，12 个肌肉区域按评分渲染发光强度与色相——低分暗红近熄、高分亮黄炽热；用户可以拖动旋转、滚轮缩放，点某个部位看到它的分数与该部位的训练建议。

历史对比用两个并排的模型（同一次加载、同步旋转），并标注变化最大的部位：胸部 +2、核心 −1。默认对比最近两次分析，也可以任选两次。模型只在用户真正进入这段视图时才加载，文字结论先出、3D 后到，不阻塞用户读结果。

评分到视觉的映射是一层纯逻辑：分数怎么变颜色、怎么变亮度、缺项怎么表达、别名怎么归并、两次记录怎么算差异徽标——这些都能在没有浏览器的环境里被断言。渲染只负责把算好的参数贴到材质上。设备不支持 WebGL、模型加载失败、或某次分析根本没有部位评分时，自动退回今天的分数条列表，功能不丢。

## User Stories

1. 作为刚拿到分析结果的用户，我想要看到一具能转动的 3D 人体，以便我一眼看出哪块肌肉最弱、不用逐行读数字。
2. 作为视觉型用户，我想要评分高的部位发光明亮、低的部位暗淡，以便亮暗本身就能告诉我训练重点。
3. 作为做了两次分析的用户，我想要把两次结果并排看，以便我直观感受几周之间的形体变化。
4. 作为细节控用户，我想要点某个部位就看到它的分数和针对性建议，以便我不只得到一个颜色。
5. 作为用着旧设备的用户，我想要 3D 加载不了时自动退回分数列表，以便我仍然能把分析读完。
6. 作为弱网环境下的用户，我想要文字结论先出现、模型随后加载，以便我不必等模型才能知道结果。
7. 作为分析结果只覆盖部分部位的用户，我想要没被评估的部位被明确标注"未评估"而不是显示成 0 分，以便我不会误判自己哪里特别弱。
8. 作为想分享的用户，我想要把当前视角的模型截图保存，以便我发给朋友或者留在相册里做记录。
9. 作为偏爱数据的用户，我想要一键切回列表视图，以便我用熟悉的方式核对具体分数。
10. 作为使用键盘或读屏软件的用户，我想要不靠鼠标也能旋转模型并听到部位的分数描述，以便这个功能对我同样可用。
11. 作为训练了两个月回看的用户，我想要系统直接标出变化最大的部位，以便我知道哪部分训练最有效。
12. 作为等待页面加载的用户，我想要看到明确的加载中状态，以便我不会以为页面卡死。
13. 作为担心照片外泄的用户，我想要 3D 模型是一具通用人体而不是我的照片，以便我不必担心隐私。
14. 作为要维护这个页面的开发者，我想要肌肉区域命名与模型网格一一对应、模型体积有预算约束，以便将来替换模型时不用返工。
15. 作为移动端用户，我想要在小屏上模型不至于挤成一条缝、图例仍然可读，以便我在手机上也能用。

## Implementation Decisions

### 1. 技术选型与依赖边界

- 渲染用 Three.js，配 React Three Fiber 与 drei（来自 ADR-0005 的 `Canvas` / `OrbitControls` / `useGLTF` / `MeshStandardMaterial` 组合）。
- 当前前端依赖里没有 `three` 与任何 React Three Fiber 包，因此这是净新增依赖。新增必须收敛在热力图相关模块内：不许把 3D 库渗透进页面外壳、路由或数据层，页面其余部分不得为了 3D 而改技术栈。
- 3D 模块必须是可懒加载的独立单元：只有进入热力图视图才加载 3D 运行时与模型。分析结果页在 3D 不可用或尚未加载时，必须已经能用（文字结论与列表视图是主路径，3D 是增强）。

### 2. 模型资产契约

- 交付形态：单个 GLB（二进制 glTF，体积最小），随前端静态资源自托管、文件名带内容哈希、长缓存（ADR-0005 建议 CDN 加速，此处改为自托管 + 长缓存，见 Further Notes）。
- 模型包含 **12 个肌肉区域网格**，网格名称固定为：`chest`、`upper_back`、`lower_back`、`abs`、`traps`、`shoulders`、`arms`、`forearms`、`glutes`、`quads`、`hamstrings`、`calves`（区域清单来自 ADR-0005，命名在此定稿）。网格名是**唯一真源**：评分侧的区域键必须先归一到这 12 个名字，渲染侧只认这 12 个名字，不允许出现第二套命名。
- 资源预算：GLB 体积目标 1-2MB 上限硬约束（ADR-0005），首次加载目标 < 3 秒；贴图压缩、删除面部/手指等无关网格（ADR-0005 的精简策略）。预算必须可被自动化断言，而不是靠人工记。
- 许可证：仅接受可再分发的开源模型（CC-BY 一类），许可证与署名信息随资产清单一起保留并在页面可达位置展示；若最终找不到满足 12 区域切分的模型，回退到"基础几何体拼装"的自建简化人体（ADR-0005 的备选方案），此时区域命名契约不变。
- 模型与评分之间只通过"12 个区域名 → 视觉参数"这一层耦合；替换模型只要满足命名与体积契约，页面逻辑不需要改。

### 3. 数据来源与读取语义

- 唯一数据源：体型分析结果中的各部位肌肉评分（0-10），来自用户当前分析结果与历史分析记录；不使用进程内的任务缓存（它随进程消失，且不是长期事实）。
- 只读：本能力不新增任何后端写入路径，也不需要新的后端接口——历史记录接口已能返回每次分析的完整结果。
- 评分集合是**开放集合**：评分由多模态模型生成，键名不保证落在固定 12 项上（现状前端已有一张含 21 个标签的映射表，覆盖头、颈、斜方、背阔、三角、肱二/三头、前臂、腹、侧腹、核心、髋、臀、股四头、腘绳、小腿等）。因此"覆盖不全"是常态，不是异常，必须被当作第一种情况来设计。
- 某次分析完全没有部位评分时：不渲染模型，显示"这次分析没有部位评分"并提供列表视图，绝不渲染一具全灰模型让用户误解。

### 4. 评分 → 视觉参数的映射（核心契约）

分数到材质的两条通道沿用 ADR-0005：

- 发光强度 `emissiveIntensity = score / 10`（线性，0 → 全暗，10 → 最亮）。
- 色相 `hue = score / 10 * 60`（0=红，60=黄），饱和度 1、亮度 0.5，即 HSL(hue, 1, 0.5)。

在其上补齐 ADR 未定义的语义（本 spec 定稿，全部落在纯函数里）：

- **归一化**：源键 → 12 区域。一对一直接映射；多个源键落到同一区域时取算术平均（如核心/腹/侧腹 → `abs`）；成对区域（肩、臂、前臂、臀、大腿前后、小腿）若评分分左右两侧，取平均，并在差异 ≥3 分时于对比视图标注"单侧偏差"。无法归一的键不进入 3D，但**保留在列表视图**（不丢用户数据）。
- **缺失语义**：未映射到的区域渲染为"未评估"——不发光的中性灰（强度取一个极低常量），并在图例中单列"未评估"。**绝不把缺失当作 0 分**，也不参与任何平均值计算。
- **非法输入**：非数值、NaN、超出 0-10 的分数一律钳制到合法区间；整条记录不可用时返回空映射并置降级标记。纯函数不做任何 I/O，也不抛异常。
- **对比差异**：两次记录的同一区域差值取绝对值 ≥2 时才生成变化徽标（避免把评分噪声当进步），差值同时带符号与颜色（升/降/持平中性）。
- **集合级派生**：给定两组评分，输出"变化最大 top-N 区域"供对比视图直接标注；输出图例条目（12 个区域各自的档位名/色值/是否未评估），供列表视图与 3D 视图共用同一套文案。

### 5. 渲染与交互约定

- 相机与控件：OrbitControls，限制最近/最远距离与俯仰角上下限，防止用户把镜头转到模型"体内"或仰视到地下；初始视角为正面略微俯视（ADR-0005 的相机位置作为起点）。
- 场景最简：环境光 + 一盏方向光，不使用阴影、后处理、物理与动画，除非它们不增加依赖与包体积。
- 点击区域 → 高亮描边 + 侧栏显示区域名、分数档位、以及该部位是否为该次分析的弱势肌群（数据来自同一次分析结果）；点击空白取消选中。
- 对比视图：同一 GLB 只下载一次，渲染两个实例；两台相机**同步旋转**（便于目视对齐），并排布局在窄屏下改为上下堆叠；变化徽标浮在被标注区域附近。
- 图例固定展示 0-10 的色带（红→黄）、"未评估"灰色条目，以及"发光越亮 = 评分越高"的一句话说明。
- 无障碍：可用键盘旋转（方向键）与缩放（+/-）；提供 aria 描述文本（"胸部 7 分，背部 6 分，核心未评估…"）；列表视图是完整等价物，3D 不可用或用户偏好时可持久切换到列表。

### 6. 加载、降级与错误

按顺序判定，逐级退让：

1. **能力探测失败**（无 WebGL、WebGL2 不可用、上下文创建失败）→ 不下载 3D 运行时与模型，直接呈现列表视图 + 一行说明。
2. **模型加载失败或超时**（网络错误、解析失败、超过加载窗口）→ 呈现列表视图 + "3D 视图暂不可用"提示 + 重试按钮（重试是显式动作，不自动循环）。
3. **运行时上下文丢失**（标签页切后台、GPU 重置）→ 保留已算好的视觉参数，提示后可重试挂载；不得让整个分析页崩掉。
4. **低端设备**（无法维持可接受帧率）→ 降低渲染分辨率上限、关闭抗锯齿；仍不达标则建议切列表视图，但不强制。
5. 加载期间显示骨架/进度占位，且**不阻塞**文字结论与分数列表的呈现。

任何降级都不得产生"看起来像 0 分"的视觉效果——降级要么不渲染模型，要么明确标注不可用。

### 7. 性能与成本边界

- 单页最多两个模型实例（当前 vs 对比），不允许为每次历史记录各建一个场景。
- 初始包体积：3D 运行时与模型都不进首屏块；热力图模块为独立分包，进入视图才取。
- 渲染循环为空闲即停（无交互时降低刷新），避免后台标签页持续占 GPU。
- 不做 3D 运行时截图以外的任何网络请求；截图在本地生成（canvas → 图片），不经过服务端。

### 8. 隐私边界

- 3D 模型是**通用人体**，不含用户照片、体型参数或任何可识别身份的信息（ADR-0005 已明确否决"在用户照片上叠加热力图"的方案）。
- 肌肉评分是健康相关数据，只在本会话内用于渲染，不发给任何第三方渲染服务；截图只在用户设备上生成与保存。
- 不新增任何数据留存：热力图是纯展示层，评分仍由既有分析记录承载，删除分析记录即失去热力图数据。

### 9. 与其它能力的边界

- 不消费姿态关键点、不做"错误动作部位高亮"（ADR-0005 把它列为后续可扩展项，此处不做）。
- 不做 AI 8 周体型预测（ADR-0005 的 MVP 明确排除）。对比只用真实存在的两次历史分析。
- 不改变分析的评分口径与 Prompt；如果评分键集合变化，是归一化层适配，不是本能力反向约束模型输出。

## Testing Decisions

### 好测试的标准

只断言"用户会看到的视觉决定"，不断言像素与渲染过程：给定一组织评分，应当得到什么发光强度、什么色相、哪些区域被标为未评估、哪些差异该出徽标、整体是否该降级。这些参数是渲染层的唯一输入，断言它们等价于断言"亮暗是否正确"，且不会因为换渲染库、换模型文件、或给材质加一个属性而失效。

### 最高 seam：纯 TypeScript 映射层

把"评分集合 → 视觉参数"整条链路做成无依赖的纯函数模块（不 import Three.js、不碰 DOM），直接单测：

1. 单区域：评分 0/5/10 → 强度 0/0.5/1、色相 0/30/60；
2. 归一化：别名（核心/腹/侧腹）归并到 `abs`、成对区域的均值、无法识别的键被保留到列表而不进 3D；
3. 缺失：未评估区域产出中性低强度 + "未评估"图例项，且不参与任何平均；
4. 非法输入：`-3`、`11`、`NaN`、`"7"`、`null` 被钳制或忽略且不抛；
5. 对比：两次记录的差值、|Δ| ≥2 才出徽标、变化 top-N 的排序；
6. 降级决策：无评分 / 能力探测失败 / 加载失败三种输入分别得到"列表视图 + 对应提示"的状态描述。

### 为什么不需要更低的 seam

再往下就是 Three.js 的材质对象与 GLTF 解析器：断言它们的内部行为等于给第三方库版本上锁，而这一层本身没有我们的业务决策。我们的决策全部集中在"分数怎么变成参数"与"缺什么怎么表达"上，已经被纯函数 seam 完整覆盖。

渲染层只做冒烟，且刻意不引入 WebGL mock 栈：

- 模块可被导入、组件在无 WebGL 环境下挂载不抛错并落到降级分支；
- 改变评分后组件不崩（用替身的渲染器或直接调用导出的映射函数断言其被采用）。

理由：在 jsdom 里伪造 WebGL 上下文会引入一整套脆弱 test-only 设施，维护成本高于它能提供的信心；渲染正确性的真实验证靠人工目视 + 截图存档。

### 资产预算检查（唯一允许下探到文件层的地方）

用 Node 侧测试断言模型资产满足契约：文件存在、体积在预算内、网格名称集合与 12 区域命名一致（解析 GLB 的 JSON chunk 或维护一份与模型同源更新的资产清单）。这是构建期事实而非运行时行为，所以值得下探——ADR-0005 把"模型体积 1-2MB / 首次加载 < 3s"写成了硬约束，靠人工记必然漂移。prior art 见下。

### 被测模块

1. 评分归一化与区域映射（含别名、成对、未知键）
2. 评分 → 材质参数（强度、色相、档位、图例项）
3. 对比差异（Δ、徽标阈值、变化 top-N）
4. 降级状态推导（能力探测 / 加载失败 / 无评分）
5. 资产预算检查（体积、网格命名）

### 必测行为清单

- 评分 0 → 强度 0、色相 0（暗红近熄）；评分 10 → 强度 1、色相 60（亮黄）。
- 中间值单调：分数升高，强度与色相都不回退（无跳变、无倒挂）。
- 越界与脏数据（负数、>10、NaN、字符串、null）被钳制或忽略，函数不抛异常，不产生"负发光"。
- 别名键（核心/腹/侧腹）归并到 `abs` 区域并取平均；归并结果与直接给 `abs` 一致。
- 未映射键（如 `head`、`neck`）不进入 3D 参数集合，但仍出现在列表视图的数据里。
- 缺失区域得到"未评估"中性参数，且不拉低其它区域；整条记录为空时降级为列表视图。
- 成对区域左右分侧时取平均；左右差 ≥3 分时对比视图产出"单侧偏差"标注。
- 两次记录 Δ=1 不产生徽标，Δ=2 与 Δ=−2 产生徽标且方向正确；变化 top-N 按 |Δ| 降序。
- 同一区域两次都未评估 → 不产生徽标（不能把"两个未知"算成变化）。
- 能力探测失败 → 返回"列表视图 + 不计为错误"的降级状态。
- 模型加载超时 → 返回"列表视图 + 可重试"的降级状态。
- 模型资产：文件存在、体积 ≤ 预算、网格名集合恰好覆盖 12 个约定名（多一个少一个都失败）。

### 仓库内 prior art

- `web/src/components/coach-lip-sync.ts` 与 `web/src/coach-lip-sync.test.ts`：把"时间/能量 → 视觉状态"的映射抽成纯函数直接单测（`visemeAtTime`、`fallbackVisemeFromEnergy`、非法输入防御），并有 `CoachVisemeClock` 这类纯状态机；肌肉评分 → 材质参数应当完全照此组织。
- `web/src/coach-lip-sync.test.ts`、`web/src/coach-2d-runtime.test.ts`：用 `node:fs` 断言静态资源存在与体积预算，正是"GLB 体积 + 网格命名"检查的模板。
- `web/src/pages/analysis/flow.ts` 与 `web/src/pages/analysis/flow.test.ts`：把页面级状态收敛成"输入布尔量 → 视图模型"的纯函数再单测，适用于"降级状态推导"（能力/加载/无评分 → 该显示哪个视图）。
- `web/src/digital-coach.test.ts`、`web/src/coach-2d-runtime.test.ts`：重渲染组件只做"模块可加载 + 不抛错"的冒烟，与本节主张一致。

## Out of Scope

- AI 预测 8 周后的体型（ADR-0005 的 MVP 排除项）；对比只用真实历史记录。
- 把姿态检测数据叠加到 3D 模型上（ADR-0005 列为后续）。
- 肌肉收缩等动画、物理、后处理（bloom 等发光后处理需额外依赖，本 spec 不允许）。
- 2D SVG 人体轮廓与照片热力图（ADR-0005 已否决的备选方案）。
- 购买商业模型（ADR-0005 已否决）。
- 移动端 App 与平板横屏专项适配；移动端仅要求"能用、不挤"。
- 后端新增接口、评分口径调整、分析 Prompt 改动。
- 社交分享/外链生成（截图保存在本地即可，不做服务端分享页）。
- 历史时间线/趋势图等其它分析资产化形态。

## Further Notes

- **ADR 未定，此处决策**：12 个肌肉区域的**英文网格名**（ADR-0005 只给了中文区域清单与"按约定命名"的示意）。命名在此定稿，并成为评分归一化与资产检查的共同真源，避免"模型叫 pectoralis、代码找 chest"的老问题（ADR-0005 权衡第 4 条已经预警）。
- **ADR 未定，此处决策**：缺失评分的语义是"未评估中性灰 + 图例单列"，不是 0 分。理由：0 分在语义上是"极弱"，把"模型没提到"渲染成"极弱"会直接误导训练决策。
- **ADR 未定，此处决策**：模型资源自托管 + 内容哈希长缓存，而非 ADR 建议的 CDN 加速。理由是隐私（不向第三方暴露资产加载）、离线开发一致性、以及部署只有单前端产物这一个事实；CDN 留作后续性能优化，不改变前端契约。
- **ADR 未定，此处决策**：变化徽标的阈值 |Δ| ≥2。依据是 ADR-0005 自己给 AI 预测设的"8 周最多提升 2 分"量级——两次真实分析之间 1 分以内的差异更可能是评分噪声。
- **ADR 未定，此处决策**：对比视图两台相机同步旋转、同一 GLB 单次下载双实例化。ADR 只说"并排显示两个 3D 模型"，没说不许同步；但不同步的并排对比基本没法用。
- **ADR 未定，此处决策**：降级判定的具体触发条件（能力探测、加载超时窗口、上下文丢失事件）与"降级不得产生像 0 分的视觉"。ADR 只提到"移动端性能可能较差，暂不支持"，没有定义降级形态。
- **现状风险（与 ADR 假设不符）**：ADR-0005 假设评分恰好覆盖 12 个肌肉区域，但现状 `muscle_scores` 是自由字典，前端已经为此维护了 21 个标签的映射表（含头、颈、斜方、背阔、三角肌等不在 12 区域内的键）。也就是说"12 区域全覆盖"从来不是现实，归一化层与"未评估"语义必须按常态设计。若要让覆盖率稳定，需要改分析 Prompt 让模型按固定区域输出——这属于分析域，本 spec 不越界，只做适配。
- **现状风险**：评分键名是中文/英文混杂（模型按提示自由生成，前端映射表里是英文键、页面显示中文标签）。归一化必须同时接受中英文别名，否则同一个部位在不同分析里会落到不同区域。
- **依赖成本提醒**：新增 Three.js + React Three Fiber + drei 会显著改变前端依赖面；drei 的 `useGLTF` 会带来 loader 依赖。若包体积不可接受，退化路径是自己用 Three.js 原生 loader 组织场景（放弃 drei），映射与契约层不受影响。
- **跨 spec 边界**：本 spec 只谈"模型资源与评分→材质映射"；姿态采集与周期切分见姿态纠错 spec，多路评估与计划调整见计划调整 spec。三者唯一的交汇点是"伤病/训练建议文案如何复用评分"，属于展示文案层面，不构成依赖。
