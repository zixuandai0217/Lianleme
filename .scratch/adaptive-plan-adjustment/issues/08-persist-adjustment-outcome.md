# 08 — 调整结论落盘最小契约

**What to build:** 用户打卡后，系统对下周计划的调整不再只是一次静默的计划覆盖：这次「往哪个方向动、动了多少、为什么」会被留住，并且后端能稳定读出来，供计划解释与打卡反馈直接引用。今天 AdjustGraph 已经算出方向与一句人话理由，但出口只把改完的动作列表写回计划，方向和理由被丢弃，于是「计划有没有被调整过、凭什么调整」无法从数据回答。本票不改判定规则，只把已有结论变成对下游可读的事实。

存储形态固定为**独立「调整结论」记录**：一次调整一条、带稳定标识，计划侧只保存「最近一次结论」的引用，不复制理由文本（Lead 裁决，作为 08 与 20 / 21 / 28 的边界）。

**Blocked by:** 06 迁移基线对齐与一致性测试

**Status:** ready-for-agent

- [ ] AC1：打卡触发一次调整后，后端可读到一条调整结论，含方向（`increase | decrease | keep`）、含触发数值的用户可读理由、触发时的完成率、发生时间、被调整的计划标识；读取不依赖任何页面或展示组件。
- [ ] AC2：没有调整记录的既有计划，读取返回明确空态，且该空态与「方向为 keep」可区分（不返回 404 歧义、不返回伪造默认值）。
- [ ] AC3：同一计划发生多次调整时，下游能取到与「本次」对应的那一条结论，不会因为后一次覆盖而无法判断方向与理由属于哪次调整。
- [ ] AC4：结论写入失败时打卡仍然成功（打卡响应 200 且打卡记录可见），失败以稳定分类可观测，不把内部异常抛给用户。
- [ ] AC5：新存储位按 06 的迁移约定落地，按 ORM 建表与按迁移升级两条路径的表/列一致，相关测试全绿。
