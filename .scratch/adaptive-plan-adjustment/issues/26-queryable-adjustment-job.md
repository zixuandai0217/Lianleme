# 26 — 可查询调整作业 + pending / detail

**What to build:** 打卡后触发的调整从「看不见的后台动作」变成一张可查询的作业：有稳定标识和状态（评估中 / 待你决定 / 已应用 / 超时未选择 / 失败），用户之后回到计划页能看到这次调整的五维小结、合并分、决策方向与计划前后差异。投递即返回、绝不等待评估完成，打卡与评估是两件独立的事实。

**Blocked by:** 11 DB 驱动执行器；24 Analyzer 抽象 + 三路规则 + Merge Node

**Status:** ready-for-agent

- [ ] AC1：打卡投递调整后产生一条持久作业，含稳定标识与状态（`evaluating | pending_choice | applied | expired_no_choice | failed` 之一）；打卡响应 200 且不等待评估完成，响应里带作业标识或明确的「未创建」原因。
- [ ] AC2：详情读取返回作业状态、五维小结（每维评分/理由/建议/降级标记）、合并结果（整体分、风险信号、顶层理由）、决策（方向、幅度、动作替换或休息日变更）、计划前后差异摘要。
- [ ] AC3：待确认列表只返当前用户未决作业并含 interrupt 载荷；无未决时返回 200 空列表而非 404；已完成作业可重复读取同一结果且读取不改写作业。
- [ ] AC4：权限与识别语义：他人作业 403 且不泄漏内容；不存在的标识 404 且错误码稳定；可跨进程重启查询——丢弃内存态后仅凭数据库仍能读到同一作业与状态。
- [ ] AC5：状态是可投影事实：`applied` 的作业能给出「是否已落地」与落地时间；`failed` 的作业给出稳定失败分类，不伪装成 `applied`。
