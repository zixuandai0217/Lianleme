# 02 — CI 三阶段编排与失败阻断

**What to build:** 把本地质量门接到 CI 上，让「是否通过」变成 PR 上看得见的结论，而不是口头承诺。阶段 A 并行跑五个必需检查（前端类型检查、前端 lint、前端单元测试、后端静态检查、后端单元测试）；阶段 B 在 A 全绿后跑主链路 smoke 与构建自检；阶段 C 跑报告制检查（后端类型检查报告、资源校验），不参与结论。

结果必须是硬的：任一必需步骤失败，整个运行标记失败，且该运行是合并的必需检查——门红了就合不进去。同时要保证这道门不会「看起来在跑其实没跑」：门入口声明的必需步骤集合与 CI 的必需检查集合必须一致，任一侧多出或缺少都要能被发现。

**Blocked by:** 01 质量门入口（前后端质量命令 + 修跨平台用例）

**Status:** ready-for-agent

- [x] AC1：向分支推送或开 PR 时自动触发：阶段 A 的五个必需检查并行执行，阶段 B 仅在阶段 A 全绿后执行，阶段 C 的结果不影响整体结论。
- [x] AC2：故意让任一必需步骤失败（临时制造类型错误、lint 违规、单元断言失败或 smoke 断言失败）时，整体运行显示失败，且该运行作为必需检查挡住合并——PR 无法在它未通过的情况下合入。
- [x] AC3：同一分支的新提交会取消该分支上一次未完成的运行，旧运行的结论不会覆盖新结论。
- [x] AC4：依赖按锁文件安装并使用缓存；锁文件缺失或依赖安装失败时运行直接失败，而不是降级为跳过或成功。
- [x] AC5：门入口声明的必需步骤集合与 CI 的必需检查集合一一对应：在门里新增一步而 CI 未同步（或反之）时，出现可发现的不一致失败/校验报警，而不是静默少跑一项。
- [x] AC6：主链路 smoke 在没有任何模型密钥、没有对象存储的环境下稳定通过；把其中任一外部替身改为返回错误时，smoke 变红——证明它不是空跑。
