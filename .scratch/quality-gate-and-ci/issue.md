# Issue: 工程质量达标（最小上线质量门、主链路 smoke、基础 CI）

## Problem Statement

这个项目现在「能不能上线」靠人肉判断。改完代码要不要跑类型检查、跑哪个 lint、后端测试怎么起、结果算不算过，全靠开发者记性和自觉；评审者看到的只是一个「我本地跑过了」的口头结论，没有任何可核对的凭据。于是同一处回归会被不同的人在不同的时间各踩一遍。

更麻烦的是「绿色的可信度」也不成立。一部分测试依赖外部二进制、外部服务或真实模型密钥：环境齐全时会跑，环境不齐全时可能静默跳过，也可能因为写法只对某个操作系统成立而失败。于是「通过」既可能是真的没问题，也可能只是这一轮什么都没跑；「失败」也可能只是这台机器的路径分隔符和写测试时假设的不一样。没人能分辨。

文档里的基线也没在跟进。规划里写着前端 lint 有 7 个错误、后端 0 个测试，而实际仓库已经修完 lint、后端也有了几十个用例和多个测试文件——这不该被解释成「文档写得早」，它说明当前缺少一个每次都重新回答「现在到底达标没有」的机制，所以任何关于工程质量的结论都会过期。

对一份要拿出去作为作品集的项目来说，这还有一层隐性成本：别人（包括自动化协作者）接手时，无法从仓库本身得知「怎样才算改对了」，只能反复追问或凭猜测。上线质量门要解决的就是这件事——把「达标」变成一条命令、一份结果、一道会挡住合并的检查。

## Solution

先立一条能自证的底线，而不是一次补齐所有工程质量话题。

定义一组固定步骤作为质量门：前端类型检查、前端 lint、前端单元测试、后端单元测试，再加上一条覆盖主链路（登录 → 档案 → 体型分析 → 计划生成 → 今日训练 → 打卡 → 陪练）的 smoke 测试。这些步骤只有一个入口、一组命令，本地跑和 CI 跑的是同一份，不允许出现「本地这样跑、CI 那样跑」的第二套逻辑。

门失败的语义要明确：任何必需步骤非零退出就让整体失败，失败就阻断合并；跳过必须是显式的、被列出来的，不能被当作通过；不允许用「忽略退出码」或「失败后自动重试」把红变绿。需要外部环境的东西一律在应用边界被替换掉，因此 CI 不需要模型密钥、不需要对象存储，也不会因为外部服务抖动而红。

门本身也要被验证。做法是「故意违规」：用一次性改动分别制造类型错误、lint 违规、单元断言失败、smoke 断言失败，确认对应步骤会红并挡住合并；同时保证门脚本声明的步骤与 CI 实际执行的必需检查一一对应，防止「配置写了但没跑」。这样「门是开着的」这件事本身有证据，而不是看起来配好了。

最后把「当前基线」从手写结论改成门的输出：文档不再维护容易过期的数字，而是指向最近一次运行结果。

## User Stories

1. 作为贡献者，我想要一条命令在本地跑完全部必需检查，以便提交前就知道会不会被挡住。
2. 作为贡献者，我想要本地门与 CI 执行同一组命令，以便不会出现「本地绿了 CI 红」。
3. 作为贡献者，我想要每个失败步骤给出可定位的输出（文件位置、规则名或失败断言），以便一次修完而不是反复试。
4. 作为贡献者，我想要门能在干净环境里复现（只靠锁文件安装依赖），以便结果不受我这台机器历史状态影响。
5. 作为评审者，我想要在 PR 上直接看到必需检查的结果，以便不必在本地重跑就能信任一次改动。
6. 作为评审者，我想要必需检查未通过时无法合并，以便「看起来没问题」不会变成「合进去才发现」。
7. 作为评审者，我想要测试跳过时在结果里显式列出并附原因，以便「跳过」不会被误读成「通过」。
8. 作为维护者，我想要前端 lint 与类型检查由 CI 持续强制，以便规则不会再次逐步回退。
9. 作为维护者，我想要后端测试覆盖鉴权、分析任务状态流转、计划生成兜底、打卡与体重记录，以便重构有回归保护。
10. 作为维护者，我想要一条主链路 smoke 覆盖从登录到陪练的完整旅程，以便「整体还能用」这件事每次都有证据。
11. 作为维护者，我想要 smoke 与单元测试都不依赖真实模型密钥与对象存储，以便 CI 不需要密钥、也不因外部服务抖动而红。
12. 作为维护者，我想要在 Windows 与 Linux 上得到一致结论，以便本地开发环境不会成为免检区。
13. 作为维护者，我想要质量门用「故意制造违规」验证过一次会红，以便不会出现配置写完却根本没生效的空门。
14. 作为维护者，我想要门脚本声明的步骤清单与 CI 的必需检查清单保持一致，以便新增检查不会被漏跑。
15. 作为维护者，我想要不稳定用例必须带原因与到期日登记，以便 flake 不靠复跑掩盖、也不会永久存在。
16. 作为维护者，我想要文档里的「当前基线」引用门的结果而不是手写数字，以便规划不再建立在过期结论上。
17. 作为新加入的协作者（含自动化 agent），我想要文档指明唯一入口命令与失败含义，以便不必追问「这个项目怎么验证」。

## Implementation Decisions

### 1. 质量门的组成

必需步骤（缺一即不算达标）：

| 步骤 | 判据 | 说明 |
| --- | --- | --- |
| 前端类型检查 | 无类型错误 | 以项目现有 TypeScript 配置为准，不额外放宽 |
| 前端 lint | 零错误 | 全仓扫描，不按目录豁免；告警不阻断但计入摘要 |
| 前端单元测试 | 全绿、非 watch 模式单次运行 | 必须显式跑一次退出，不允许停在监听态 |
| 后端单元测试 | 全绿 | 需要外部二进制的用例按第 5 节显式跳过 |
| 主链路 smoke | 全绿 | 定义见第 6 节 |

附加步骤：后端静态检查（ruff 规则集）本期纳入必需；类型检查（mypy）本期为报告制（不阻断），因其未参与门禁，注解缺失会一次性产生大量噪声；升级条件明确写死——报告条目归零后转为必需。资源校验脚本与「应用可构建/可导入」作为报告制步骤，稳定后再升必需。

理由：门要能长期站住，就必须从「当前真的能全绿」的集合起步，同时把升级路径写清楚，避免「临时放宽」变成永久缺口。

### 2. 单一入口

- 提供一份「质量门」定义：步骤名、命令、是否必需、超时上限。本地与 CI 都只调用它，CI 不做第二套命令拼装。
- 提供两个档位：快速档（静态检查 + 单元测试，供提交前使用）与完整档（快速档 + smoke + 构建/导入自检，供合并前与 CI 使用）。两档共用同一步骤定义，只是选择子集。
- 步骤输出结构化摘要：步骤名、命令、退出码、耗时、跳过数、失败摘要首行。人读与机器读同一份。
- 整体退出码 = 必需步骤的聚合（任一失败即非零）。禁止用「忽略退出码」「失败继续」「自动重试」等手段让必需步骤变绿。

### 3. CI 阶段划分

- 阶段 A（并行、无外部依赖、目标总时长五分钟量级）：前端类型检查、前端 lint、前端单元测试、后端静态检查、后端单元测试。
- 阶段 B（依赖 A 全绿）：主链路 smoke、应用可构建/可导入自检。
- 阶段 C（不阻断）：后端类型检查报告、资源校验。
- 触发：拉取请求（草稿状态只跑阶段 A 以加快反馈；转为可评审后跑全量）、推送到主分支、手动触发。
- 并发：同一分支/PR 的新提交取消旧运行，避免旧结果覆盖新结论。
- 缓存：前端依赖与后端依赖分开缓存，缓存键包含锁文件哈希；不使用跨分支共享的可写缓存。
- 工具链版本固定：前端 Node 单一 LTS 主版本、后端单一 Python 版本（与项目声明的最低版本一致的方向选一档），不做多版本矩阵——本期目标是「有一道可信的门」，不是兼容性调查。
- 必需状态检查：阶段 A 的五个步骤与阶段 B 的 smoke 作为合并前必需检查；阶段 C 不设必需。

### 4. 失败与阻断语义

- 必需步骤失败 → 整体失败 → 合并被阻断；合并前不允许「管理员绕过」作为常规路径（紧急绕过需留记录）。
- 不稳定用例：不允许靠重跑掩盖。隔离需三件套——显式标记、原因说明、到期日（量级：一周）；到期未修复则视为失败。隔离清单本身在门里可见。
- 跳过语义：因缺少外部依赖而跳过，必须附原因并在摘要里单列；无原因跳过视为失败。
- 静默失败禁止：任何「命令不存在」「依赖没装好」「配置读不到」都必须报错，不允许降级为跳过或成功。

### 5. 平台与可移植性策略

- CI 权威环境为单一 Linux 发行版；测试套件必须在 Windows 与 Linux 上同时通过，平台差异断言按缺陷处理，不按环境差异豁免。
- 路径分隔符、换行符、编码、时区、大小写敏感性相关的断言视为可移植性缺陷；需要平台条件分支时，用显式的平台判定并说明理由，而不是让断言在某个平台必然失败。
- 需要外部二进制的用例（例如唇形同步依赖的第三方工具）在缺失时显式跳过，附原因；安装了该二进制的环境必须真的执行并断言，不允许「检测到就跳过」。
- 不引入多操作系统矩阵作为门；跨平台一致性靠断言可移植性保证，而不是靠跑更多机器。

### 6. 主链路 smoke 的定义

- 一条端到端旅程，按用户视角串联：登录 → 档案写入/读取 → 体型分析（VisionGraph 以替身替代多模态调用）→ 计划生成（同时覆盖「无分析结果时仍能生成」的兜底路径）→ 今日训练读取 → 打卡 → 陪练（一次非流式回复 + 一次流式对话的帧契约冒烟）。
- 每一步断言「响应可解析 + 关键字段存在 + 状态推进到下一步」，并至少包含一条负向断言（未认证或跨用户访问被拒），证明鉴权没有被 smoke 顺手绕过。
- 全部外部边界（LLM、多模态、对象存储、语音）在应用边界替换为替身；数据库使用一次性隔离实例；测试不依赖应用启动期的对象存储初始化（应用生命周期钩子中的外部依赖初始化必须可被跳过或替换，否则 smoke 会在 CI 里卡住）。
- smoke 的定位是「整体还能走通」，不是覆盖率工具，也不替代单元测试。

### 7. 质量门自身的可验证性

门必须能证明「它真的会红」。三件事：

1. 负向金丝雀（一次性、人工执行，改动门或新增门时必做）：分别制造类型错误、lint 违规、单元断言失败、smoke 断言失败，确认对应步骤变红、整体退出码非零、PR 上呈现红色且合并被阻断；四个场景各一次，结果记在门的变更说明里。
2. 清单一致性自检（自动、轻量）：门脚本声明的必需步骤集合必须与 CI 的必需检查集合一致，缺一即失败；新增检查只改一处会被立刻发现。
3. 确定性验证（自动、随门运行）：在无模型密钥、无外部存储的环境下 smoke 与单元测试必须稳定通过；再把某个替身改为返回错误，smoke 必须失败——证明断言不是空跑。

另外两条硬要求：质量门入口在全部步骤通过时返回零且跳过清单符合预期（防止假绿）；依赖安装失败、锁文件缺失、命令不存在时必须报错（防止空转）。

### 8. 基线的事实来源

- 文档不再手写「当前 lint 有几个错、pytest 有几个测试」这类会过期的结论，改为引用最近一次门的运行摘要；如需在文档里出现数字，必须标注采集方式与时间。
- 门的摘要保留最近若干次运行结果，便于回答「这条回归是什么时候进来的」。

### 9. 覆盖率与门禁的取舍

本期不设覆盖率阈值。理由是当前缺口是「没有门」而不是「覆盖不够」，覆盖率数字在没有稳定基线时更容易被凑而不是被改善；用「必测行为清单 + 主链路 smoke + 必需检查」替代，待门稳定后再单独讨论阈值。

## Testing Decisions

本节只讨论「质量门本身如何被验证」；应用侧各模块的测试策略由各自的 spec 决定（陪练事件流契约见 coach-stream-protocol，其余见对应功能 spec），这里只规定它们必须进入门。

### 好测试的标准（针对门）

只断言门的可观测结果：步骤是否执行、退出码、摘要里的步骤名与跳过清单、必需检查是否阻断、清单一致性。不为 lint 规则、类型检查规则、CI 配置文件的内部结构写测试——那些由工具与平台拥有；也不断言命令输出全文，只断言「哪一步失败了、失败摘要里有可定位线索」。

### 最高 seam：质量门入口 + CI 编排层

在真实环境里跑真实命令，断言三件外部事实：

- 全部通过时整体退出码为零，摘要包含全部必需步骤且无未登记跳过；
- 任一必需步骤失败时整体退出码非零，失败步骤在摘要中可定位；
- CI 的必需检查集合与门脚本的必需步骤集合一致（清单级断言）。

为什么不需要更低的 seam：门的行为完全体现在「命令序列 + 退出码 + 阻断」这三件事上，再往下就是各工具的规则实现与 YAML 的语法细节，测它们只会锁死配置写法，无法回答「门是否真的挡住了坏改动」。真正的风险不在实现细节，而在「以为在跑其实没跑」「跑了但红不了」，这两个风险只能在这一层被证明。

### 门自身的四类验证

1. **会红**：故意制造类型错误 / lint 违规 / 单元断言失败 / smoke 断言失败，四类各自让对应步骤失败并阻断；每类只验证一次，作为门变更时的验收动作。
2. **不会假绿**：全绿运行时退出码为零且跳过清单为空或只含已登记项；缺少密钥的环境下 smoke 仍通过（证明不依赖外部），而把替身改成错误时 smoke 变红（证明断言有效）。
3. **不会漏跑**：清单一致性自检——门脚本必需步骤集合与 CI 必需检查集合相等，任一侧多出或缺少都失败。
4. **不会空转**：删除/篡改锁文件、让依赖无法安装时，门必须报错而不是跳过或成功。

### 被测模块

1. 质量门入口（步骤定义、档位选择、聚合退出码、摘要输出）
2. CI 编排（阶段划分、触发、并发取消、缓存、必需检查集合）
3. 主链路 smoke（旅程断言与替身替换）
4. 跨平台可移植性约束（跳过登记与到期机制）

### 必测行为清单（进入门）

- 鉴权与越权：未认证被拒、跨用户访问被拒、管理员路由的权限边界。
- 分析任务状态流转：创建 → 处理中 → 成功/失败，失败可追踪。
- 计划生成兜底：缺少分析结果时仍返回可用的今日训练。
- 打卡：完成一次训练后记录与统计可读。
- 体重记录：新增、趋势读取、删除。
- 陪练输出契约：按 coach-stream-protocol 定义的帧契约与清洗行为。
- 各步骤在故意违规下确实失败（门自检）。

### 仓库内 prior art

- 后端路由层测试骨架：应用客户端 + 隔离数据库 + 依赖替换的既有写法，可直接用于 smoke 的替身装配。
- 陪练流式失败的回归测试：把「上游失败」替换成替身后断言对外契约的方式，是 smoke 中失败路径断言的模板。
- 前端纯函数测试与页面级 jsdom 测试：纯逻辑走单测、接线走轻量渲染测试的既有分工。
- 仓库内已有的一次性脚本（例如教练资源校验脚本）是把「检查」封装成可重复步骤的现成模式，可作为门步骤的写法参照。

## Out of Scope

- 部署与持续交付流水线（发布、回滚、环境晋级）。
- 浏览器端到端测试（真实浏览器驱动的用户旅程）。
- 性能、压测与容量基线。
- 覆盖率阈值与覆盖率趋势。
- 依赖漏洞扫描、静态安全分析、密钥扫描。
- 多操作系统/多语言版本矩阵。
- 分支保护规则的具体平台配置落地（本 spec 只写要求，不写平台操作步骤）。
- 把既有测试套件整体重写或补全到某个数量目标。

动手前实测的当前状态（用于划定起点，不作为验收目标）：

- 后端：89 条通过、1 条失败。失败用例与本 spec 直接相关——它把 POSIX 风格路径写死为期望值，在 Windows 下 `Path` 会给出反斜杠形式，于是断言必然失败而代码本身没有问题。也就是说「后端全绿」这一步目前并不成立，门的第一个动作必须是让这条断言跨平台，而不是把它加进跳过清单。
- 仓库没有 CI 配置目录，也没有 pytest 的集中配置文件（测试靠显式异步标记驱动）、没有声明 Node 引擎版本；本地实际为 Node 24、Python 3.12，而项目声明的最低 Python 版本是 3.11，说明工具链版本需要被门固定下来，否则「本地通过」的含义会漂移。
- 后端有 uv 锁文件、前端是 npm 锁文件：缓存键与安装命令按此确定，不混用包管理器。
- 后端测试在应用客户端直连时不触发应用生命周期钩子，因此对象存储初始化不会被真实调用——smoke 必须显式依赖或显式替换这一点，否则 CI 会卡在对外部存储的等待上。

未向 Lead 确认、按现状做出的决策（记录于此）：

- 后端类型检查（mypy）本期只报告不阻断，并把「报告归零后转必需」写死在门定义里，避免口头承诺。
- 后端静态检查（ruff）本期直接纳入必需，因为当前规则集小、噪声可控。
- CI 只跑单一 Linux 环境，不做 OS 矩阵；跨平台一致性靠断言可移植性保证。若后续要求 Windows 也进门，应作为独立议题，而不是把当前唯一失败用例改成跳过。
- 本期不设覆盖率阈值（理由见 Implementation Decisions 第 9 节）。
- 门的「会红」验证是一次性人工动作，不纳入每次运行（让 CI 每次自我破坏既慢又容易产生假失败）；但清单一致性自检与确定性验证是每次运行都做的。
