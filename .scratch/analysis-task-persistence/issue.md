# Issue: 体型分析任务持久化与可恢复执行

## Problem Statement

用户点「开始分析」，把一张全身照交出去，等一份体脂区间、弱势肌群和肌肉评分的判断。今天这份等待只活在进程内存里：服务重启、一次滚动发布、或者请求被路由到另一个实例，用户页面上的轮询就会突然得到「任务不存在或已过期」——明明什么都没做错，却必须从头再传一次照片，再等一轮。等待期间刷新页面，同样等于放弃这次分析。

失败也无法解释。任务失败时用户只会看到一串原始异常文本，分不清是自己没配 API Key、供应商限流、超时，还是模型输出解析崩了；历史列表里更是完全没有这次失败的痕迹——只有成功的分析才会落一条历史。于是「用户说坏了」这句反馈，既无法还原到具体那一次执行，也无法判断是个别配置问题还是系统性故障。

更深一层的错位在于：任务状态和体型分析历史被塞在同一层结构里。任务是一次执行的事实，历史是用户长期想回看的资产，两者生命周期完全不同，现在却由同一次写入绑在一起，于是「任务完成但历史没写」「历史有记录但任务查不到」都可能发生，前端为了拼出一次完整经历不得不做额外猜测。

同一个缺口还出现在打卡后自动触发的 AdjustGraph 上：同样是「开出去就不管」的异步方式。所以这不是体型分析一处的毛病，而是系统里缺了一条统一承诺——一件事被答应了之后，它到底做成了没有，必须留下可查的记录。

## Solution

把「分析任务」提升为第一类持久实体。用户提交照片时，服务端先在数据库登记一条任务（状态、错误分类、超时时间都在里面），再由一个可靠的执行器去执行它。轮询接口只从数据库读事实，所以刷新页面、换设备、跨实例、服务重启后看到的都是同一份真相。

任务按明确状态机流转：待执行 → 执行中 → 已完成 / 失败，另有「过期作废」终态，以及执行中被回收后重新排队（重试次数累加）的补偿路径。终态一经写入不再改写，前端可以据此确定地结束等待。

任务与历史分层：任务记录执行事实，可按状态查询、会被过期清理；历史记录是成功分析的长期资产，长期保留。两者由一次事务里的外键连接，任何一侧写失败都不产生「半个成功」。

失败对用户可解释：错误按类型分类（Key 缺失、供应商鉴权失败、供应商超时、输出不可解析、图片无效、内部错误），对外只给稳定错误码加一句安全文案，供应商原文只进日志。同时前端能直接看到「这次是在第几次尝试」「什么时候会过期」，不用靠固定次数盲轮询猜超时。

打卡后的训练计划动态调整也改走同一个执行器，让「异步工作」在这个系统里只有一种说法。

## User Stories

1. 作为第一次使用体型分析的用户，我想要提交照片后立刻拿到一个可以长期查询的任务号，以便页面刷新或换设备后还能找回这次分析。
2. 作为在分析进行中刷新了页面的用户，我想要重新进入时看到任务仍在执行，以便不用重新拍照、重新等待。
3. 作为正在等待结果的用户，我想要看到明确的状态（待执行 / 执行中 / 已完成 / 失败 / 已过期），以便判断该继续等、该改配置还是该重试。
4. 作为分析失败的用户，我想要看到可理解的失败原因分类，以便知道是自己没配 API Key、Key 无效，还是系统暂时故障。
5. 作为分析失败的用户，我想要失败后能重新发起而不覆盖上一次记录，以便保留这条失败脉络供排查和对照。
6. 作为用户，我想要失败的分析不写入我的体型分析历史，以便历史列表只呈现真正完成的分析。
7. 作为用户，我想要每一次成功分析都留下一条带缩略图与结构化结果的历史记录，以便回看体型变化。
8. 作为用户，我想要任务过期时得到「已过期，可重新发起」的明确提示，而不是无限转圈到超时，以便我的时间不被浪费。
9. 作为用户，我想要的是一次分析只消耗一次我自带 Key 的额度，以便重复轮询或容器重试不会额外花我的钱。
10. 作为只关心自己数据的用户，我想要任务与历史都只对我可见，以便别人即使拿到任务号也读不到我的体型数据。
11. 作为值班开发者，我想要服务重启后未完成的任务被自动回收或标记失败，以便没有任务永远卡在「执行中」。
12. 作为值班开发者，我想要按用户和状态查询任务，以便从「用户说坏了」定位到那一次具体执行。
13. 作为值班开发者，我想要多实例部署时同一个任务只会被一个实例执行，以便不重复调用多模态 LLM、不产生互相覆盖的结果。
14. 作为运维，我想要过期任务与陈旧历史有明确的保留与清理策略，以便数据库不会无限膨胀。

## Implementation Decisions

### 1. 任务实体与状态机

新增持久实体「分析任务」，最小字段集：对外可见的任务标识（不可猜测的字符串，不复用自增主键）、所属用户、状态、阶段与进度、尝试次数、错误码与安全错误文案、结果引用、创建/开始/结束时间、心跳时间、租约归属与租约到期时间、过期时间。

状态机（这是设计决策，不是代码）：

```
pending ──claim──▶ processing ──success──▶ completed
   ▲                   │
   └──reclaim──◀───────┤──exhaust attempts──▶ failed
                       └──explicit fail─────▶ failed
pending / processing ──timeout──▶ expired
```

约束：终态（completed / failed / expired）不可再转移；回收只允许从 processing 回到 pending 且尝试次数加一；尝试次数达到上限直接进 failed（错误码为「重试耗尽」）。阶段（如「读取图片 → 调用多模态模型 → 结构化解析 → 存档」）只用于展示，不参与流转判断。

### 2. 任务与历史的分层

任务表承载执行事实，历史表承载成功资产，二者一对零或一。任务成功时在同一事务内：写入历史记录 → 回填任务的结果引用 → 置 completed。顺序固定，因此不存在「任务已完成但历史缺失」。

任务自身的结果字段在过渡期保留一份内联副本，用于满足既有轮询契约（前端已按「轮询直接拿结果」编码）；历史记录是唯一长期事实源，内联副本可安全丢弃。任务过期清理只清任务侧，历史永不因任务过期而删除。

### 3. 可靠执行器契约

不引入外部队列依赖（当前工程没有 Celery / RQ / arq，也没有 CI 兜底），执行器是进程内的 DB 驱动 worker，契约固定为五个操作：

- 认领（claim）：取最早一条 pending 且未过期的任务，用租约（归属标识 + 租约到期时间）占住，置 processing，记录开始时间与心跳。
- 心跳（heartbeat）：执行期间周期性续租；续租失败说明任务已被别人认领，当前执行者必须放弃写入。
- 成功（succeed）：幂等写入结果并置 completed；若任务已不是自己持有，丢弃。
- 失败（fail）：写入错误码与安全文案；可分类型决定是否允许重试，可重试则回到 pending，否则进 failed。
- 回收（reclaim）：启动时以及周期巡检中，把租约已过期仍为 processing 的任务按尝试次数决定重新排队或置 failed，日志标注「回收」。

并发安全依赖数据库的条件更新语义（认领必须是「状态仍为 pending 且版本未变」的条件写），生产 Postgres 可以使用行级跳过已锁，开发 SQLite 退化为单写事务——两种路径对外行为必须一致。单实例内额外用信号量限制并发执行数，防止一次涌入大量任务把进程拖死。

打卡后触发的训练计划动态调整改为投递同一类任务记录，由同一执行器消费，不再直接开协程。这是本次唯一被夹带的迁移，理由是同根因、同观测面。

**执行器边界**：本执行器只消费任务表。提醒引擎的周期 tick 是另一套轻量调度——只做规则判定与投递记录的写入，不跑 LLM、不跑重任务；它需要异步重活时把工作投递成任务记录交给本执行器，不允许在 tick 内自开协程做重活。任何新增异步能力都走这条边界，避免出现第二套「异步机制」。

### 4. API 契约

- `POST /api/vision/analyze`：请求体保持现状（图片、用户、档案）；既有前置校验保留，即未配置可用 Key 时必须在创建任务之前就失败（428 + `api_key_required`），不产生任务记录。响应扩展为包含任务标识、状态、创建时间、过期时间、建议轮询间隔。
- `GET /api/vision/analyze/{task_id}`：只读数据库。响应形状（设计决策）：

```json
{
  "task_id": "01J...",
  "status": "pending | processing | completed | failed | expired",
  "stage": "queued | vision | parse | persist | done",
  "attempt": 1,
  "progress": 40,
  "result": { "body_type": "...", "body_fat_range": "...", "weak_muscles": [], "strengths": [], "muscle_scores": {}, "summary": "..." },
  "error": { "code": "provider_timeout", "message": "分析超时，请稍后重试", "retryable": true },
  "created_at": "2026-05-01T10:00:00Z",
  "updated_at": "2026-05-01T10:00:20Z",
  "expires_at": "2026-05-01T10:10:00Z"
}
```

  `result` 与 `error` 互斥且各自可为空。任务从未存在 → 404 且错误码为「任务不存在」；存在但已过期 → 200 且 `status=expired`（**不要**用 404 表达过期，否则前端无法区分「过期」与「从未存在」，且现有前端会把它当作异常中止）。非本人任务 → 403，与既有越权语义一致。
- `GET /api/vision/tasks`：当前用户的任务列表，支持按状态过滤与游标分页，返回摘要（任务标识、状态、错误码、时间、历史记录标识），供「我的分析」与排障使用；不返回图片内容。
- 历史接口保持不变，但语义收紧为「只返回已完成分析所对应的记录」，并在列表项中回传对应任务标识，前端可据此把历史与任务对齐。

### 5. 错误与降级策略

错误码是稳定枚举，与对外文案分离：`api_key_required`、`provider_auth_failed`、`provider_rate_limited`、`provider_timeout`、`output_unparsable`、`image_invalid`、`storage_unavailable`、`retry_exhausted`、`task_expired`、`internal_error`。可重试错误在响应里带 `retryable`，前端据此决定是否自动重试。

- 供应商异常一律不透传原文：安全文案形如「AI 服务暂时不可用，请检查 API Key 配置后重试」，原文只进日志（字段约定见观测基线 spec）。
- 输出不可解析时保留既有降级（用原始文本作为 summary 兜底），且这条降级必须被记录成一次「解析退化」事件，不静默。
- 执行器不可用（例如数据库写不进）时，创建任务的请求必须失败而不是返回一个永远不会完成的任务号。
- 过期任务不再被认领；对过期任务再次轮询不报错，前端可引导重新发起。

### 6. 保留、过期与清理

- 任务默认过期时长按分钟级配置（量级：单次分析远小于此），过期后停止认领。
- 终态任务保留可观窗口后由执行器的定时清理删除（量级：数天），历史记录长期保留。
- 清理必须打日志计数，不能静默删；删除按批次，避免长事务。

### 7. 迁移与数据模型落地约定（本组 spec 中只在此处定义，媒体与观测 spec 引用本节）

当前工程的运行时建表事实源是 ORM 元数据（应用启动时按模型建表），而迁移目录只有一份初始迁移，且与 ORM 已经漂移（用户主键在初始迁移里是 UUID，在 ORM 里是自增整数）。因此本次采用如下约定：

1. ORM 模型是唯一事实源；迁移文件必须与模型手写对齐，不允许「迁移跑完与模型不一致」。
2. 每次交付追加一份迁移，接在上一份之后；同一批次一次交付的多个改表可以合并为一个 revision（本 spec 交付内包含：任务表、历史表新增的结果引用与任务关联列、必要的索引——用户 + 创建时间、状态 + 创建时间、租约到期）。不要把后续批次的改表（媒体资产表、提醒投递表、调整作业、计划解释字段等）预留或塞进本次迁移。
3. 开发期 SQLite 继续依赖 ORM 元数据建表，生产 Postgres 只走迁移；两者字段类型由兼容层统一映射，禁止在业务代码里出现数据库方言判断。
4. 迁移必须可回滚（downgrade 删除本迁移新增的对象），且不得包含数据回填脚本之外的多步操作。
5. 用户主键类型以 ORM 为准；外键列类型必须与之完全一致，不顺延初始迁移里的 UUID 假设。

### 8. 前端契约影响

前端最小改动：把任务状态映射成展示文案与可执行动作的纯函数化（待执行 / 执行中 / 已完成 / 失败 / 已过期），并把「已过期」「重试耗尽」视为终止态（现有实现在这两种情况下会一直轮询到 120 秒超时才报「分析超时」）。轮询间隔改为优先采用服务端返回的建议间隔。轮询次数上限仍然保留，作为服务端异常时最后一道保险。

### 9. 观测钩子

任务创建、认领、心跳失败、成功、失败、回收、清理各产生一条结构化事件，字段命名与错误码语义统一由观测基线 spec 定义，本 spec 不重复定义字段。

## Testing Decisions

### 好测试的标准

只断言外部可观测行为：HTTP 状态码、响应体里的状态与错误码、持久化后可见的历史记录数量。不断言进程内字典、任务对象内部字段、调用顺序、SQL 语句，也不断言执行器内部如何调度。一个通过的测试应该能容忍执行器换成外部队列、任务表加列、状态机内部重构。

### 最高 seam：FastAPI 路由层

后端起一个测试内应用客户端（ASGI 传输 + 依赖覆盖到隔离的临时数据库），用真实路由 + 真实服务层，只把「执行」这一侧替换成可控替身（测试里手动推进任务状态，或用一个同步执行器把任务立刻跑完）。这样创建、轮询、权限、过期、历史落库这些行为都在同一条 seam 上被覆盖。

为什么不需要更低层的 seam：本 spec 的全部风险都是「对外可见的事实是否可靠」——重启后能不能查到、过期后返回什么、非本人能不能读、失败会不会污染历史。这些全部可以由路由层的请求/响应表达。再往下的执行器单元测试会把租约/心跳的实现细节钉死，而实现细节正是未来最可能被替换的部分（换外部队列时应当只在部署层变化）。

例外（必须有一条低层验证）：迁移与 ORM 一致性。用一个测试在空库上跑「按 ORM 元数据建表」与「按迁移升级」两条路径，然后对比表与列集合，保证约定 7 不被悄悄破坏。这是本 spec 唯一值得下探的地方，因为它是构建期的事实而非运行时行为。

### 被测模块

1. 分析任务 API（创建、轮询、列表、越权）
2. 任务执行器（认领 / 回收 / 重试 / 幂等成功写入）
3. 历史查询 API（只返回已完成、与任务对齐）
4. 迁移与 ORM 一致性检查

### 必测行为清单

- 创建任务后立刻轮询：可见 `pending` 或 `processing`，绝不 404。
- 轮询期间模拟「进程重启」（丢弃内存态，仅保留数据库）：状态仍可查询，且能推进到完成。
- 执行成功：任务变 completed、历史多一条、两者标识一致。
- 执行失败：任务变 failed 且带稳定错误码，历史不新增。
- 过期任务：轮询返回 `status=expired`，不返回 404。
- 不存在的任务标识：404 且错误码为「任务不存在」。
- 他人任务：403，且不泄漏任何结果内容。
- 未配置可用 Key：创建即 428，且数据库里没有新任务记录（用历史与任务计数断言）。
- 租约过期的 processing 任务被回收：回到 pending 或按尝试上限进 failed，且尝试次数递增。
- 同一任务被并发认领：只有一个执行者拿到（用条件写的结果断言，而不是断言锁实现）。
- 打卡后调整任务：产生可查询的任务记录，且失败不影响打卡响应成功。

### 前端 seam

纯 TypeScript 函数：任务状态 → 展示文案 + 下一步动作 + 是否终止等待；轮询间隔与上限的推导。用 vitest 单测，不渲染页面。prior art 见下。

### 仓库内 prior art

- `backend/tests/test_auth_guards.py`：临时 SQLite + 依赖覆盖 + 构造 JWT 头的完整骨架，直接复用。
- `backend/tests/test_user_api_keys.py`：monkeypatch 掉分析执行入口、断言 428 且下游未被调用的写法，是「创建即失败、不产生任务」的模板。
- `backend/tests/test_coach_stream.py`：上游失败时对外仍给出可读错误与结束标记的断言风格。
- `web/src/pages/analysis/flow.ts` 与 `flow.test.ts`：把页面布尔量/状态收敛成纯函数再单测，正是状态文案映射该走的路。

### 显式不做

不写真实调用多模态模型的测试；不写连接真实 Postgres 的测试（方言相关分支靠一致性检查与人工验证）；不写断言日志内容的测试（观测面在观测基线 spec 里覆盖）。

## Out of Scope

- 引入外部任务队列（Celery / RQ / arq）或独立 worker 进程部署形态；本 spec 的执行器是进程内的，改造点被刻意收在「认领与租约」这一个契约后面。
- 分析结果对比、体型变化时间线、同期照片对比等资产化功能。
- 前端页面重做；只要求状态映射与终止态处理。

## Further Notes

- 代码现状里两个具体的坑：任务状态字典只增不删，进程内无上限；轮询接口对未知任务一律 404，导致「过期」与「从未存在」不可区分——后者是前端必须改的契约点。
- 用户主键类型在初始迁移与 ORM 之间不一致（UUID vs 自增整数），新增外键前必须先按约定 7 对齐，否则生产迁移会在类型上直接失败。
- 认领的并发语义依赖数据库能力：Postgres 可以行级跳过已锁，SQLite 只能靠单写事务串行化。两条路径必须由同一组路由层测试覆盖，且不得在业务代码里出现方言分支。
- Redis 已经在配置与编排里存在但完全没有使用。本次不引入它；若将来需要「多实例即时唤醒」，把认领轮询换成 Redis 通知即可，契约不变。
- 打卡后训练计划调整的迁移与本文同根因，已列入决策 3，但调整本身的算法（多路分析器）不在本 spec 讨论范围。
- 跨 spec 依赖：图片进对象存储后，任务输入从内联图片换为资产引用，见 `media-asset-storage`；任务状态流转与失败事件需要落成结构化日志，字段约定见 `observability-baseline`；打卡与训练计划调整的业务语义分别见 `workout-session-loop` 与 `adaptive-plan-adjustment`，本 spec 只规定它们的异步部分必须投递为持久任务，而不是直接开协程。

## 落地修订（工单 12）

任务列表与历史对齐的落地取舍：

1. **任务列表**：`GET /api/vision/tasks` 只认 token 身份（没有 user_id 参数），返回
   `{items, next_cursor}`；列表项只有任务标识、状态、错误码、创建/更新时间与对应历史记录
   标识，不含结果明细、图片内容或档案。状态五态与创建接口同一套词表；DB 仍为 pending/
   processing 但已过 `expires_at` 的行对外投影为 `expired`（不写库），`status=expired`
   过滤同时命中这些行与历史已落库的 expired 行。
2. **游标分页**：游标是不透明 URL-safe base64（`created_at` + `task_id` 的键集），严格校验；
   非法游标 422 `invalid_cursor`，limit 越界由 FastAPI 422。按 (created_at desc, task_id desc)
   稳定排序，连续翻页不重不漏。
3. **历史与任务分层**：历史列表通过 `AnalysisTask.history_record_id` 反查任务标识，只返回
   已完成分析对应的记录（失败/过期任务不产生历史行）；旧记录没有关联任务时保留可读、
   `task_id=null`（向后兼容，不删用户数据）。单条详情接口采用同一口径，避免绕过列表读取
   脏数据。
4. **错误码**：`invalid_cursor` 作为稳定错误码定义在服务模块，路由只引用常量。
5. **前端**：补充任务摘要与列表的类型、`getAnalysisTasks` 客户端（本票不做页面）。
