# 09 — 分析任务实体与创建接口

**What to build:** 用户提交全身照后，服务端不再只是「把这次请求丢进内存再返回一个号」，而是在数据库里留下一条可追溯的分析任务：谁提交的、什么时候、什么状态、什么时候过期。用户拿到的任务标识不可猜测、可长期引用，刷新页面或换设备都不会让它变成陌生人。既有前置校验保持不变——没配 API Key 的用户在创建之前就被拦下，不产生这条记录，因此不会出现「任务已创建但注定失败」的脏数据。这张票只做写入侧；读取侧紧接着由 10 接上，两者合起来才是用户看到的等待体验，所以不在中间态上做任何临时契约。

**Blocked by:** 06 迁移基线对齐与一致性测试

**Status:** ready-for-agent

- [ ] 已配置可用 Key 的用户提交照片：响应 200，返回任务标识、`status=pending`、创建时间、过期时间与建议轮询间隔；任务标识不是自增数字，连续两次提交得到不同标识。
- [ ] 数据库中出现对应的任务记录：所属用户正确、状态 `pending`、尝试次数为 0、过期时间在未来。
- [ ] 未配置可用 Key 的用户提交：返回 428 且错误码为 `api_key_required`，任务记录数前后一致（0 新增）。
- [ ] 重建应用实例（模拟进程重启、内存清空）后，该任务记录仍以 `pending` 存在且未过期（用全新会话读取断言）。
- [ ] 创建阶段写库异常时请求返回 5xx，不返回任务标识（不存在「已返回但永远不会完成」的任务号）。
- [ ] 既有体型分析历史接口行为不变，既有回归用例全绿。
