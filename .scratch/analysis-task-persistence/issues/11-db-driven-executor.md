# 11 — DB 驱动执行器

**What to build:** 任务真的会被执行，而且不会再永远停在「执行中」。执行器从任务表里认领工作，用租约占住它，成功就落结果与历史记录，失败就写稳定错误码并决定是否重试；进程被强杀留下的「执行中」任务会被回收重试，重试耗尽则明确失败，超过过期时间的任务不再被认领。多实例部署时同一个任务只会被一个执行者拿到，因此不会重复消耗用户自带的 API Key 额度，也不会出现两次结果互相覆盖。用户侧的观感只有一件事：等待总会结束，而且结束的方式是可解释的。

**Blocked by:** 09 分析任务实体与创建接口

**Status:** ready-for-agent

- [ ] 创建任务后无需人工触发，执行器自动认领并推进到 `completed`；历史记录恰好多一条，且与任务的结果引用一致。
- [ ] 执行中进程被强杀（模拟崩溃）后重启：遗留的 `processing` 任务被回收，尝试次数 +1 并重新排队，最终可完成；尝试次数达到上限则置 `failed` 且错误码为 `retry_exhausted`。
- [ ] 两个执行者同时认领同一任务的测试中只有一个能写入结果，另一个放弃写入；历史记录只增加一条。
- [ ] 执行失败（供应商鉴权失败、限流、超时、输出不可解析）时任务置 `failed` 并带对应稳定 `error.code` 与安全文案，历史记录不新增。
- [ ] 创建后超过过期时长仍未被执行的 `pending` 任务自动置 `expired`，且不再被认领。
- [ ] 单实例并发执行数受配置上限约束：一次性投递远超上限的任务时进程不被拖死，超出部分保持 `pending` 并最终被执行完成。
