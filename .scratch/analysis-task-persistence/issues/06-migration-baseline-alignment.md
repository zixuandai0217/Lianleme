# 06 — 迁移基线对齐与一致性测试

**What to build:** 用户看不见这张票，但它决定后面每一张改表票能不能安全上线。当前数据库有两条互不承认的「真相」：应用启动时按模型建表，而迁移目录里只有一份初始迁移，且已经和模型漂移（用户主键在迁移里是 UUID 带随机默认值，在模型里是自增整数）。结果是：今天谁想加一张表，要么绕过迁移，要么按迁移的类型写外键然后在上线时炸掉。本票把两条路对齐，并把「对齐」这件事变成质量门里跑得起来的检查——否则任务表、媒体资产表、提醒投递表、调整作业、计划解释字段会各自踩一遍同样的坑。

**Blocked by:** 01 质量门入口（前后端质量命令 + 修跨平台用例）

**Status:** ready-for-agent

- [ ] 在空库上分别用「按模型元数据建表」与「按迁移升级到最新」两条路径建库，表集合、列名与列类型逐项一致；存在任何差异时该检查失败（检查可在 `pytest` 中运行）。
- [ ] 迁移可从最新回滚到基线再升级回最新，全程无错误；回滚后不留本批次新增的对象。
- [ ] 该一致性检查已接入质量命令，在本地与另一操作系统上跑质量命令均全绿。
- [ ] 用户主键列在迁移与模型中同为自增整数，迁移中不再有 UUID 默认值假设；所有引用用户表的列类型与之一致。
- [ ] 迁移目录中 revision 链线性唯一，从空库执行一次「升级到 head」即成功，且迁移与模型定义中不出现数据库方言分支（SQLite 兼容只出现在兼容层）。
