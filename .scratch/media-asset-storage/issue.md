# Issue: 媒体资源接入对象存储（原图存档、签名访问、校验与生命周期）

## Problem Statement

用户上传的全身照，今天只以 base64 在请求体、函数参数和数据库列之间流转。真正落库的只有一张宽 200 像素的缩略图 base64——原图在任务结束后就消失了。用户三个月后想对比体型变化，历史上只剩一张模糊缩略图；分析结果说得再准，用户也拿不出当时的照片佐证。

base64 这条路还在别处持续收费：请求体被撑到数兆，一次分析请求的负载大部分是图片字串；历史列表为了显示缩略图，要把每行 base64 全部传下来，弱网下翻一页历史要等很久；数据库行宽被图片撑大，备份与查询都变慢。更糟的是这条链路没有任何校验——格式不支持、图片过大、分辨率过低（甚至一张截图或头像）都能一路走到后台，等 Pillow 解码或模型调用阶段才炸，用户等待数十秒后只得到一句失败。而失败发生在后台，用户连「重拍一张」这个正确动作都得不到提示。

同时，对象存储其实已经写好了客户端、建好了 bucket、编排里也起好了 MinIO，但主链路一次都没用过。而且现有上传封装返回的是把配置里的地址与 key 直接拼起来的 http 地址，对私有 bucket 根本不可访问：一旦有人照着这个返回值去用，用户的体型照片就会以「知道链接就能看」的方式暴露。缩略图这件事也没有归属——它现在只是历史表里的一个字符串字段，不占任何存储对象，因此无法批量清理、无法迁移、无法说明它属于谁。

## Solution

把「媒体资产」变成一等实体：原图上传到对象存储，数据库只保存对象 key 与元数据（不含任何 URL、不含任何 base64），缩略图由后台执行器异步生成后同样进对象存储。历史记录通过资产引用拿到原图与缩略图，接口按需签发短时有效的访问链接。

访问控制交给签名：bucket 保持私有，读图必须先经过鉴权接口，由服务端校验归属后签发短时有效的预签名 URL。URL 不落库、不进日志、不进缓存键，因为它会过期且具有临时授权含义。

入库前先校验：内容类型白名单、字节上限、解码后的最小边长、单帧、方向纠正与 EXIF 清理。校验失败在请求阶段就以可判定的错误返回，不创建分析任务，用户当场就知道该换一张什么样的照片。校验通过后的原图是「已存档」的，后续分析任务只引用资产标识，不再搬运图片内容。

生命周期有明确归属：资产属于用户，能被记录引用；删除记录时对应资产被标记删除并异步清理对象；用户级删除按前缀批量清理；未被任何记录引用的孤儿对象由巡检发现后清理。对象存储不可用时行为必须可预测——明确失败，绝不悄悄回退到把图片塞回数据库。

## User Stories

1. 作为用户，我想要上传的原图被真正保存下来，以便几个月后还能回看当时的照片而不是一张缩略图。
2. 作为用户，我想要历史列表和详情只在需要时才拉取图片，以便弱网和移动端翻历史不会卡住。
3. 作为用户，我想要上传不支持的格式（如 HEIC、PDF）时立刻被告知支持的格式，以便不用等几十秒才失败。
4. 作为用户，我想要超过大小上限的照片被明确拒绝并告知上限，以便知道该怎么处理这张照片。
5. 作为用户，我想要分辨率过低或明显不是全身照的图片被提示重拍，以便得到的分析结果值得信任。
6. 作为用户，我想要我的照片只有我自己能看到，即使链接被别人拿到也会很快失效，以便身体照片不被传播。
7. 作为用户，我想要删除一条分析记录时对应照片也被删除，以便「删除」是真的删除而不是隐藏。
8. 作为用户，我想要缩略图在历史里稳定显示，即使原图很大，以便列表加载快而且视觉一致。
9. 作为用户，我想要照片里的位置等敏感元信息在上传后被清除，以便分享或存档不会顺带泄漏拍摄地点。
10. 作为值班开发者，我想要对象存储不可用时分析链路给出可判定的失败，以便系统行为可预测、不出现「一半在库里一半在对象存储」的数据。
11. 作为值班开发者，我想要孤儿对象能被巡检发现并清理，以便存储成本不会无限增长。
12. 作为值班开发者，我想要同一个文件重复上传不会产生多份对象，以便重试和重复提交不会浪费存储。
13. 作为运维，我想要能按用户一次性清理其全部媒体资产，以便响应注销与数据删除请求。
14. 作为开发者，我想要存取媒体只经过一个端口（写入、读取、签名、删除、存在性检查），以便将来换成其他对象存储服务时不用改业务代码。
15. 作为开发者，我想要测试里能把对象存储替换成内存实现，以便测试不依赖 MinIO 服务。

## Implementation Decisions

### 1. 媒体资产实体与引用策略（本组 spec 中对象存储引用方式只在此处定义，其他 spec 引用本节）

新增「媒体资产」实体，只存元数据，不存内容、不存 URL：

- 资产标识（不可猜测字符串，作为对象 key 的一部分）
- 所属用户
- 种类：原图 / 缩略图（未来可扩展姿态视频等，本期只两种）
- 对象 key（对象存储内的完整键）
- 内容类型、字节大小、宽、高
- 内容校验摘要（用于去重与完整性核对）
- 状态：可用 / 已降级 / 待清理 / 已删除
- 创建时间、删除时间

业务表（例如体型分析历史）通过资产标识引用原图与缩略图，绝不冗余保存 key 之外的副本信息，也绝不保存签名 URL。

### 2. 对象 key 组织

key 采用「环境 / 用户 / 年月 / 资产标识.扩展名」的分层结构。不把用户原始文件名写进 key（原始名只作为元数据保留，且不参与路径拼接），避免路径注入与文件名里的隐私信息泄漏到存储层日志。同一用户的所有对象共享可枚举前缀，用户级删除因此是一次前缀批量操作。

### 3. 访问控制与签名

- bucket 私有，不允许匿名读，也不配置公开前缀。
- 读图唯一入口是鉴权后的签名接口：校验当前用户是该资产所有者（或管理员），签发短时有效的预签名 URL（量级：分钟级，可配置），URL 不落库、不进日志、不进缓存键。
- 写图只走服务端中转（客户端不直传），因此写入凭据永不出现在前端。
- 历史与详情接口返回缩略图与原图的签名 URL 字段；旧的内联缩略图字段保留一个弃用窗口，过渡期返回空值，前端优先读新字段。
- 资产不存在、已删除、非本人持有，一律返回统一的「资源不存在或无权访问」语义（403/404 之一固定下来），不区分「存在但不属于你」与「不存在」，避免探测。

### 4. 上传校验（在请求阶段完成，失败不创建分析任务）

- 内容类型白名单：image/jpeg、image/png、image/webp。其余一律 415。
- 字节上限：解码前按配置上限拒绝（量级：单张数 MB），超限 413。
- 最小分辨率：解码后最短边不低于配置下限（量级：数百像素），低于则提示重拍。
- 单帧：拒绝多帧与动图。
- 方向与隐私：按 EXIF 方向纠正像素后**清除**全部 EXIF（尤其地理位置），存档的字节是清理后的版本。
- 解码失败、被截断、伪造内容类型（声明 jpeg 实为他物）→ 400，并记录一次校验拒绝事件。
- 校验结果（尺寸、类型、字节数）一并写入资产元数据，供后续分析与前端展示使用。

### 5. 缩略图生成

缩略图由后台执行器异步生成（复用分析任务的执行器与租约契约，不新造一套异步机制）：长边缩放到配置尺寸、JPEG 质量固定档、写入对象存储、回填资产引用。生成幂等：目标对象已存在或资产已标记缩略图可用则跳过。

缩略图失败不阻断分析结果：资产状态置为「已降级」，历史接口在该条记录上返回空缩略图 URL，前端用占位图。降级必须被记录（计数 + 事件），不得静默。

### 6. 与分析任务链路的衔接

分析任务创建接口的输入从「内联图片」改为「资产标识」，兼容期同时接受内联图片：收到内联图片时服务端先落成资产再建任务，**不把图片写进任务表或历史表**。任务侧状态机、重试与过期语义由 `analysis-task-persistence` 定义，本 spec 不重复。

### 7. 存储端口（唯一对外契约）

业务代码只依赖五个操作的端口：写入（字节 + 内容类型 + key → 元数据）、读取（key → 字节流，仅服务端校验/巡检使用）、签名（key → 短时 URL）、删除（key）、存在性检查（key）。端口的具体实现在配置装配处决定，业务代码不得直接持有客户端对象，也不得拼接访问地址。当前实现返回拼装 URL 的方式必须被替换为「签名」语义。

上传封装是同步阻塞调用，而链路是异步的：端口实现必须把阻塞调用隔离到线程池，不得在事件循环里直接等待网络 I/O。同理，图片解码与缩略图重编码是 CPU 密集操作，必须在执行器的线程池中完成。

### 8. 幂等与去重

上传支持可选的客户端校验摘要：同一用户、同一摘要、仍处于可用状态的资产直接复用，返回既有资产标识，不重复写对象。没有摘要时按「新资产」处理。去重只影响原图，缩略图随资产生成一次。

### 9. 生命周期与清理

- 删除分析记录：资产标记「待清理」并进入清理队列，异步删除对象；记录本身软删除或硬删除由既有语义决定，但对象必须最终被删。
- 用户级删除：按用户前缀批量列举并删除，附带对象计数日志。
- 孤儿巡检：周期性列举对象，与资产表比对，未被任何资产引用且超过宽限期（量级：一天）的对象删除；反向巡检发现「资产存在但对象缺失」时把资产置为「已降级」并记事件。
- 清理必须分批、可重入、有计数日志，不允许一次性长事务。

### 10. 降级策略

对象存储不可用时：上传接口返回明确错误（服务暂不可用语义），分析任务创建失败，**不回退到把 base64 写进数据库**。理由是一旦允许回退，数据会出现两种形态，历史接口、清理、迁移全部要处理两条路径。若某条历史记录已存在但读图失败，接口返回空 URL 与降级标记，而不是让整个列表失败。

### 11. 配置

新增配置项（数量从简）：单张字节上限、缩略图长边、允许的内容类型、签名有效期、孤儿宽限期、清理批次大小。配置缺失时使用安全默认值，不因缺少配置而放行任意大小/任意类型。

## Testing Decisions

### 好测试的标准

只断言外部可观测行为：接口返回的状态码与错误码、返回体里是否出现签名 URL、数据库里是否只留下 key 与元数据（且不出现图片字串）、删除后对象是否不可再用、重复上传是否拿到同一资产标识。不断言 S3 SDK 的调用参数、不断言对象 key 的具体拼法（只断言其稳定性与归属前缀）、不断言缩略图字节内容（只断言尺寸与内容类型）。

### 最高 seam：FastAPI 路由层 + 内存存储端口

用测试内应用客户端（ASGI 传输 + 依赖覆盖到隔离数据库），并把存储端口替换成内存实现（字典 + 可失效的签名）。这样上传、校验、读取签名、删除、历史响应映射全部在同一条 seam 上被覆盖，而无需 MinIO 或网络。

为什么不需要更低层的 seam：本 spec 的全部风险都在端口边界上——「有没有写进去」「读出来能不能鉴权」「删了还能不能拿到 URL」「非法图片会不会被挡在请求阶段」。内存实现已经完整表达端口的语义（key 不可猜测、URL 会过期），再往下测等于测假实现。真实 S3 兼容性属于部署验证，不属于回归测试。

必测的一条低层检查：端口实现的「签名 URL 过期后不可用」语义，用内存实现验证即可；不要为真 MinIO 写集成测试（CI 不可依赖它）。

### 被测模块

1. 媒体上传接口（校验矩阵、去重、降级）
2. 媒体签名读取接口（归属校验、URL 有效期、已删除资产）
3. 分析历史响应映射（新 URL 字段、旧字段弃用、缩略图降级占位）
4. 资产服务（删除、按用户清理、孤儿判定）
5. 存储端口实现（内存版与真实版共享同一契约测试）

### 必测行为清单

- 合法 JPEG 上传：返回资产标识与元数据；数据库里该资产的记录不含图片字串、不含 URL。
- 超过字节上限：413；不产生资产。
- 内容类型不在白名单：415；不产生资产。
- 分辨率低于下限：400 且错误码可判定；不产生资产。
- 伪造内容类型（后缀/声明与实际不符）：400。
- 读取：本人换取 URL 成功；他人 403/404（语义固定且一致）；未登录 401。
- URL 过期后再次使用：失败（用内存实现推进时钟断言）。
- 删除记录后：资产不可再换取 URL，对象被标记清理。
- 重复上传同一摘要：返回同一资产标识，对象数量不增加。
- 存储端口抛错：上传接口返回服务不可用语义，分析任务未创建，数据库无 base64 落库。
- 缩略图生成失败：分析结果仍可查，历史返回空缩略图 URL 与降级标记。
- 分析任务创建接受资产标识；兼容期内联图片也会先落成资产。

### 前端 seam

纯 TypeScript 函数覆盖：把资产/URL 字段映射成图片展示状态（就绪 / 加载中 / 降级占位 / 失败重试），以及上传前的本地预校验（类型、大小）。用 vitest 单测，不渲染页面。页面级只需一条 jsdom 测试验证「图片加载失败时出现占位而不是破图」。

### 仓库内 prior art

- `backend/tests/test_auth_guards.py`：临时 SQLite、依赖覆盖、JWT 头的骨架；媒体接口的归属校验测试直接复用这套。
- `backend/tests/test_user_api_keys.py`：用 monkeypatch 把外部依赖（此处是存储工厂）替换成替身、并断言「下游未被调用」的写法，正好用于「校验失败不创建资产/任务」。
- `backend/tests/test_coach_stream.py`：降级路径的断言风格（失败时对外仍有可用形态）。
- `web/src/pages/analysis/flow.ts` 与 `flow.test.ts`：把展示决策收敛成纯函数并单测的范例。
- `web/src/api-key-gate.test.tsx`：页面级条件渲染的 jsdom 测试写法，占位图场景可照此写。

### 显式不做

不写连接真实 MinIO 的测试；不写缩略图像素级比对；不写前端上传进度条动画测试。

## Out of Scope

- 客户端直传（预签名 PUT）：本期一律服务端中转，直传留作后续优化。
- 视频、姿态序列、音频等其他资产类型。
- CDN、图片转码集群、多规格自适应图（本期只有原图 + 一种缩略图）。
- 内容审核/人脸/裸露检测。
- 图片水印、分享链接、公开相册。
- 迁移约定与任务状态机（见 `analysis-task-persistence`）。
- 日志字段约定与健康检查（见 `observability-baseline`）。

## Further Notes

- 现有存储封装返回的是把配置地址与 key 拼起来的 http 地址，对私有 bucket 不可用，也没有签名与过期概念；同时它把同步客户端直接在异步上下文里调用，会阻塞事件循环。这两点必须一起改，否则「接入对象存储」只是把 base64 换成了另一个错误。
- 启动时的 bucket 初始化会吞掉所有异常并只打一条 warning：对象存储不可用时应用照常启动，于是故障被推迟到用户第一次上传才暴露。这个行为与第 10 条的降级策略需要一起确认（允许启动，但上传必须明确失败）。
- 开发编排里 MinIO 已就绪，但 bucket 没有生命周期策略、没有匿名访问控制声明；这些属于部署侧配置，本 spec 只要求行为上私有 + 签名。
- 用户主键类型在迁移与 ORM 之间已漂移，资产表的外键类型必须以 ORM 为准，避免第二处同类错误。
- 缩略图与降级状态是「可接受的坏」，原图缺失是「不可接受的坏」：如果上传与建任务必须二选一成功，宁可不建任务。
- 跨 spec 依赖：任务侧状态机与重试见 `analysis-task-persistence`；对象存储失败与降级事件需要结构化日志，字段约定见 `observability-baseline`。
