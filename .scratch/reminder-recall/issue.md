# Issue: 提醒召回体系（每日训练提醒 / 连续未训练召回 / 周目标提醒）

## Problem Statement

现在用户只有在主动打开应用时才会被系统「看见」。整个仓库里没有任何提醒能力：后端没有任何定时调度器或任务队列依赖（依赖清单里只有 Redis 客户端，没有 APScheduler / Celery / arq 一类的东西），应用启动时只做建表与对象存储初始化，没有任何周期任务；没有通知表、没有推送通道、没有「用户是否授权接收提醒」的字段；前端侧边栏只有数字人、训练计划、体重记录、我的四个入口，既没有通知铃铛也没有通知列表，全仓库搜不到一条与提醒相关的代码。

这带来三个具体损失。第一，训练日用户必须自己记住「今天要练」，而计划的今日任务其实已经算得出来（今天是不是训练日、重点是什么、预计多久），只是没人主动告诉他。第二，连续多天不训练的用户会静默流失：系统明明知道他最近一次打卡是哪天，也知道他已经 6 天没动过，但不会做任何事。第三，正向反馈缺失：用户在某周达成了目标（连续天数、本周完成次数、完成率），除了首页四个数字卡片之外没有任何「被看见」的时刻。

PRD 的 P1-6 明确写了前提依赖：正式登录、用户订阅授权、后台任务可稳定运行。身份体系已经落地（JWT bearer + 用户/管理员分离，打卡与统计都做了本人校验），但后两项都还没有：既没有订阅授权模型，也没有可稳定运行的后台任务基础设施。因此这个特征的重点不是「写几条文案」，而是**先明确引入什么样的调度与投递机制**，再在其上实现三类提醒规则。

## Solution

引入一个**提醒引擎**：由应用内常驻的周期调度器按时钟节拍驱动，按规则为每个用户生成「应提醒」候选，写入一个带幂等约束的投递记录，再由通道适配器投递出去——第一版通道是**站内通知收件箱**（登录后可见、带未读红点），外部推送作为可选通道在用户授权后启用。用户侧新增：顶栏铃铛与未读数、通知列表页（可标已读 / 全部已读 / 点击跳转到对应页面）、提醒偏好设置（按类型开关、免打扰时段、每日上限）。三类提醒规则：每日训练提醒（训练日且当天尚未打卡，休息日走差异化的恢复日提醒）、连续多天未训练召回（3 / 7 / 14 天阶梯，逐步降频而不是天天催）、周目标提醒（达成时给正反馈，周期末仍有缺口时给一次温和提醒）。管理员侧只增加一个聚合的提醒运营概览，用于判断召回是否真的在起作用。

## User Stories

1. 作为训练日用户，我想要在每天固定的提醒时刻收到一条「今天练什么」的提醒（含今日重点与预计时长），以便不靠记忆想起要训练。
2. 作为已经当天完成训练的用户，我想要当天不再收到训练提醒，以便不被重复催促。
3. 作为休息日的用户，我想要收到差异化的一条「今天是恢复日」提醒（含轻量活动建议），以便不被误催训练。
4. 作为连续 3 天以上未训练的用户，我想要收到一条召回提醒（含上次训练距今多少天、给一个低门槛的 10 分钟起步方案），以便更容易重新开始。
5. 作为连续更久未训练的用户，我想要召回提醒按 3 / 7 / 14 天阶梯逐步降频而不是每天一条，以便不被骚扰。
6. 作为本周达成周目标的用户，我想要收到达成提醒（本周完成次数、连续天数），以便获得正反馈。
7. 作为周期末还没完成周目标的用户，我想要收到一条温和的缺口提醒（还差几次），以便决定要不要补练。
8. 作为还没有训练计划的新用户，我想要收到的是「先完成体型分析并生成计划」的引导，而不是「今天练什么」，以便提醒不会落空。
9. 作为用户，我想要在顶栏看到一个铃铛和未读数红点，以便知道有没有错过提醒。
10. 作为用户，我想要打开通知列表并按时间倒序看到所有提醒，以便补看错过的内容。
11. 作为用户，我想要把单条通知标为已读、或一键全部已读，以便未读数是准确的。
12. 作为用户，我想要点击一条通知直接跳到今日训练 / 计划 / 统计对应页面，以便一步到达要做的事。
13. 作为用户，我想要在设置里逐类开关提醒（每日训练 / 召回 / 周目标 / 引导），以便只保留我想要的。
14. 作为用户，我想要设置免打扰时段（例如 22:00–08:00）与每日最多接收条数，以便夜间不被打扰、白天不被刷屏。
15. 作为授权了浏览器推送的用户，我想要在页面关闭时也能收到系统级通知，以便真正的「被叫醒」。
16. 作为用户，我想要在通知设置里看到「当前设备是否已授权推送」，以便知道为什么收不到系统通知。
17. 作为运维/开发，我想要同一条提醒（同一用户、同一规则、同一本地日期、同一通道）最多只发一次，即使调度重跑、进程重启或手动触发也不会重复，以便重试机制不会变成骚扰。
18. 作为管理员，我想要看到一个提醒运营概览（今日发送量、失败量、按规则类型的分布、召回后 7 日内回访人数），以便判断召回是否有效。

## Implementation Decisions

**调度机制：引入进程内周期调度器，不引入 Celery / 外部 broker。** 应用启动时创建一个常驻 asyncio 长任务，按固定间隔（建议 60 秒）tick；每次 tick 读取当前时间，计算所有受支持时区里落在「调度窗口」内的每日任务并执行，然后 sleep 到下一个节拍。tick 必须可重入保护（进程内标志位：上一次 tick 未结束则跳过本次），单次 tick 的异常必须被捕获并记录，不允许让调度长任务死掉。进程退出时优雅取消该任务。

**tick 的职责边界（与任务持久化 spec 的分工，必须显式约定）：** tick 只做两件轻量事——**规则判定**与**投递记录写入**。它不执行 LLM 调用、不做批量外部推送、不访问第三方网络，也**绝不在 tick 内自己 spawn 协程去跑重活**；tick 的单次耗时上限是毫秒到秒级，超时就意味着设计错了。凡是需要异步重活的部分（例如召回文案的个性化生成、Web Push 的批量投递与重试、任何可能需要重试的外部调用），一律投递成**任务持久化 spec 定义的持久作业**，由同一套 DB 驱动执行器消费；本 spec 只消费执行器的「作业状态可查询」语义，不定义也不实现执行器。这样系统里「周期性触发」与「一次性作业执行」是两件事：前者归本 spec 的 tick，后者归执行器契约（认领 / 心跳 / 成功 / 失败 / 回收），二者不互相吞并。

这样选择的理由：部署形态是单实例（一辆小机器 + 外部 API），引入 broker 会带来运维成本和「跑不起来」的风险，而这正是简历项目最忌讳的；Redis 客户端已经存在，但第一版只把它当作可选的分布式互斥锁预留位，不作为运行前提。为了不让机制焊死，调度器对业务只暴露一个「tick(now) → 本次判定与投递摘要」的接口：将来换成 APScheduler、arq 甚至外部 cron 调一个 tick 接口，都只需要替换调度宿主而不改规则与投递逻辑。**如果将来多实例部署**，必须在外层加互斥（Redis 锁或只让一个实例跑调度），这一点要写进部署文档，而不是留给下一个人猜。

**幂等（本 spec 唯一负责，其他特征不得重复实现）：** 投递记录的唯一键是（用户、规则代码、本地日期、通道）。写入采用「唯一约束 + 冲突即跳过」的语义，重复 tick、进程重启、手动重跑、失败重试都只能在**同一条记录**上更新状态，绝不新建第二条。tick 本身也要保证「同一天同一规则同一通道」只产生一条记录；失败重试是针对已存在记录的重试次数与状态流转，不是重新生成。

**规则引擎是纯函数。** 输入：用户本地日期与当前时刻、今日是否为训练日、今日是否已打卡、最近一次打卡日期、本周完成次数与周目标、是否存在训练计划/体型分析、用户提醒偏好（类型开关、免打扰区间、每日上限）、该规则最近一次投递日期。输出：候选提醒列表（规则代码 + 渲染所需参数 + 目标跳转），以及被判定为「不该发」的原因（用于运营排查）。规则判定与「今天该不该发这条」必须可以在不碰数据库、不碰时钟的情况下单测。

**规则集合与频率：**

- `daily_training`：训练日、当前时刻已过提醒时刻、当天无打卡 → 发；提醒时刻默认 19:00（本地时间），可由配置覆盖。
- `rest_day_note`：休息日、已过提醒时刻 → 发差异化恢复日提醒；默认关闭（用户可在设置里打开），避免休息日仍被「催」。
- `recall_inactive`：距最近一次打卡 ≥3 天 → 在 3、7、14 天各发一次；≥14 天后降为每 7 天一次的节奏上限，且永不在用户已连续 7 天内出现过任何提醒时叠加发送。
- `weekly_goal_hit`：本周完成次数达到周目标 → 每周期仅一次，且只在达成当天发。
- `weekly_goal_gap`：周期末（默认周日）仍有缺口 → 每周期最多一次。
- `onboarding_nudge`：无训练计划或无体型分析、且注册满 1 天 → 引导去完成分析/生成计划；发满 2 次后不再发。

**优先级与每日上限：** 同一用户在同一天命中多条候选时，按 召回 > 每日训练 > 周目标 > 引导 的顺序裁剪，超出每日上限（默认 2 条）的候选标记为跳过并记录原因，而不是静默丢弃——运营需要能回答「为什么这个人今天没收到提醒」。

**免打扰：** 免打扰区间按用户本地时间解释，支持跨零点（如 22:00–08:00）。落在免打扰内且仍在当日窗口内的提醒顺延到区间结束后；已超出当日窗口的标记为跳过，不跨日补发。

**数据模型：**

- 提醒偏好：每个用户一条（唯一），含各规则开关、免打扰开始/结束（本地时间）、每日上限、时区标识（第一版默认 Asia/Shanghai，字段先留出）。
- 投递记录：用户、规则代码、本地日期、通道（in_app / web_push）、状态（sent / failed / skipped / suppressed）、渲染参数摘要、错误摘要、时间戳；唯一键见「幂等」。这条记录同时充当**站内收件箱**（channel=in_app 且 status=sent 的行即用户可见的通知），因此不为收件箱再建一张表，避免两套状态不一致。
- 推送订阅：用户、通道、订阅对象（endpoint + keys）、是否有效、最后成功时间、失效原因。订阅失效（推送服务返回 404/410）时标记失效并不再重试该订阅。

**时间与窗口：** 所有「今天/昨天/本地日期」判断都走同一个本地日期工具，禁止用服务器 UTC 日期直接比较（当前打卡统计里已有 UTC 日期与本地日期混用的隐患，本节要求新代码不重复）。每个每日任务有一个「当日有效窗口」（建议：提醒时刻起 4 小时内）；服务重启或机器休眠后若仍在窗口内则补发一次，超出窗口标记跳过。

**通道适配器接口：** 一个统一的投递函数：输入用户、通道、渲染好的通知，输出结果（成功 / 可重试失败 / 永久失败），实现方对内是站内写入，对外是 Web Push（可选）。业务规则只依赖这个接口，因此新增邮件/短信/微信模板消息时不需要动规则。**轻通道与重通道的分界与 tick 边界一致**：站内通道是一次本地写入，属于 tick 内的轻量操作；Web Push 这类需要网络调用、可能超时、需要重试的通道**不在 tick 内直接发送**，tick 只写投递记录并投递一条持久作业，由任务持久化 spec 的 DB 驱动执行器负责实际发送与重试（作业状态可查询，失败的投递记录标 failed 而不是重新生成新记录）。Web Push 的具体实现依赖浏览器订阅对象与 VAPID 密钥配置；密钥缺失时该通道整体标记禁用（配置层），不影响站内通道。

**接口契约（全部要求登录 + 本人校验；管理员只有聚合只读）：** 通知列表（分页、可只看未读、返回未读数）、单条标已读、全部标已读、读取提醒偏好、更新提醒偏好、推送订阅登记与注销、推送通道可用性查询（是否配置了服务端密钥、当前订阅是否有效）、管理员提醒运营概览（今日投递量、失败量、按规则分布、召回后 7 日回访数）。普通用户只能读写自己的通知与偏好；管理员概览不得包含任何用户的通知正文。

**前端：** 顶栏铃铛 + 未读数（页面聚焦时刷新，不做 SSE/WebSocket 长连接，第一版以简单可靠为先）；通知列表页支持未读筛选与批量已读；偏好设置放在个人设置区内，保存前在客户端做一次合法性校验（免打扰开始≠结束、每日上限 0–5、至少保留一种通道）。未读数汇总、偏好校验与「通知该跳到哪个页面」的映射都放在纯函数里，便于单测。

**文案：** 提醒正文以模板 + 变量插值为主（角色口吻遵循 West Coast Slang，但每条必须包含明确动作与可跳转目标）；LLM 可选，仅用于召回类提醒的个性化一句话，LLM 失败或超时一律回退模板，且模板必须让用户不需要任何 AI 能力也能看懂要做什么。

### 落地修订（工单 33：调度宿主 + 投递记录 + 收件箱）

- **投递记录即收件箱，不再建第二张表**：`reminder_deliveries` 一行同时是幂等事实与用户可见通知；`payload` 里存渲染结果（title / body / target_path / 规则参数），收件箱直接投影，不在读取时重新渲染——否则规则文案一改，历史通知会「变脸」。未读即 `read_at is null`（仅 `channel=in_app` 且 `status=sent` 的行进入收件箱）。
- **唯一键是幂等契约的物理保证**：（user_id, rule_code, local_date, channel）。写入走 SAVEPOINT + 唯一键冲突即跳过，冲突只回滚这一条，不会让整次 tick 的事务一起失效；tick 摘要里区分 `delivered` / `duplicates` / `failed`。
- **调度宿主先睡后 tick**：启动瞬间不写业务数据，滚动发布时不会和旧实例抢同一条记录；`start()` 对重复调用幂等，`stop()` 幂等且等待任务真正结束（先停调度再释放连接池）。单次 tick 异常被捕获并记 `reminder.tick.failed` error 事件，长任务不死；进程内标志位做可重入保护。事件按 `domain.action.result` 命名：`reminder.tick.completed` / `reminder.tick.failed` / `reminder.delivery.failed`。
- **tick 固定三条读查询**：用户、当前 active 计划、当日打卡各一次取齐后在内存里逐用户判定；逐用户查询会让 60 秒一次的 tick 成本随用户数线性增长，违背「轻量 tick」的边界。
- **手动 tick 是管理员入口，不是公开端点**：`POST /api/notifications/tick` 仅管理员可调，支持注入 `at` 时刻（运维补跑/排障/测试确定性），不返回任何用户通知正文。普通用户与未登录一律 401/403。
- **tick 内的训练日判定复用计划的周几查询**：新增 `PlanService.get_workout_for_weekday()`，今日三态与提醒共用同一口径，避免「提醒说今天没练、统计说今天练了」。本地日期统一走共享的本地时间工具（见「相关文件」），不再拿服务器日期冒充用户本地日期。
- **时区依赖显式化**：Windows 没有系统 tzdata，`zoneinfo` 解析 `Asia/Shanghai` 会失败，因此依赖里新增 `tzdata`（部署级时区第一版固定 `Asia/Shanghai`）。
- **本票只实现第一条规则**（`daily_training`：训练日 + 已过提醒时刻 + 当天未打卡），规则是纯函数、可脱离数据库与时钟单测；其余五条规则、偏好、免打扰与每日上限归工单 34，调度与投递链路不需要改。
- **收件箱有页面，不只是接口**（正文要求「用户能在应用里看到通知列表与未读数」）：`/notifications` 页面提供未读筛选、单条点击标已读并跳转、全部已读与空态；侧边栏新增「通知」入口。铃铛角标挂在顶栏属于工单 34 的偏好/入口收口，本票只保证数据与页面可用。

### 落地修订（工单 34：六条规则 + 每日上限 + 免打扰）

- **规则判定返回「候选或跳过原因」而不是布尔**：每条规则输出 `RuleOutcome(candidate | skip_reason)`，因此「今天为什么没收到」这类运营问题有结构化答案，而不是靠猜。优先级写死为 召回 > 每日训练 > 恢复日 > 周目标 > 引导（`RULE_PRIORITY`），裁剪只在服务层做，规则本身互不知道对方。
- **当日窗口语义收紧为三段**：早于提醒时刻 = 尚未到点（不落记录）；窗口内 = 可投递；晚于窗口结束（提醒时刻 + 4 小时）= 记 `outside_daily_window` 跳过、不跨日补发。这条区分避免了凌晨 tick 为每个用户刷一条「今日未提醒」的噪声记录。
- **免打扰是「顺延」而不是「丢弃」**：落在免打扰区间内、但区间结束仍在当日窗口内时，本轮**不落任何记录**，由免打扰结束后的 tick 正常投递；区间结束已越过当日窗口时才写 `quiet_hours` 跳过记录。免打扰区间支持跨零点（如 22:00–08:00）。
- **每日上限只数「真正发出去的」**：上限按当日 `status=sent` 的条数计算，跳过记录不占额度；超出上限的候选按优先级从低到高写 `daily_cap` 跳过记录，用户看不到它们（收件箱只投影 `status=sent`）。
- **周目标类提醒每周期最多一次**：达成提醒在达成当天发一条，同周期后续 tick/次日通过「本周已发过该规则」判定为 `already_sent_this_week`；缺口提醒只在周期末（默认周日）且仍有缺口时发，正文含「还差 N 次」。
- **召回阶梯与叠加抑制**：距上次打卡 3 天、7 天各一次，14 天起每 7 天一次（AC2 为准）。「不叠加」只约束**同一天**：当天已经提醒过一次时，召回记为 `already_reminded_today` 跳过，避免一天两条催促；历史上收到过提醒不影响阶梯触发。从未打卡的用户不进入召回（由引导规则负责）。
- **偏好是一对一懒创建**：没有记录时读取返回缺省值且不写库，首次保存才创建；更新为整份替换，校验（`HH:MM` 格式、开始≠结束、每日上限 0–5、周目标 1–14）在写入前完成，非法值返回 422 且已存偏好保持不变。时区第一版仍为部署级，接口只读不写。
- **跳过记录有内部查询入口**（AC5 的「可查询」）：`GET /api/notifications/deliveries` 仅管理员可用，按用户 / 状态 / 本地日期区间分页查询投递记录，返回 `skip_reason`，不返回通知正文；这是运营回答「他今天为什么没收到」的入口，公开收件箱仍然只看得到 `status=sent` 的通知。
- **用户主动关闭的规则不写跳过记录**：关闭是用户选择，不是系统拒绝；跳过记录只承载系统侧的裁剪原因（窗口、免打扰、上限、本周已发、近期已提醒、引导用尽），避免把用户偏好污染成运营异常数据。
- **tick 的读查询固定为常数条**：用户、当前计划、今日打卡、历史最近打卡、本周次数、分析记录、偏好、近 30 天投递、引导已发次数各一次，全部在内存里逐用户判定；仍不发起任何外部网络调用。

## Testing Decisions

好测试只断言**外部可见行为**：给定时间与数据，跑一次调度后「哪些通知真的产生了、哪些被幂等拦住、哪些被上限或免打扰裁掉」，以及用户能看到的列表、未读数与偏好生效结果。绝不断言调度器内部的 sleep 精度、任务对象或 ORM 语句。

**后端最高 seam：FastAPI 路由层 + 可注入的时钟与手动 tick 入口**，用 httpx ASGITransport + `dependency_overrides`（隔离 SQLite 与假时钟），prior art：鉴权守卫路由测试（ASGITransport、从用户 ID 构造 JWT 的 helper、含越权与管理员用例的写法，位置见「相关文件」）。时钟与 tick 通过依赖覆盖注入，测试里「前进到明天 19:05 再 tick 一次」，因此不需要真的等待，也不会出现不稳定用例。

为什么这是最高且够用的 seam：提醒的产品行为完全可表达为「时间 + 数据 → 投递集合 + 用户可见列表」，路由层就能观察全部结果；再往下测规则函数把测试绑到实现结构，再往上就没有更靠近用户的自动入口（真的起进程等定时器既慢又不稳）。规则纯函数另有极薄单测作为补充，但主要契约由路由层持有。

必须在路由层覆盖的外部行为：训练日未打卡 → tick 后出现 1 条站内通知且未读数为 1；同一天再 tick 一次 → 仍只有 1 条（幂等）；当天已打卡 → 不产生训练提醒；休息日 + 类型关闭 → 不产生；休息日 + 类型打开 → 产生恢复日提醒；距上次打卡 3 天 → 召回，6 天 → 无（阶梯），7 天 → 召回；用户关闭某类提醒后该类不再产生；免打扰区间内的候选被顺延，跨日超出窗口标记为跳过；同日命中三条候选且上限为 2 → 只发 2 条且被裁的有跳过记录；标已读/全部已读后未读数正确；越权读他人通知或改他人偏好 → 403，未登录 → 401；非管理员访问运营概览 → 403。另外验证一次「投递失败」路径：站内写入成功但通道报错时，该记录状态为 failed 且**不会**在下次 tick 重复生成新记录。与执行器的分工也要被外部行为锁定：Web Push 通道打开时，tick 只产生投递记录与一条待执行的持久作业（作业状态可查），断言 tick 期间**没有**发生外部发送调用（用替身断言未被调用），实际发送与重试由执行器一侧负责——执行器自身的认领/租约/重试不属于本 spec 的 seam。

**前端最高 seam：纯 TS 判定函数**（未读数汇总、免打扰区间合法性与跨零点校验、每日上限校验、通知 → 目标页面的映射），prior art：体型分析旅程的纯函数与其单测（纯函数输入输出式单测，位置见「相关文件」）。这些判断是产品规则的全部，组件只是展示，因此不需要为它们写更低层的 hook 测试。

**页面级测试用 vitest + jsdom**：MemoryRouter + mocked `useAuth` + mocked API 模块，断言铃铛上的未读数、通知列表空态与已读后红点消失、偏好保存时非法的免打扰区间被拦下并给出提示、点击通知后路由跳转到预期路径。prior art：API Key 网关的 jsdom 页面测试（MemoryRouter + mocked auth + 断言路由与查询串，位置见「相关文件」）。不断言 className，不测第三方组件内部。

## Further Notes

**读代码时确认的现状问题：**

1. 依赖清单里没有任何调度库，应用生命周期钩子只做「建表 + 确保对象存储桶」，没有任何周期任务的挂载点。这意味着本特征必须新增一个启动期挂载的调度宿主，并且要考虑它与「开发环境热重载」的交互（uvicorn reload 会重启进程，调度任务要能干净取消与重建，不能出现双跑）。
2. 打卡统计与「今日」判断直接使用服务器本地日期与 `datetime.now()`，没有统一的本地日期抽象；提醒是按用户本地日界生成的，如果不先抽出统一的日期工具，跨零点与跨时区会出现「提醒说今天没练，但统计说今天练了」的矛盾。
3. 前端完全没有通知概念（侧边栏只有四个入口），也没有任何可复用的「未读/列表/设置」模式，因此这块 UI 是从零建；同时需要注意个人设置区当前并非独立页面结构，偏好设置放进去之前要先确认它的信息层级。
4. 打卡数据、计划数据都已有「按用户查询最近记录」的能力，召回与周目标的判定可以直接复用既有统计口径（连续天数、本周次数），不要另起一套算法，否则两处数字会打架。

**方向性决策记录：**

- 为什么不用 Celery：没有 broker 依赖、单实例部署、要能一条命令跑起来；用进程内 asyncio tick + 幂等写入已足够，且把「换成什么」留给一个极窄的调度接口。
- **调度与执行是两件事，边界写死**：tick 是「周期性触发器」，只做规则判定 + 投递记录写入，轻量、可重入、幂等；一次性作业的执行、租约、心跳与失败重试归任务持久化 spec 定义的 DB 驱动执行器（认领 / 心跳 / 成功 / 失败 / 回收，契约见同批次「体型分析任务持久化与可恢复执行」spec 的「可靠执行器契约」一节），本 spec 不重复定义执行器契约，也**禁止 tick 内自己开协程跑 LLM 或外部网络重活**——需要异步重活时投递持久作业，由执行器消费。
- 第一版通道以站内收件箱为主，因为站内通道不需要用户授权、不需要 VAPID 密钥、测试可以完全确定地断言；Web Push 作为开关式增强，允许在未配置密钥的环境里整体关闭。
- 投递记录同时充当收件箱：少一张表、少一次状态同步，代价是通道维度必须进唯一键。
- 每日上限的裁剪结果要落成 skipped 记录而不是丢弃，是为了让运营概览能回答「为什么没发」——这类可解释性比省几行数据更值钱。
- 重启补发的窗口给 4 小时：既能覆盖滚动发布，又不会在深夜补一条早上该发的提醒。

> **迁移约定**：本 spec 引入了新的持久实体（提醒投递记录，兼作站内收件箱）与用户提醒偏好字段，属于改表，必须遵守全组统一约定——见 `analysis-task-persistence` spec 的「迁移与数据模型落地约定」一节（ORM 为唯一事实源、迁移与模型手写对齐、按交付追加 revision、可回滚、方言判断只出现在兼容层）。本 spec 不另立迁移约定。

## 落地修订（工单 35）

Web Push 重通道的落地取舍：

1. **两张表**（迁移 0016）：`push_subscriptions`（用户、endpoint 唯一、p256dh/auth、
   是否有效、最后成功时间、失效原因）与 `push_jobs`（投递记录唯一、订阅、状态
   pending/sent/failed、尝试次数、`claimed_at` 租约）。两者都不存通知正文之外的隐私数据。
2. **订阅接口**：`GET /notifications/push/status` 返回 available / subscribed /
   subscription_count，并在通道可用时返回 VAPID **公钥**（浏览器订阅需要它）；
   `POST .../subscribe` 按 endpoint upsert——同一账号重复登记只更新密钥并重新激活，
   **同一 endpoint 属于其他账号时返回 409 `push_endpoint_in_use`**，绝不静默转移归属；
   `DELETE .../subscribe` 软失效本人全部订阅。VAPID 三项配置不齐时通道整体不可用，
   登记返回 409 `push_unavailable` 且不落任何订阅行；站内通道完全不受影响。
3. **tick 边界**：只有站内投递真正写入（status=sent）之后，且通道可用、用户有有效订阅时，
   才追加一条 `reminder_deliveries(channel=web_push,status=pending)` 与一条 `push_jobs`；
   tick 内零外部发送调用，跳过/被裁的候选不入队。重复 tick 由投递记录唯一键与作业
   `delivery_id` 唯一键双重幂等。
4. **执行器与租约**：`PushJobExecutor` 用条件 UPDATE 抢租约（`claimed_at`，`status=pending`
   且未占用），发送前释放会话与事务，发送在 `asyncio.to_thread` 中执行，结果在短事务回写；
   崩溃遗留的旧租约在下一轮回收。成功 → 作业/记录 sent、订阅最后成功时间；404/410 →
   作业/记录 failed、订阅失效（`endpoint_gone`），后续 tick 不再投递；其他失败重试到上限
   （3 次）后 failed。作业与订阅归属不一致时拒绝发送（`subscription_owner_mismatch`）。
5. **worker**：`PushJobWorker` 在 lifespan 启停，先睡后跑、可重入保护、异常不杀循环；
   **仅当 `REMINDER_ENABLED` 且 VAPID 配置齐全时才启动**，通道禁用时不做无意义的轮询。
6. **配置**：`VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`、
   `PUSH_JOB_TICK_SECONDS`(10)、`PUSH_JOB_MAX_ATTEMPTS`(3)、`PUSH_JOB_BATCH_SIZE`、
   `PUSH_SEND_TIMEOUT_SECONDS`。`pywebpush` 依赖随本票加入（同时带来 `cryptography` 升级）。
7. **已知取舍**：tick 第三条读查询之外在配置了推送时多一条订阅批量查询（工单 33 的
   「固定三条」在开启重通道后放宽为四条，已在代码注释与本修订记录）；入队失败是
   best-effort（只记事件，不生成可重试记录），当天的推送可能因此缺失一次；执行器无
   跨实例租约，发送后、回写前崩溃会按 at-least-once 重发；每个用户只取最新一条有效
   订阅（多设备扇出不在本票范围）；管理员投递列表目前仍只展示站内通道。
