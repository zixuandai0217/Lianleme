feat: add resumable workout sessions, session page and admin user detail

Tickets 22 / 23 / 37.

Workout session (22)
- New `workout_sessions` aggregate (migration 0008): one session per user per
  local date, status machine in_progress / completed / abandoned, exercise detail
  stored as JSONB keyed by "exercise index + set index". Current exercise / set
  are derived from the detail rather than duplicated as columns.
- POST /sessions/start returns the session, the first exercise and the planned
  total sets; a same-day second call returns the same session (unique key plus
  concurrent-conflict fallback). Rest day / no plan return 409 with stable codes
  `rest_day` / `no_plan` and create nothing.
- POST /sessions/{id}/sets is a set-wise idempotent operation: re-submitting a
  completed set returns 200 without moving progress, submitting out of order is
  422, and the JSONB detail is deep-copied before assignment so SQLAlchemy
  actually persists it.
- POST /sessions/{id}/skip requires a reason that is non-blank after trimming
  (422 otherwise), keeps the exercise in the detail as skipped, and never adds
  to the completed set count.
- GET /sessions/current resumes the newest in-progress session even when it
  started before midnight (a session continued past 00:00 keeps its start date);
  a session idle for 12 hours converges to abandoned on read and is read-only.
  Ownership is enforced per session (403) and unauthenticated calls are 401.

Session page (23)
- New /session page: overall progress, current exercise with "第 2/4 组", a rest
  countdown driven by that exercise's rest_seconds, a skip dialog that cannot be
  submitted without a reason, and the "收尾并打卡" entry only after every
  exercise is handled. Non-in-progress sessions render read-only.
- State is never recomputed locally: the page renders the server view, so a
  refresh restores the same progress. Rest day and no-plan empty states reuse the
  ticket-07 three-state helper and differ from each other; neither shows 开始训练.
- The dashboard today card gains a 开始训练 entry; the session page's check-in
  action navigates to "/?checkin=1" and the dashboard opens its check-in dialog
  from that URL (cleared after opening, covered by a jsdom test).

Admin user detail (37)
- GET /api/admin/users/{user_id} aggregates profile, latest body analysis,
  current plan + latest adjustment (reusing the ticket-20 projection), 90-day
  check-in series with streak, 90-day weight series, a fixed-vocabulary timeline
  (paginated, derived from existing rows, never fabricated) and AI usage.
- `sections` accepts comma-joined and repeated forms; unknown names are 422; a
  section that was requested but has no data is null while unrequested sections
  are omitted, so "not requested" and "no data" stay distinguishable.
- Masking happens in the API layer: masked openid/email, key status only, and a
  whole-response test proves raw contacts, password hashes and ciphertext never
  appear. 401/403/404 covered; no migration needed.
