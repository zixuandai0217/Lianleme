# ADR-0010：姿态会话用进程内内存而非持久化

## 状态

已采纳（工单 40，配套 `pose-correction` spec）。

## 背景

姿态纠错需要客户端以 3–5 fps 连续上行骨架关键点，服务端把序列按动作周期切段，再把
完整周期交给识别与评估节点。关键点序列是**生物特征数据**：它足以还原一个人的体态与
动作习惯，既不属于分析结果，也不该为了「以后可能有用」而长期留存。另一方面，一次
纠错会话只有几分钟，结束后序列本身没有再次读取的业务需求。

如果按常规做法把帧落到数据库或对象存储，会同时付出三种成本：存储成本随训练次数线性
增长；隐私面从「结果」扩大到「原始动作轨迹」，删号与导出都要额外处理；而窗口切分是
有状态的流式算法，落库反而要在每次请求里重建窗口。

## 决策

### 1. 会话状态只活在进程内存

`PoseSessionStore` 用字典保存会话：会话标识、所属用户、机位、未成周期的窗口、已完成
周期与计数。**不落库、不写文件、不写日志、不进异常堆栈**。进程重启即全部失效，这是
预期的隐私行为，不是可用性缺陷。

### 2. 用 TTL 与上限代替持久化的生命周期

- 空闲 30 分钟过期（每次成功请求续期），过期按 404 处理；
- 每用户最多 3 个进行中会话，避免单客户端无限开窗造成内存压力；
- 单会话 3600 帧、单批 60 帧硬上限，超出返回 4xx，绝不静默截断；
- 会话结束后帧与窗口立即丢弃，只保留周期计数与质量统计。

### 3. 单进程假设写进契约

内存会话要求同一会话的请求落到同一进程。部署为多 worker 时必须配置粘性路由，否则
跨进程请求会得到 404。这一条在工单 40 的落地修订与部署文档中同时注明；真正的多实例
共享会话属于后续能力，若要做，应另立 ADR 并接受「加密持久化」的隐私成本。

### 3.1 日志只允许短哈希会话标识

结构化日志允许携带会话短标识（会话 id 的 SHA-256 前 8 位）、周期序号、耗时、错误分类与规则命中类型，用于排障与成本核算；不允许坐标、角度序列、帧内容或可还原到单次动作的明细。短哈希不可逆且不能用于跨日志关联出原始会话，这是「不写日志」与「可运维」之间的显式取舍。

### 4. 时钟用单调时间

TTL 用 `time.monotonic`（测试注入时钟），不用墙钟：训练中的系统时间调整不应让会话
提前过期或永不释放。

### 5. 模型调用闸门

不成周期、或周期质量不可评估（可见度低、出画、多人入镜）时，只返回提示与计数，
**不调用任何模型**。这条闸门在工单 40 就固化为可断言的行为（`model_calls == 0`），
避免后续接入识别/评估后把算力花在无效序列上。

## 后果

- 会话不可跨设备、跨进程恢复：用户换设备或服务重启需重新开始一次纠错。
- 隐私面最小：没有原始关键点的持久副本，删号与数据导出不涉及姿态序列。
- 多 worker 部署需要粘性路由；内存上限由每用户会话数与帧数共同兜底。
- 工单 43 若要把聚合结果落库，只持久化「评分 + 问题项 + 周期计数」，不回填关键点。
