# ADR-0008：运行观测契约（请求关联、结构化日志、脱敏）

- 状态：已接受（2026-11-01）
- 背景文档：[观测基线工单](../../.scratch/observability-baseline/issues/03-structured-logs-and-request-id.md)、[观测基线规格](../../.scratch/observability-baseline/issue.md)

## 背景

在本次改造之前，后端的「运行事实」几乎不可用：

- 应用从未配置 logging 格式，全局异常处理器只把异常翻译成 500 响应而不记录堆栈——线上出现 500 时没有任何线索。
- 一条请求跨多个服务与后台任务时无法串联：日志里没有请求标识，任务日志也没有继承发起它的请求。
- 谁在写日志、写成什么格式全凭调用点自觉，同一语义有多个字段名（`user` / `user_id` / `uid`），敏感信息没有统一防线。

## 决策

1. **请求关联**：入口生成或沿用 `X-Request-ID`（入站值需通过格式校验，非法值不原样回显，改为新生成），全链路日志与响应头都带同一个标识；后台任务在创建时记录标识、执行时重新注入，因此任务日志能对回它是由哪次请求产生的。
2. **单行结构化日志**：一条日志一行 JSON，字段名集中定义为常量，禁止同义别名；开发环境允许人类可读的单行格式，但两种格式的字段集合必须一致。
3. **事件分级**：请求完成、慢请求、异常、SSE 结束、后台任务生命周期各自有稳定事件名；4xx 记 warning、5xx 与未捕获异常记 error。
4. **统一脱敏**：由日志层统一处理，而不是每个调用点自觉——禁止字段名整字段丢弃，密钥样式（`sk-*`、Bearer、JWT）、图片 data-URI、长 base64 值一律替换为占位符，递归处理嵌套结构。
5. **健康检查分层**：存活检查只回答「进程还在吗」，就绪检查逐项报告依赖状态；必需依赖不可用时就绪检查返回 503，且不掩盖其他依赖的结论。

## 影响

- 所有日志调用点共享同一套字段常量与事件名；新增日志字段要先加常量再用，避免三处维护同一枚举。
- 请求中间件成为最外层 ASGI 中间件，因此它对流式响应也能观察到开始/结束/中断。
- 错误码与字段名是跨端契约（前端据此展示稳定提示），改动需要同步前端与规格。

## 被否决的方案

- **引入第三方日志/追踪 SDK**：当前是单实例部署，标准库 `logging` + `contextvars` 已足够；引入 SDK 会把「一条命令跑起来」变成运维负担。
- **在每个调用点手动脱敏**：无法保证覆盖，且新增调用点必然遗漏。
