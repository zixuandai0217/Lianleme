# ADR-0002: 选择 MediaPipe 进行姿态检测

## 状态

已接受 (2026-10-27)

## 背景

当前项目缺少**动作质量评估**能力，训练计划生成和调整都基于用户主观上报的完成情况，无法：
- 检测动作是否标准（如深蹲膝盖内扣、硬拉腰部代偿）
- 提供实时纠错反馈
- 量化动作进步（如深蹲深度从 90° 提升到全蹲）

为了提升项目的技术亮点和实用价值，需要引入**姿态检测**能力。作为简历项目，需要考虑：
1. **技术栈多样化**：展示计算机视觉 + LLM 的多模态能力
2. **实时性**：训练中实时反馈，不能等几秒才出结果
3. **部署成本**：个人项目，需要在浏览器/移动端运行，避免 GPU 依赖
4. **开发周期**：2 周 MVP，需要快速集成

## 决策

选择 **Google MediaPipe Pose** 作为姿态检测方案。

### 核心特性

- **33 个关键点**：覆盖面部、上肢、躯干、下肢
- **轻量级**：可在浏览器（WebAssembly）和移动端运行
- **实时性**：30 FPS，延迟 < 50ms
- **无 GPU 依赖**：CPU 即可运行（但支持 GPU 加速）
- **开源免费**：Apache 2.0 许可证

### 技术架构

采用**混合部署模式**（前端实时 + 后端深度分析）：

```
前端 (MediaPipe.js)
  ↓ 实时提取关键点 (30 FPS)
  ↓ HTTP 短轮询传输（每秒 3-5 帧）
后端 (Python FastAPI)
  ↓ 动作周期检测 (2-4 秒/周期)
  ↓ LLM 深度分析（关键点序列 → 自动识别动作类型 + 质量评估）
  ↓ 生成纠错反馈
  ↓ TTS 语音播报 + 视觉高亮
前端显示
```

### 数据流

1. **前端**：
   - MediaPipe.js 从摄像头实时获取视频流
   - 提取 33 个关键点的 3D 坐标 `(x, y, z, visibility)`
   - 通过 HTTP 短轮询发送到后端（每秒 3-5 帧）

2. **后端**：
   - 接收关键点序列
   - **动作周期检测**：识别一个完整动作（如深蹲下蹲→站起）
   - **LLM 分析**：发送关键点序列 → LLM 自动识别动作类型 + 生成质量评估
   - **反馈生成**：文字 + 语音（TTS）+ 视觉标注（叠加箭头/圈出错误部位）

3. **前端显示**：
   - 实时绘制骨骼图（33 个关键点连线）
   - 收到后端反馈后显示纠错提示（周期结束后 1-2 秒内）

### 关键点精简策略

虽然 MediaPipe 输出 33 个点，但：
- **前端**：全部 33 个点获取（保持灵活性）
- **可视化**：只绘制运动相关的 12-16 个点（肩、肘、腕、髋、膝、踝）
- **后端分析**：保留全部 33 个点供 LLM 深度分析

## 后果

### 优势

1. **技术栈多样化**
   - 展示前端计算机视觉能力（WebAssembly）
   - 展示多模态融合（视觉关键点 + LLM 语义理解）

2. **用户体验优秀**
   - 实时反馈（30 FPS 骨骼图 + 周期结束后语音纠错）
   - 无需下载额外 App，浏览器即可使用

3. **部署成本低**
   - 前端运行，不占用服务器 GPU
   - 后端只需 CPU 运行 LLM（已有 LLM 调用基础设施）

4. **开发周期短**
   - MediaPipe 官方提供完整的 JavaScript SDK
   - 2-3 天即可完成前端集成 + 后端 WebSocket

### 权衡

1. **精度限制**
   - MediaPipe 是 2D 姿态检测（虽然输出有 z 坐标，但深度精度有限）
   - 某些动作（如侧向拍摄的硬拉）可能检测不准
   - **缓解方案**：要求用户正面/侧面拍摄（UI 引导），后续可扩展多视角

2. **浏览器兼容性**
   - 需要 WebAssembly 支持（现代浏览器均支持）
   - 摄像头权限需要 HTTPS 或 localhost
   - **缓解方案**：提供兼容性检测，不支持时降级为上传视频分析

3. **网络依赖**
   - HTTP 短轮询在本地运行时延迟可控（< 100ms）
   - 网络差时延迟增加
   - **缓解方案**：前端显示骨骼图不依赖后端，只有纠错建议需要网络

4. **动作识别准确性**
   - MediaPipe 只提供关键点，不识别动作类型
   - 依赖 LLM 从关键点序列推断动作，可能识别错误
   - **缓解方案**：要求用户保持标准起始姿态（如深蹲站立位），降低识别难度；错误识别时用户可重新开始

## 备选方案

### 方案 A：OpenPose

**特点**：
- 精度更高（25 个关键点，但模型更大）
- 需要 GPU（CUDA）
- 部署复杂（需要编译 C++ 库）

**未采用原因**：
- 部署成本高，无法在浏览器运行
- 个人项目没有 GPU 服务器
- 开发周期长（需要搭建推理环境）

### 方案 B：YOLO-Pose

**特点**：
- 基于 YOLOv8，速度快
- 可部署到移动端
- 精度和速度平衡

**未采用原因**：
- 需要自行训练或使用预训练模型（额外学习成本）
- 浏览器部署需要 ONNX Runtime（集成复杂度高于 MediaPipe）
- MediaPipe 官方支持更完善

### 方案 C：多模态 LLM 直接分析

**特点**：
- 无需额外模型，直接发送视频帧给 GPT-4V / Qwen-VL
- 实现简单（复用现有 LLM 基础设施）

**未采用原因**：
- **成本高**：每帧都调用视觉 LLM，费用不可控
- **延迟高**：视觉 LLM 推理慢（2-5 秒），无法实时反馈
- **技术栈单一**：无法展示计算机视觉能力，全靠 LLM

### 方案 D：不做姿态检测

**未采用原因**：
- 缺少视觉亮点，技术深度不足
- 与豆包视频等产品相比无差异化
- 无法支撑"AI + 健身"的完整闭环
