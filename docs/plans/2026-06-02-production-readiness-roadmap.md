# 练了么：正式产出前优化建议与未完成功能路线图

## 1. 当前状态判断

当前项目已经具备可演示的主链路：

- 登录
- 体型分析
- 训练计划生成
- AI 陪练
- 训练打卡
- 体重记录
- 管理后台

从运行结果看，前后端可以启动，主页面可以进入，首页和 AI 陪练页能够展示；`npm run typecheck` 通过，说明基础类型约束尚可。

但从正式产出的标准看，它还处于 **Alpha / Demo 可体验** 阶段，不适合直接投入生产。核心原因不是“功能不够多”，而是“安全、可靠性、交付闭环和工程质量还不达标”。

结论：

- 如果目标是“内部演示/找方向”，当前状态已经够用。
- 如果目标是“真实用户可长期使用”，应先做生产化收敛，再扩功能。
- 正确顺序应该是：**先补 P0 稳定性与安全，再做 P1 产品闭环，再做 P2 增长功能。**

## 2. 生产化上线前的关键短板

### 2.1 认证与权限基本未落地

这是当前最严重的问题。

虽然前端会保存 `token`，后端也会签发 JWT，但后端接口没有看到统一的“当前用户”鉴权依赖；绝大多数接口直接信任 `user_id` 路径参数或请求体参数。也就是说，只要知道别人的 `user_id`，理论上就可能读写别人的数据。

证据：

- JWT 只负责生成，没有看到解码与鉴权链路  
  [user_service.py](/Users/edy/Daizixuan/Lianleme/backend/app/services/user/user_service.py:96)
- 用户接口直接按传入的 `user_id` 读写  
  [user.py](/Users/edy/Daizixuan/Lianleme/backend/app/api/user.py:37)
- 前端只是把 token 放进请求头，但不能证明后端真正校验了它  
  [client.ts](/Users/edy/Daizixuan/Lianleme/web/src/api/client.ts:10)

正式产出前必须完成：

- 建立 `get_current_user()` 鉴权依赖
- 所有用户数据接口改为“当前登录用户只能访问自己的资源”
- 管理后台使用独立管理员鉴权
- `dev-login` 仅在本地开发保留，正式环境彻底禁用

### 2.2 邮箱登录已接入，正式认证能力仍需完善

Web 端已提供邮箱注册和密码登录，同时保留仅限开发环境的快速登录。正式发布前仍需补齐邮箱验证、密码找回和 token 生命周期管理。

证据：

- 登录页已提供邮箱注册和密码登录
  [login/index.tsx](/Users/edy/Daizixuan/Lianleme/web/src/pages/login/index.tsx)
- 后端已提供邮箱注册和登录接口
  [user.py](/Users/edy/Daizixuan/Lianleme/backend/app/api/user.py)
- `dev-login` 已限制为开发环境使用
  [user.py](/Users/edy/Daizixuan/Lianleme/backend/app/api/user.py)

正式产出前必须完成：

- 增加邮箱验证、密码找回和 token 刷新机制
- 设计首次注册与用户建档流程
- 去掉演示入口对正式环境的依赖

### 2.3 体型分析任务是内存态，不可恢复

体型分析任务状态保存在进程内 `_tasks` 字典中，后台任务用 `asyncio.create_task(...)` 跑。单机调试没问题，但正式环境会遇到以下问题：

- 服务重启后任务状态丢失
- 多实例部署时轮询不到正确任务
- 失败任务无法追踪与补偿

证据：

- 任务状态仅存在内存字典 `_tasks`  
  [vision.py](/Users/edy/Daizixuan/Lianleme/backend/app/api/vision.py:29)
- 分析任务直接 `asyncio.create_task(...)`  
  [vision.py](/Users/edy/Daizixuan/Lianleme/backend/app/api/vision.py:45)

正式产出前必须完成：

- 将任务状态落库
- 为任务增加状态机：pending / processing / completed / failed / expired
- 引入后台任务队列或至少可靠的异步执行器
- 历史分析记录与任务记录分离

### 2.4 图片与媒体资源未真正进入对象存储

项目已经写了 MinIO 客户端和 `upload_bytes`，但体型分析流程里并没有真正上传原图或标准化存档，只是把压缩后的缩略图 base64 存进数据库。

证据：

- 存储工具已经存在  
  [storage.py](/Users/edy/Daizixuan/Lianleme/backend/app/core/storage.py:36)
- 分析历史中保存的是 `image_thumbnail` base64  
  [vision.py](/Users/edy/Daizixuan/Lianleme/backend/app/api/vision.py:127)

正式产出前建议：

- 原图上传对象存储，数据库只存 URL / object key
- 缩略图异步生成
- 图片访问权限分级：用户私有、带签名、过期控制
- 增加内容类型、大小、分辨率校验

### 2.5 AI 陪练输出契约不稳定

实际运行页面时，AI 陪练页已经出现了原始 JSON 风格内容直接展示在聊天气泡里的情况。这说明“模型输出约束”和“前端渲染约束”没有真正闭环。

证据：

- 流式接口只要求自然语言，但前端对内容没有做结构化保护  
  [coach_graph.py](/Users/edy/Daizixuan/Lianleme/backend/app/services/ai/coach_graph.py:61)
- 前端直接逐块拼接字符串并渲染  
  [coach/index.tsx](/Users/edy/Daizixuan/Lianleme/web/src/pages/coach/index.tsx:69)

正式产出前建议：

- 明确两种模式只能二选一  
  1. 全自然语言流式  
  2. 全结构化事件流
- 推荐改为事件流：`message_chunk`、`actions`、`state`、`done`
- 前端快捷动作不要硬编码，应该用服务端真实返回
- 增加输出兜底清洗，避免代码块和 JSON 泄漏到用户界面

### 2.6 工程基线不够，缺少回归保护

当前工程验证结果：

- `npm run typecheck`：通过
- `npm run lint`：失败，共 7 个错误
- `uv run pytest`：0 个测试

这意味着当前没有足够的回归防护，代码可维护性和可上线性都偏弱。

主要信号：

- React hooks 规则报错
- 未使用变量
- Fast Refresh 规则问题
- 后端没有任何自动化测试

正式产出前必须完成：

- 让前端 lint 通过
- 为核心服务补测试：鉴权、计划生成兜底、体重记录、打卡、分析任务
- 至少覆盖主链路 smoke test
- 增加基础 CI：typecheck + lint + backend tests

### 2.7 管理后台与路由存在半成品

管理后台导航里存在 `/admin/users`，但实际路由只注册了 `/admin`，说明页面结构和实际功能还没有收口。

证据：

  [admin-layout.tsx](/Users/edy/Daizixuan/Lianleme/web/src/components/admin-layout.tsx:9)
- 路由只注册了 `/admin`  
  [App.tsx](/Users/edy/Daizixuan/Lianleme/web/src/App.tsx:88)

这类问题本身不算致命，但它说明项目里还有若干“看起来准备好了，实际上没闭环”的点。

## 4. 如果投入正式产出，建议如何优化

### 4.1 先做“收敛”，不要先做“扩张”

当前最容易犯的错误，是继续加饮食、课程、社区、成就等功能。但这会把一个还没稳定的 Alpha 扩成一个更难收口的半成品。

建议先把产品范围收窄成一条最短可成交付链路：

1. 用户登录
2. 完成档案填写
3. 上传照片做体型分析
4. 获得周训练计划
5. 按“今日训练”完成打卡
6. AI 陪练提供训练中反馈
7. 体重记录形成可见趋势

这条链路打通后，产品已经具备“明确价值闭环”：

- 有输入：照片、档案、训练数据、体重
- 有输出：分析、计划、陪练、调整
- 有留存抓手：打卡、趋势、提醒

### 4.2 生产化的重点不只是功能，而是约束

正式产出要建立的不是“更多页面”，而是约束体系：

- 权限约束
- 数据约束
- 任务约束
- 模型输出约束
- 资源生命周期约束
- 运营与审计约束

建议把这些非功能性要求写成上线门槛，而不是隐含在口头里。

### 4.3 产品体验上要减少“AI 感”，增强“教练感”

现在很多页面还在“工具型 AI 应用”的层面，而不是“有陪伴感的训练产品”。

可以优化的方向：

- AI 陪练不要泛泛聊天，要更强训练上下文
- 今日训练页要更明确：现在练什么、练到第几组、下一步干什么
- 打卡后要给出有解释的反馈，而不是单句鼓励
- 计划页要让用户看懂“为什么这样安排”

换句话说：用户不是想用一个大模型界面，而是想要一个真的能带他练下去的系统。

## 5. 推荐路线图

## P0：上线前必须完成（2 周左右）

目标：让产品具备“可对真实用户开放”的基础能力。

范围：

- 完成正式认证与鉴权
- 移除正式环境下 `dev-login`
- 为所有用户接口补权限校验
- 将分析任务状态持久化
- 原图接入对象存储
- 修复 AI 陪练输出契约与前端渲染问题
- 让前端 lint 通过
- 为核心流程补最小自动化测试
- 增加错误监控与结构化日志
- 增加生产环境配置与密钥校验

验收标准：

- 不能越权访问其他用户资源
- 服务重启后任务不会整体失忆
- 主链路出现错误时能追踪
- 前后端最小质量门可自动检查

## P1：形成可交付 MVP（2-4 周）

目标：让用户能顺畅完成一次“完整训练闭环”。

范围：

- 正式登录接入
- 首次建档引导
- 分析结果页增强解释
- 计划页增强“为什么这样练”
- 今日训练页增强组数推进与操作反馈
- 打卡后展示计划调整说明
- 体重页增加阶段性总结
- 接通提醒系统最小版

验收标准：

- 用户首次进入后，不需要人工解释也能走完主链路
- 用户能理解自己现在处于哪个阶段
- 用户能感知 AI 的建议不是随机回答

## P2：增长与运营（4-8 周）

目标：把产品从“能用”提升到“能增长、能管理”。

范围：

- 用户行为埋点
- 漏斗分析
- 留存与召回策略
- 后台筛选/搜索/导出
- 周报/月报
- 训练成就体系
- 多阶段对比分析
- 饮食建议模块

## 6. 建议优先补的未完成功能

如果只看“哪些功能值得继续做”，优先顺序建议如下：

1. 正式登录体系  
   这是所有真实用户使用的前提。

2. 训练闭环强化  
   包括：今日训练进度、AI 陪练动作引导、打卡后调整反馈。

3. 提醒与召回  
   当前留存抓手偏弱，提醒系统补齐后价值会明显提升。

4. 分析历史与变化趋势  
   包括照片/体型/体重的阶段性变化展示，这是长期留存的重要内容。

5. 管理后台深化  
   上线后很快就会需要用户运营、异常排查和数据导出。

6. 用户自带 API Key 的稳定化  
   更适合作为高级用户能力，而不是 MVP 首要项。

## 7. 我会怎么收缩产品范围

如果目标是尽快做成一个正式可交付版本，我会主动砍掉或延后以下内容：

- 多 provider 扩展
- 复杂管理后台
- 高级报表
- 过早的社交/社区能力
- 过早的花式成就系统

我会保留并强化：

- 档案
- 体型分析
- 周计划
- 今日训练
- AI 陪练
- 打卡
- 体重趋势
- 提醒

这个范围更小，但能更快形成一条可信的产品价值链。

## 8. 下一步最推荐的动作

如果按投入正式产出来走，下一步不建议直接改代码到处补，而是先做这两件事：

1. 写一版正式的 P0/P1 排期表  
   明确每项的 owner、工期、依赖关系、验收口径。

2. 把 P0 中最危险的三项先立刻开工  
   推荐顺序：
   - 鉴权
   - 分析任务持久化
   - AI 陪练输出契约修复

这三项一旦不做，后面的功能越多，返工成本越高。
